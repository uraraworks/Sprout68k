# Sprout68k IDE 配布設計（2026-08-22）

## 公開境界

公開先は GitHub Pages の `/Sprout68k/` とする。Service Worker は
`/Sprout68k/sprout68k-sw.js` を `scope: /Sprout68k/` で登録し、fetch 処理でも同じパスを
再確認する。Cache Storage 名は `sprout68k-precache-<build ID>` とし、activate 時に
削除するのは `sprout68k-precache-` で始まる旧版だけである。IndexedDB 名は既存の
`Sprout68kProjectFS` を維持する。この3境界により、同一 origin の他アプリへ触れない。

## 公開物とオフライン

`vite build` の終了時に `tools/distribution.mts` が次を `build/web-page/` へ収集する。

- Vite が生成した IDE、検証ページ、px68k コア、ROM、ライセンス
- `build/web-assets/manifest.json` の全エントリ（サイズとSHA-256も照合）
- `build/wasm-tools/` の cc1、as、ld、objcopy 各 memfs JS／wasm

公開物を走査して `offline-manifest.json` と Service Worker の pre-cache 一覧を生成する。
一覧の手書きは行わない。`tools/verify_distribution.mts` は、公開物集合、pre-cache一覧、
manifestの内容、HTML参照先が一致することを検査する。

## 更新

build ID はIDE／検証ページの入力、束manifest、wasmツールの内容から生成する。
新しいService Workerは固有名のcacheを全件取得してから `skipWaiting()` し、activate後に
自分の接頭辞を持つ旧cacheだけを削除して `clients.claim()` する。登録は
`updateViaCache: none` とし、Service Worker本体のHTTPキャッシュによる更新遅延を避ける。
既に開いている画面は処理中のソースを守るため強制再読込せず、フッタのbuild IDで
公開版との食い違いを確認できるようにした。次回再読込から新cacheが使われる。

## Chromiumの早期サブリソース要求

初版のオフライン実測では、SWが返したHTMLは表示できた一方、Viteが`head`へ置いた
module、modulepreload、stylesheetの3要求だけが`workerStart=0`でnetworkへ出て失敗した。
同じURLを制御済みページから同じCORS条件でfetchするとSW経由で成功し、cache内Responseも
正常だったため、`crossorigin`、cache内容、fetch handlerは原因から除外できた。差は要求時点
だけであり、Chromiumのpreload scannerがnavigation先clientのSW制御確定前に外部タグを
先読みしたことが真因である。

配布工程ではIDE HTMLから外部のmodule／modulepreload／stylesheetタグを除き、deferされる
inline moduleが文書確定後にCSSとmoduleをfetchしてからentryをimportする。これにより初期の
先読み要求を発生させず、制御確定後のSW経路だけでページを組み立てる。

その後のオフライン実測では、CSSとpreload chunkはSW経由で200になった一方、entryだけが
`workerStart=0`になった。生成HTMLを比較すると前2本は`fetchRequired()`、entryだけは
native `import(ENTRY_MODULE)`であり、同じcache／controller下でこの取得方式だけが異なっていた。
よって残った原因はプリロード一般ではなく、Chromiumのdynamic import module loaderがこの
オフライン再読込条件でSW fetchへdispatchしない経路だと確定した。

entryとその静的依存chunkも`fetchRequired()`で文字列として取得し、依存specifierを取得済み
chunkのBlob URLへ置換してからentryをBlob importする。ネットワークURLに対するnative importを
なくし、全起動資産を実測済みの明示fetch経路へ統一した。

## cache退去と自己修復

Cache Storageを削除しても、同じSW scriptのinstallは再実行されない。さらにunregister後も
制御中clientが存在する間はactive workerが生存し、同じscope／scriptを直ちに再登録すると
既存activeが再利用され得る。実測の`installing=null`、`waiting=null`、`active=activated`は
install失敗ではなく、installが走っていない状態を示す。`waitUntil()`へ渡したprecache promiseが
rejectした新workerはactivatedになれないためである。

SWは`addAll`を使わず、生成されたprecache一覧の全件を1件ずつURL・サイズ・SHA-256検証して
格納する。install中に
失敗した場合はURLと原因をconsoleおよびclientへ通知し、部分cacheを削除してpromiseをrejectし、
activateを阻止する。active workerはactivate時、IDE起動時のmessage、precache対象のfetch miss時、
ブラウザのonline復帰時に不足を検査・補充する。既存cacheの一部が残る場合は正常な項目を保持し、
不足分だけを補う。全件確認が終わるまでUIは「準備中」、完了後は「オフラインでも使えます」、
失敗時は「オフライン準備に失敗しました」とする。

## 20MBのwasmツールを公開する方式（決定）

memfs版8ファイルは決定的archiveとsidecar manifestをGitHub Releaseへ添付する。
Pages workflowは設定されたRelease URLから取得し、追跡済みmanifest SHA-256、archive全体、
展開した各fileの順に検証してからVite buildを行う。repoへの20MBのコミットは履歴肥大化を、
Actionsでの再ビルドはLinux移植の新規作業とcache退去時の長時間化を招くため採用しない。
詳細と手動コマンドは`docs/Release配布手順_20260822.md`に記録した。

## 実行方法

```sh
../WebX68k/node_modules/.bin/vite build
node tools/verify_distribution.mts
../WebX68k/node_modules/.bin/vite preview
```

previewの `/Sprout68k/ide/` を一度読み込み、ビルドと実行を完了させてからサーバーを停止し、
同じURLを再読込してオフライン動作を確認する。Service Workerの登録にはlocalhostまたはHTTPSが必要である。
