# コンパイラ wasm 化 作業記録 20260820

## 目的と現在地

目的は、**ブラウザの中で C ソースから X68000 用ディスクイメージまでを
ビルドできる経路を作ること**である。現在の通常ビルドはホストにインストールした
`m68k-elf-gcc`（および binutils）に依存しており、ブラウザだけでは完結しない。

本書はコミット `8f941d7`、`896e788`、`36c4e4a`、`8da2b7d`、`97fcf26`、
`59ad3b8`、`5ee9cbb`、`d6ec296`、`4833e82`、`3b769d9`、`146b977`、
`d995234`、`827e50c` と、
`tools/build_native_toolchain.sh`、`tools/build_wasm_binutils.sh`、
`tools/build_via_cc1.sh`、`tools/driver/` の内容を照合してまとめた作業記録である。
**完了した検証と未完了の工程を混同しない。F-2/F-3 のツールチェーンは
Node 上の NODERAWFS/MEMFS 両形態で完了した。F-4ではChromium系ブラウザ1種で
Cソースから `.xdf` を生成し、ネイティブ正典とのバイト一致まで実測した。一方、
学習者向けUI、配布方式、ブラウザ内px68kへの受け渡しはまだ無い。**

## コンパイラ本体の選定: GCC

コンパイラ本体には GCC を採用した。判断材料は次の2点。

### 権利

vbcc / vasm / vlink の配布条件は「非商用のみ」「無改変での再頒布」であり、
商用利用の例外も M68k + AmigaOS に限られるため X68000 は対象外となる。
さらに、Emscripten で生成した JS / wasm を配布する行為が「無改変での再頒布」に
収まるかが明瞭でない。この不確実性を採用すると、このプロジェクトで維持してきた
「権利は論点にならない」という前提を壊す。

GCC は GPL で、ライセンス条件に従った改変と再頒布の経路が明確である。
px68k も GPLv2 であり、採用するコンパイラを同じ自由ソフトウェアの世界に
置けることを優先した。

### バイト一致する基準器を作れること

同じ GCC / binutils ソースからネイティブ版と wasm 版を作れば、各ツールの出力が
ネイティブ版とバイト一致するかを最初から判定条件（オラクル）にできる。
単に「動いたように見える」ことではなく、どのツールを wasm に替えた時点で差が
生じたかを切り分けられる。

## 工程の切り方と判定条件

工程は次の順に分離した。

| 工程 | 内容 | 2026-08-20 時点 |
|---|---|---|
| F-1 | driver を外した駆動モデルの分離検証 | 完了 |
| F-0 | 同一ソースで作る正典ネイティブ基準器 | 完了 |
| F-2 | binutils（as / ld / objcopy）の wasm 化（NODERAWFS/MEMFS） | 完了 |
| F-3 | GCC `cc1` の wasm 化（NODERAWFS/MEMFS） | 完了 |
| F-4 | ブラウザの仮想FSとビルド経路（検証ページ） | **完了（Chromium系1種）**。学習者向けUIとpx68k結線は未完了 |

各段の判定条件は、原則として**ネイティブ出力とのバイト一致**である。また
`cc1` / `as` / `ld` / `objcopy` を一括で切り替えず、ツール単位で native / wasm を
差し替える混成モードを常に持つ。これにより、たとえば `as` だけを wasm に替え、
その前後を native のまま比較できる。

## バイト一致は同時に機能検証でもある

移植前後で同じ入力に同じ出力を要求できるのは、コンパイラ／バイナリツール移植の
強みである。このため、単に終了コード0やファイル生成を確認するのではなく、正典
ネイティブ版の `.o` / `.elf` / `.bin` / `.xdf` との**バイト一致**を合格条件にした。
最終 `.xdf` の一致は、それを構成するコード生成・アセンブル・リンク・バイナリ変換の
結果が既存検証を通った正典と1バイトも違わないことを示し、同時に機能検証になる。

さらに `cc1` / `as` / `ld` / `objcopy` を個別に置換する混成モードで、差が出た場合の
帰属先をツール単位に絞れるようにした。#6（NODERAWFS版 `cc1`）と #8（全MEMFS版）では
`cc1.wasm` を読めなくする故障注入も常設した。両方が実際に失敗するため、wasm 指定が
黙って元の native 経路へ落ち、その結果だけが一致している可能性も潰している。

## F-1: driver を外した駆動モデルの検証（`8f941d7`）

ブラウザでは GCC driver が子プロセスとして `cc1` / `as` / `ld` を起動する形を
そのまま使えないため、まずホスト上で各ツールを直に呼ぶ経路が等価かを分離して
検証した。`objcopy` も最終バイナリ生成のため個別に呼んでいる。

Stage C と breakout の両方で、gcc driver 経由と直呼び経路を比較し、
**`.o` / `.elf` / `.bin` / `.xdf` がすべてバイト一致した**。また比較検査が
空振りしていないことを確かめる陽性対照として最適化を `-Os` から `-O0` に替え、
こちらは不一致になることも確認した。この結果が示すのは「ネイティブ環境で
driver を外しても同じ成果物を作れる」ことまでであり、wasm 版ツールの動作を
示す結果ではない。

## F-0: 正典ネイティブ基準器（`896e788`、`97fcf26`）

binutils 2.44 と GCC 13.4.0（C のみ、target libgcc を含む）を自前ビルドし、
ネイティブ基準器を作った。バージョンは `docs/toolchain調査.md` で確認した
elf2x68k / xdev68k の正典と合わせている。

この基準器は2つの理由で必要になる。

1. wasm 版 `cc1` は概念上
   `build=darwin / host=wasm32-emscripten / target=m68k-elf` の Canadian cross
   となる。その構築には、ビルド途中の target 用生成物を作るネイティブ
   `m68k-elf` クロスツールチェーンが前提となる。
2. Homebrew の GCC 16.2.0 は、この作業で合わせる GCC 13.4.0 とは版が異なり、
   configure 内容も不明である。同一ソース・同一 configure の wasm 版と比べる
   バイト一致の基準器にはできない。

newlib、C++、gdb は今回のフリースタンディング C の経路には含めていない。一方、
`libgcc` は省略できない。既存 `.o` を `nm` で調べ、
`__mulsi3` / `__modsi3` / `__udivsi3` / `__umodsi3` への未定義参照が実在することを
確認したため、`all-target-libgcc` / `install-target-libgcc` までを基準器の
ビルド対象にした。

GCC 13.4.0 へ切り替えた成果物について、px68k 上で `verify/verify.mts`、
`verify/verify_lib.mts`、`verify/verify_l1.mts`、`verify/verify_panic.mts`、
`verify/verify_breakout.mts` を実行し、Stage A〜D、lib、L1、パニック画面、作例の
既存検証がすべて通過することを確認した。

## F-2: binutils の wasm 化

binutils 2.44 の `as` / `ld` / `objcopy` を、Node専用の NODERAWFS 形態と、
ブラウザ結線用の modularized factory + MEMFS 形態の2種類でビルドした。
サイズ実測は後述の F-3 と合わせて表に示す。

`SPROUT68K_TOOLCHAIN=$HOME/x68kdev-toolchain` の正典ネイティブ版を基準に、Stage C と
breakout のそれぞれで全 native、as のみ wasm、ld のみ wasm、objcopy のみ wasm、
binutils 3本 wasm の5構成を実行した。全構成で `.o` / `.elf` / `.bin` / `.xdf` が
すべてバイト一致した。MEMFS形態を含む全ツール置換も混成表 #8 で同じ結果となった。
このprefixはビルド時の絶対パスとしてネイティブcc1へ焼き込まれている。ディレクトリだけを
改名すると内部ヘッダを発見できず、再ビルドするとバイト一致の基準器自体が別物になる。
そのため製品名の改名後もディレクトリ名は維持し、製品側の環境変数名だけを
`SPROUT68K_TOOLCHAIN` とする。既定値を親切心で製品名へ揃えてはならない。
再実行手順と不一致時の `cmp -l` / `objdump -drs` 診断は
`tools/driver/verify_wasm.mts` に固定した。

NODERAWFS形態の生成 JS は modularized factory ではなく、ロード後に `process.argv` を
渡して main を自動実行する形式だった。runner はツール呼び出しごとに独立した Node
子プロセスを起動する。NODERAWFS による絶対パスの入出力、引数の受け渡し、正常終了0に
加え、不正引数時の終了コード1を runner が失敗として扱うことまで実測した。

MEMFS形態は毎回 factory から新しいモジュールを生成し、`preRun` で入力と出力先を
仮想FSへ用意してから `callMain()` を呼ぶ。同一モジュールを再実行するとクラッシュする
ことを実測したため、モジュールの使い回しは不可と確定した。

## F-3: GCC `cc1` の wasm 化（`5ee9cbb`、`4833e82`）

`tools/driver/` に、`cc1` / `as` / `ld` / `objcopy` をツール単位で native / wasm に
差し替える駆動層を作った。コマンド列の正典は `tools/driver/build.mts` に一本化し、
従来の `tools/build_via_cc1.sh` はその薄いラッパーにした。

native 経路に加え、F-2 で Node/NODERAWFS 用 wasm runner を実装した。指定した
Emscripten JS が未指定または存在しない場合は明示的にエラーで停止する。
続いて GCC 13.4.0 の `cc1` を
`build=darwin / host=wasm32-unknown-emscripten / target=m68k-elf` でビルドし、
同じ runner から起動できるようにした。

混成表の実測結果は次のとおり。Stage C / breakout の両方で、各構成の
`.o` / `.elf` / `.bin` / `.xdf` を #1 と比較した。

| # | cc1 | as | ld | objcopy | Stage C | breakout |
|---:|---|---|---|---|---|---|
| 1 | native | native | native | native | PASS（基準） | PASS（基準） |
| 2 | native | wasm | native | native | PASS（全成果物バイト一致） | PASS（全成果物バイト一致） |
| 3 | native | native | wasm | native | PASS（全成果物バイト一致） | PASS（全成果物バイト一致） |
| 4 | native | native | native | wasm | PASS（全成果物バイト一致） | PASS（全成果物バイト一致） |
| 5 | native | wasm | wasm | wasm | PASS（全成果物バイト一致） | PASS（全成果物バイト一致） |
| 6 | wasm | native | native | native | PASS（全成果物バイト一致） | PASS（全成果物バイト一致） |
| 7 | wasm | wasm | wasm | wasm | PASS（全成果物バイト一致） | PASS（全成果物バイト一致） |
| 8 | memfs | memfs | memfs | memfs | PASS（全成果物バイト一致） | PASS（全成果物バイト一致） |

#1〜#7 は NODERAWFS形態、#8 は MEMFS形態である。#6と#8の `cc1.wasm` 故障注入も
それぞれ失敗を検出した。さらに両形態ともビルド木を捨て、クリーンな状態から
再現ビルドが `EXIT=0` で完了することを確認し、そのクリーン版生成物でも #1〜#8を
再実行して全件PASSした。

クリーンビルド版の wasm 本体を2026-08-20に測定した概数は次のとおり。gzip は
`gzip -9` による値で、4本の合計が配布量の大半を占める。

| ツール | raw | gzip |
|---|---:|---:|
| cc1 | 16.8 MB | 5.7 MB |
| as | 888 KB | 351 KB |
| ld | 1.28 MB | 400 KB |
| objcopy | 677 KB | 274 KB |
| **配布合計** | — | **約6.7 MB** |

速度は Stage C の `main.c` 1本の `cc1` で native 0.07秒、NODERAWFS版 wasm
1.93秒（約28倍）、混成検証一式で約79秒だった。いずれも Node 上の実測であり、
ブラウザ上の速度ではない。

MEMFS版 `cc1` では、自作ヘッダと `GCC_EXEC_PREFIX` を初期化前の `preRun` でFSへ
配置する必要があった。`/tmp` ディレクトリが無くても今回の入力は成功した。
また `callMain()` は不正引数でも例外を投げず戻り値1を返すため、runner側で非0の
戻り値を捕捉して失敗へ変換する。全ツールとも1回の実行ごとに factory から新しい
モジュールを生成する。

## 途中で踏んだ罠

### ビルド木の残骸を「正しいスクリプト」と誤認した

今回もっとも重要な学びである。最初の NODERAWFS版は増分ビルドで完成したように
見えたが、木を捨てて MEMFS版へ展開すると再現しなかった。次の3件は別々の不具合では
なく、前の試行が残した生成物へ暗黙に依存した同じ根の問題だった。

- top-level の `configure-gcc` を実行する工程が欠けていた。
- ジェネレータが必要とする build側（ネイティブ）のライブラリを作っていなかった。
- `gcc` サブディレクトリを `emmake` で直接叩くと、ネイティブであるべき
  `genmodes` / `genmatch` / `genhooks` / `genchecksum` 等まで `em++` でリンクしてしまう。
  build/host の区別を持って正しく依存を作れるのは top-level の make だけである。

逆向きの混入も起こり得る。誤った手順で wasm オブジェクトが build側へ残ると、次の
試行でネイティブの `c++` がそれをリンクし、`unknown file type` で停止する。つまり
残骸は不足を隠すだけでなく、別形態の成果物を混ぜて後続を壊す。

**教訓**: 増分ビルドは前回の木の状態を暗黙の入力にする。「スクリプトの正しさ」を
測っているつもりでも、実際には「木の状態＋スクリプト」を測っている。手順を書き換えた
直後と別形態へ展開する直前は、ビルド木を捨ててゼロから通す。`-k` で不要ターゲットの
失敗を越える設計にする場合は、欲しい成果物（今回は `cc1`）の存在を明示的に検査し、
失敗を握り潰したまま成功扱いしない歯止めを置く。

### 1. `make: *** Error 2` を exit 0 と誤読した

**症状**: ビルドログ末尾には `make: *** Error 2` が出ていたのに、実行結果を
成功（exit 0）と読んでしまった。

**真因**: 長いログを `| tail -40` で受けており、確認していたのは `make` ではなく
パイプ末尾の `tail` の終了状態だった。

**どう気づいたか**: 完了したはずの生成物を確認し、`bin/m68k-elf-gcc` が存在しない
ことを見て初めて、表示された終了状態とビルド本体の成否が一致していないと分かった。

**再発防止**: ビルドスクリプトは `set -euo pipefail` を使う。ログをパイプへ流す
場合も `pipefail` を有効にし、最終判定では終了状態だけでなく期待する生成物の
実体と、生成したツール自身の `--version` 等を確認する。

### 2. binutils 同梱 zlib と最近の macOS SDK ヘッダが衝突した

**症状**: 正典 binutils のネイティブビルドが zlib 周辺で落ちた。

**真因**: binutils 同梱 zlib が最近の macOS SDK ヘッダと衝突していた。正典の
elf2x68k は `--with-system-zlib` を付けて回避しているが、その指定を初版の
スクリプトへ反映していなかった。

**どう気づいたか**: エラー箇所を追い、既に読んでいた `docs/toolchain調査.md` と
elf2x68k の configure 条件を見直すと、`--with-system-zlib` が記録済みだった。
必要な情報を調査資料に残していたのに、実装時に拾えていなかった。

**再発防止**: `tools/build_native_toolchain.sh` の binutils と GCC の configure に
`--with-system-zlib` を明記した。正典を再現するスクリプトでは、実装前に調査資料の
configure オプションをチェックリストとして突き合わせる。

### 3. multilib をディレクトリ名で決め打ちした

**症状**: libgcc のビルド後にもかかわらず、「`-m68000` 用 multilib が無い」と
完了確認が常に失敗した。駆動層も `m68000/libgcc.a` という配置を決め打ちしていた。

**真因**: GCC を `--with-cpu=m68000` でビルドすると、`-m68000` は名前付きの
`m68000` multilib ではなく既定 multilib（`.`）を選ぶ。そのため `m68000` という
ディレクトリ名の存在は、`-m68000` 用 libgcc の有無を表さない。

**どう気づいたか**: `-print-multi-lib` の出力と実際の配置を照合し、
`-m68000` を指定した GCC 自身に選択先を問い合わせると既定 multilib が返った。

**再発防止**: 名前や配置を解釈せず、GCC に
`-m68000 -print-multi-directory` と `-m68000 -print-libgcc-file-name` で答えさせる。
基準器の完了確認と `tools/driver/toolchain.mts` の双方をこの方式に直した。

### 4. 駆動層の自己検証が同語反復になった

**症状**: 新しい駆動層の検証が PASS していたが、独立した既存経路との等価性を
証明していなかった。

**真因**: `tools/build_via_cc1.sh` を駆動層のラッパーに変更した後も、検証側が
「`build_via_cc1.sh` 対 駆動層」を比較していた。両辺が同じ実装を通るため、比較が
同語反復になっていた。

**どう気づいたか**: 比較の両辺を呼び出し先まで辿ると、どちらも
`tools/driver/build.mts` に到達することが分かった。

**再発防止**: 比較相手を gcc driver 経由の実物、すなわち Stage C は
`tools/build_stage_c.sh`、breakout は `tools/build_breakout_plain.sh` に差し替えた。
陽性対照（`-Os` 対 `-O0`）も残し、比較が差を検出できることを確認する。

### 5. Emscripten libc の `psignal` は宣言だけで実体がなかった

**症状**: wasm 版 binutils のビルドが、libiberty の `psignal` 代替定義と
Emscripten のヘッダにある宣言の型不一致で落ちた。

**真因**: Emscripten libc は `psignal` を宣言するが実体を持たない。configure は
関数なしと判定して libiberty の代替定義を有効にするが、代替側の引数型
`char *` とヘッダ側の `const char *` が衝突した。

**どう気づいたか**: コンパイルエラーに現れた2つの宣言を追い、ヘッダ上の宣言、
関数実体の欠如、configure が選んだ libiberty の代替定義を突き合わせた。

**再発防止**: binutils 本体は `psignal` を使わないため、configure 時に
`ac_cv_func_psignal=yes` を渡して代替定義を無効化した。もし呼び出しが残って
いれば、未定義シンボルとしてリンク時に必ず表面化する。この修正後に F-2 の
ビルドと混成モード比較まで完走した。

### 6. in-tree ライブラリの `config.sub` だけが host=wasm を弾いた

**症状**: GCC 本体の configure は進む一方、in-tree の mpfr/isl が
`wasm32-unknown-emscripten` を `system 'emscripten' not recognized` として弾いた。

**真因と対策**: mpfr/isl 同梱の `config.sub` が古かった。gmp と GCC 本体は同じ host を
認識するという非対称があるため、GCC 本体の新しい `config.sub` を認識できない
サブディレクトリへだけ配る処理を `build_wasm_gcc.sh` に入れた。

### 7. `--with-system-zlib` は host=wasm では成立しなかった

**症状**: ネイティブ基準器と同じ `--with-system-zlib` では `zlib.h` が無く、
`lto-compress.cc` のコンパイルが停止した。

**真因と対策**: Emscripten 側には利用する system zlib が無いため、wasm 側は
`--without-system-zlib` で in-tree zlib を使う。最近の macOS SDK と in-tree zlib が
衝突するネイティブ側とは指定が逆になる。最終的なコード生成への影響がないことは
混成表のバイト一致でも確認できた。

### 8. `all-gcc` は不要な gcov-tool の `ftw` で停止した

**症状**: `all-gcc` が gcov-tool まで作ろうとし、`libgcov-util.o` の要求する `ftw` が
Emscripten libc に無いため wasm-ld で停止した。

**対策**: build/host の依存関係を正しく作るため top-level の `all-gcc` は使い、`-k` で
不要な gcov-tool の失敗を越える。終了後に今回欲しい host executable である `cc1` の
存在を明示検査し、無ければ失敗とする。`gcc` サブディレクトリの直接ビルドは、前節の
とおり build側ジェネレータまで `em++` でリンクするため対策にはならない。

## F-4で済んだことと、次に残っている宿題

F-4ではHostFs抽象化、`nm` 依存撤去、配信用アセット束、検証ページまでを実装した。
Chromium系ブラウザ1種で Stage C は1,889 ms、breakoutは11,182 msで `.xdf` を生成し、
両方のSHA-256がネイティブ正典と一致した。故障注入による不一致検出も実測済みである。
構成、SHA-256、束サイズ、ヒープ値、罠の記録は
[`ブラウザ結線_20260821.md`](ブラウザ結線_20260821.md) にまとめた。

したがって「ブラウザでツールチェーンを動かし、同じ `.xdf` を作れるか」は完了した。
次の項目はその結果に含まれず、引き続き未設計または未実装である。

- **配布方式。** 39ファイル・gzip 250,046バイトのアセット束と、wasm込みgzip
  7,061,641バイトについて、初回取得、Cache Storage、分割、更新、キャッシュ無効化、
  オフライン動作を設計していない。
- **学習者向けUI。** コンパイルや実行の失敗から1クリックで既知の状態へ戻り、編集した
  ソースを失わないUIと状態管理は無い。今回のページは自動検証用である。
- **コンパイルエラーの日本語注釈層。** GCCの原文を保持しつつ初心者向け説明を重ねる
  層は無い。
- **px68kとのブラウザ内結線。** 生成した `.xdf` をブラウザ内px68kへ渡して実際に起動する
  ところまでは結線していない。
- **ブラウザ差。** 実測はChromium系1種だけで、Safari / Firefoxは未実測である。
