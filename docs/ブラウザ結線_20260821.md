# ブラウザ結線 F-4 実測記録 2026-08-21

## 目的と結論

F-4では、Node専用だったX68000向けビルド駆動層をブラウザから利用できる形へ分離し、
配信用アセットだけを入力として `cc1` → `as` → `ld` → `objcopy` を実ブラウザで
実行した。Chromium系ブラウザ1種で Stage C と breakout の `.xdf` を生成し、
WebCryptoで求めたSHA-256がネイティブ正典と一致することを実測した。

ここで完了したのは、**ブラウザ内でCソースから正典と同じ `.xdf` を作るビルド経路**
である。学習者向けUI、配布・キャッシュ設計、生成した `.xdf` をブラウザ内のpx68kで
起動する結線までが完成した、という意味ではない。

その後、学習者向けIDEとpx68k実行結線まで実装した。後続の確定実測と未実装項目は
[`IDE実装_20260822.md`](IDE実装_20260822.md)を参照。

対象コミットは `3b769d9`、`146b977`、`d995234`、`827e50c` である。

## F-4を4段に分けた結果

### 1. HostFs抽象化とNode依存の分離

`builder.mts` / `runner.mts` / `hostfs.mts` をNode組み込みモジュール非依存の中核にし、
実ファイルシステム、子プロセス、環境変数への依存を `node_hostfs.mts`、
`node_runner.mts`、CLI側へ分離した。ブラウザ側で使う `MemoryHostFs` はPOSIX絶対パスを
持つメモリ内ファイルシステムとして実装した。

実測結果:

- `MemoryHostFs` だけを入出力境界としてmemfsビルドした Stage C / breakout の `.xdf` は、
  それぞれ全native版と **1,261,568バイト一致**した。
- `stage_c/src/main.c` を1バイト変える陽性対照では `.xdf` が不一致になった。
- `verify.mts` はPASS、`verify_wasm.mts` は混成表#1〜#8がPASS、SKIP 0だった。

### 2. `nm` 依存の撤去

breakoutのメモリ衝突検査は、当初native `nm` で `__bss_end` を読む必要があった。
ブラウザに `nm` を追加せず、既に使う `ld` の `-Map` 出力を `HostFs` から読み取る方式へ
変更した。これによりビルドの判定経路からnative実行物への依存を撤去した。

実測結果:

- 変更後も Stage C / breakout はそれぞれ **1,261,568バイト**で全native版と一致した。
- `-Map` 追加前後で breakout の `.xdf` / `.elf` / `.bin` のSHA-256はすべて一致した
  （順に `f08ba572…` / `d20bbd5b…` / `21edcbba…`）。
- 陽性対照では `STACK_ADDR=0x86000` に対し `__bss_end=0x85df4` の衝突を検出し、
  ビルドが失敗した。
- `verify_wasm.mts` は **16件PASS、SKIP 0**だった。

### 3. 配信用アセット束

`tools/build_web_assets.mts` で、リポジトリ内の対象ソース、GCC標準ヘッダ、m68000用
`libgcc.a` を相対パスの束へまとめた。`manifest.json` は各ファイルのサイズとSHA-256、
合計サイズを保持する。GCCの `include` / `include-fixed` からは役割上ヘッダである
`.h` だけを収録し、README等の文書は除外した。拡張子のない配信パスはViteのfallbackを
避けるため束生成時にエラーとする。

最終的な実測値:

| 内容 | ファイル数 | raw | gzip |
|---|---:|---:|---:|
| アセット束 | 39 | 829,971バイト | 250,046バイト |
| アセット束 + wasmツール4本（JS/wasmの8ファイル） | 47 | 20,798,234バイト | 7,061,641バイト |

束だけを `MemoryHostFs` へ流し込むNode検証では、Stage C / breakoutの `.xdf` が
それぞれ全native版と **1,261,568バイト一致**した。必要ファイル
`toolchain/lib/gcc/m68k-elf/13.4.0/include/stdarg.h` を1つ除く故障注入ではbreakoutが
コンパイルエラーになり、束の検査が実際に必要入力を踏んでいることも確認した。

### 4. 実ブラウザでのビルド

Vite dev serverの `http://127.0.0.1:5180/web/` をChromium系ブラウザで開き、ページの
自動処理としてmanifestとアセット、wasmツール4本を取得し、`MemoryHostFs` と
`MemfsWasmToolRunner` を通して `builder.mts` の `build()` を実行した。SHA-256は
`crypto.subtle.digest` で求め、ネイティブ正典から生成した `expected.json` と比較した。

通常実行の確定値:

| ターゲット | ブラウザ生成 `.xdf` のSHA-256 | 判定 | 所要時間 |
|---|---|---|---:|
| stage_c | `e8ec4fca90e24c26d8acc766fd628214afbadb3feab31b959ffc09d4720c2d9c` | 期待値と一致 | 1,889 ms（約1.9秒） |
| breakout | `9df7bdf901b77b62f298bc17e7851594eb5d8cad325f38fc649355c91f3edb4f` | 期待値と一致 | 11,182 ms（約11.1秒） |

`performance.memory` の観測値は、Stage Cで約 **47.8 MB → 73.2 MB**、breakout完了後で
約 **37.4 MB**だった。これはChromium系ブラウザ1種で取得できた値であり、他ブラウザの
メモリ特性を示すものではない。

`http://127.0.0.1:5180/web/?fault=1` では `stage_c/src/main.c` を1バイト変更した。
Stage CのSHA-256は
`2d343f764c4a75ea707952beac73d9d9ac9750cb9d7b78ed7d843d7bf5f2ba27`
となり、期待値との不一致を `detected:true` で検出した。同じ実行のbreakoutは正典と
一致したままであり、故障注入の適用範囲がStage Cだけに閉じていることも確認した。

## 検証の構成と実行方法

Node側の4本はリポジトリ直下で実行する。確定結果はいずれも終了コード0だった。

| 実行コマンド | 検証内容 | 確定結果 |
|---|---|---|
| `node tools/driver/verify.mts` | gcc driver経由と全native駆動層、`-O0` 陽性対照 | 両ターゲット各1,261,568バイト一致、陽性対照は不一致、PASS |
| `node tools/driver/verify_wasm.mts` | native / NODERAWFS / MEMFS混成表#1〜#8を2ターゲットで比較 | **16件PASS、SKIP 0** |
| `node tools/driver/verify_hostfs.mts` | `MemoryHostFs` と全native版、`__bss_end` 衝突、ソース1バイト変更 | 両ターゲット各1,261,568バイト一致、故障2件を検出、PASS |
| `node tools/driver/verify_web_assets.mts` | 束だけのビルド、全native版・expected.json、`stdarg.h` 欠落、サイズ | 両ターゲット各1,261,568バイト一致、欠落を検出、PASS |

ブラウザ検証は先に束と `expected.json` を生成し、借用するViteを起動する。

```sh
node tools/build_web_assets.mts
../WebX68k/node_modules/.bin/vite --config vite.config.ts
```

- 通常: <http://127.0.0.1:5180/web/>
- 故障注入: <http://127.0.0.1:5180/web/?fault=1>

完了時は成功・失敗とも `#result` の `textContent` に1行JSONが入る。通常時は両ターゲット
の `ok` と `allOk`、故障注入時は `faultInjection` と `detected` も外部から判定できる。
進捗と結果はコンソールにも出力する。

## 踏んだ罠

### 拡張子のないファイルへViteが `index.html` を返した

- **症状**: `include-fixed/README` のfetchはHTTP 200だったが、manifestのサイズ・
  SHA-256検査に失敗した。期待した実体は750バイトなのに、取得内容は3,841バイトの
  HTMLだった。
- **真因**: Vite dev serverが拡張子のないパスをSPAの経路とみなし、存在するファイル
  ではなく `index.html` へfallbackした。HTTP成功は要求したファイルの内容が正しい
  ことを意味しない。
- **どう気づいたか**: ブラウザ結果が `manifest 不一致` を報告し、応答サイズと本文を
  調べるとHTMLが返っていることが分かった。各ファイルのSHA-256検査が誤配信を捕捉した。
- **再発防止**: GCCの束は役割上 `.h` ヘッダだけを収録し、README等を除外した。
  さらに拡張子なしまたは末尾dotのパスが束へ入った場合は、生成時に明示エラーとする。
  ブラウザ側のmanifestサイズ・SHA-256検査も残し、200応答だけで入力を信用しない。

### 意図した失敗が `process.exitCode=1` を残した

- **症状**: `verify_web_assets.mts` の表示は全行PASSなのに、プロセス全体の終了コードが
  1になっていた。
- **真因**: `stdarg.h` を故意に欠落させる陽性対照で、EmscriptenのNode用 `quit_` が
  `process.exitCode` を1にした。例外を期待どおり捕捉しても、その値は自動では戻らなかった。
- **どう気づいたか**: PASS表示だけでなく呼び出し元が観測した終了コードまで確認し、
  ログの判定とプロセス状態が矛盾していることから、故障注入前後の `process.exitCode` を
  調べた。
- **再発防止**: 意図した失敗を起こす直前の `process.exitCode` を退避し、捕捉後に復元する。
  正常系は表示だけでなく終了コード0、本当の失敗は非0であることを検証条件にした。

## まだ無いもの

次の項目はF-4のブラウザ内ビルド実測には含まれず、未設計または未実装である。

- **配布方式**: 初回取得、Cache Storage、分割、更新、キャッシュ無効化、オフライン動作。
- **学習者向けUI**: 失敗からの1クリック復帰と、編集中ソースを失わない状態管理。
- **コンパイルエラーの日本語注釈層**: GCC原文を保ったまま初心者向け説明を重ねる仕組み。
- **px68kとのブラウザ内結線**: 生成した `.xdf` を同じブラウザ内のpx68kへ渡し、実際に
  起動するところまでの経路。
- **ブラウザ差の検証**: 実測はChromium系1種だけで、Safari / Firefoxは未実測。
