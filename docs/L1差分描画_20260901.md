# L1 差分描画（静止物を塗り直さない）— 設計

2026-09-01。`lib/src/x68_l1.c` の描画コスト構造を変える。

## なぜやるか（実測）

利用者の作品（ブロック崩し風・描画命令55件）が **6fps** でしか動いていなかった。
原因は2つあり、うち2つ目がこの文書の対象。

1. `fill_rect` が1画素ずつ塗っていた（1画素66サイクル）→ 2026-09-01 に32bit化して2倍（済）
2. 命令一覧の上限64件を超えると毎フレーム全画面転送に落ちる → 512件へ引き上げ（済）
3. **静止している物も毎フレーム塗り直している** ← これ

3 の内訳（16MHz・1フレーム=260,000サイクル基準の実測）:

- 画素: `x68_cls` が前フレームの矩形を背景色で塗り戻し、そのあと利用者が全部描き直すので
  **画面上の全前景を毎フレーム2回塗る**。ブロック50個の作例で約38,000画素/フレーム。
- 命令: 1命令あたり **約5,200サイクル**（pset 0/50/100/200/400 個の掃引で線形を確認）。
  1命令が1フレームに4回触られる（描画・cls塗り戻し・差分比較・一覧の複写）。
  **1フレームに約50命令が天井**という、画素とは別の制約になっている。

同じ画面を「動く物だけ描く」形に手で書き換えると **60fps 出る**（実測）ので、天井は空いている。

## 変更後の流れ

裏バッファへの書き込みを **flip まで遅らせる**。描画関数は命令を記録するだけにする。

1. `x68_cls(color)` … 背景色を覚えるだけ。**画素を触らない**。色が前フレームと違えば全画面dirty。
2. 描画関数（pset/box_fill/box/line/circle）… 命令を `curCmds` に積むだけ。**画素を触らない**。
3. `x68_screen_flip()`:
   1. **突き合わせ**: `curCmds` と `prevCmds` の各命令が同一かを判定する（下記）
   2. **dirty矩形の決定**: 「消えた命令」「増えた命令」「変わった命令」の前後両方の矩形。
      背景色が変わった／初回／溢れたときは全画面1枚。
   3. **再生**: dirty矩形を背景色で塗り、そのあと `curCmds` を**順番どおり**に、
      **dirty矩形へクリップして**描き直す
   4. **転送**: dirty矩形をGVRAMへ送る
   5. `prevCmds = curCmds`

静止している物は dirty に入らないので、画素も命令ごとの手間もかからない。

## 突き合わせは「添字」ではなく「内容」で

現行は `cmds[i]` と `prevCmds.cmds[i]` を添字で比較している。この方式は**挿入・削除に弱い**。
`ide/samples/life.c` のように「生きたマスだけ描く」形だと、マスが1つ死んだだけで以降の
添字が全部ずれ、全命令が「変わった」と判定される。ブロック崩しでもブロックが1個消えた
フレームで同じことが起きる。

そこで2段にする（O(n^2) を避けつつ、実装を単純に保つため）:

1. **添字で先に照合**（速い道）。`cur[i]` と `prev[i]` が同一ならそれで確定。
   挿入も削除も無いフレーム（大多数）はここで終わる。
2. 残った未確定のものだけ、総当たりで相手を探す。未確定数を `m` とすると `O(m^2)`。
   **`m > 64` になったら突き合わせを諦めて全画面dirtyに倒す**（費用を必ず有界にする）。

## dirty矩形の数の上限

dirty矩形が多いと「命令 × dirty矩形」の当たり判定が効かなくなる。
**dirty矩形が 32 枚を超えたら、全画面1枚に畳む**。畳んだ結果は「今の実装と同じ費用」であって、
それより悪くはならない。

再生時は、まず命令の矩形を **dirty全体の外接矩形** と1回だけ比較して大半を捨て、
残ったものだけ個々のdirty矩形と交差判定する。

## 期待される効果（予測。実測で置き換えること）

- 利用者の作品（動くのは玉とパドルだけ、ブロック50個は静止）… dirty は数枚 → **60fps**
- `stars.c`（220個が全部動く）… dirty が32枚を超えて全画面に畳まれる → 現状据え置き
- `life.c`（世代ごとに多数が変わる）… 同上

**「動いている物が少ないほど速い」**という、説明できる費用モデルになるのが狙い。
全部動かす作品が速くならないのは仕様であって、資料にそう書く。

## クリップして再生する理由（重なりの正しさ）

「dirty矩形に交差する命令を、クリップせずまるごと描き直す」は**誤り**。
先に描かれた命令Xと、あとから重ねて描かれた命令Yがあるとき、dirtyがXにだけ触れていると
Xだけが再描画され、Yが持つべき画素をXが上書きしてしまう。
**dirty矩形へクリップして順番どおり全命令を再生する**ことで、全画面を描き直した場合と
同じ結果になることが保証される。

## `x68_pget` の扱い

裏バッファは flip まで最新でないため、`x68_pget` は**その場で裏バッファを作り直してから**読む。
`backbuffer_valid` フラグを持ち、作り直しは1回だけ。次の描画呼び出しで無効に戻す。
（pset→pget を交互に呼ぶと毎回作り直しになるが、その使い方は想定しない。資料に注記する。）

## 検証

`verify/verify_l1.mts` の Model（期待される画面をホスト側で独立に組み立てる）は**変更しない**。
実装が変わっても**画面は1画素も変わらない**はずなので、台本と判定をそのままにして通ることが
そのまま正しさの証明になる（[[feedback_byte_identity_is_also_functional_proof]] と同じ考え方）。

故障注入は既存のものを新構造へ読み替えて残す。最低限、次の3つは**必ず検出できること**を確認する:

- dirty矩形の「前フレーム側」を送らない → 移動前の位置が消し残る
- dirty矩形を背景色で塗らずに再生する → 前の絵が残る
- クリップせずに再生する → 重なりの前後関係が壊れる（上記の理由）

さらに **陽性対照**として、「静止している物を毎フレーム塗り直す（＝最適化を無効化する）」
版を作り、画面が同一であること・遅くなることの両方を確認する。

## 追記（2026-09-01）: 描き方が2つある — 最初の実装が breakout を壊した

上の設計は **`x68_cls` で毎フレーム作り直す流儀だけ**を前提にしていた。これは誤りで、
`lib/include/x68.h` は描き方を2つ公式に持っている。

- **cls方式**: 毎フレーム `x68_cls()` を呼び、画面を背景から作り直して全部を描き直す。
  （`ide/samples/` の move / catch / stars / life、および利用者の作品）
- **frame_begin方式**: `x68_frame_begin()` で「裏バッファは消さず、命令一覧だけを空にする」。
  動かない絵は最初に1回だけ描き、以後は**前の位置を背景色で消して新しい位置だけ描く**。
  （`samples/breakout/block.c`。x68.h の x68_frame_begin のコメントがこの用法を明記している）

差分描画の第一版は「今フレームに再発行されなかった命令＝消えた命令」とみなして背景で
消すため、frame_begin方式では**動かない絵が2フレーム目で全部消える**。
実測: `verify_breakout.mts` が `drawnPixels=576`（パドル512＋ボール64のみ、ブロック32個が消滅）で不合格。

### 直し方: フレームの開始関数で流儀を決める

流儀は**そのフレームで `x68_cls()` を呼んだかどうか**で判定する。

- `x68_cls()` を呼んだ → **再構築フレーム**。命令一覧が画面の正。
  本文書の本体どおり（遅延記録 → 突き合わせ → dirty矩形 → 背景で塗ってクリップ再生 → 転送）。
- 呼んでいない（`x68_frame_begin()` を使う、または何も呼ばない）→ **追記フレーム**。
  **裏バッファが画面の正**。描画命令は**その場で裏バッファへ描き**、その矩形をそのまま
  dirty に積む。突き合わせも「消えた命令の消去」も行わない。
- 前フレームと流儀が変わった場合、および同一フレーム内で両方が呼ばれた場合は、
  安全側に倒して**全画面dirty**にする（裏バッファの由来が切り替わるため）。

費用モデルはどちらの流儀でも「**描いたもの・変わったものにだけ費用がかかる**」で一致する。
frame_begin方式はもともと利用者が自分で差分を作っているので、追記フレームの費用は
そのまま「利用者が描いた分」になる。

### この穴が示していること

`verify_l1.mts` は cls方式の台本しか持っていなかったため、**全項目PASSのまま
frame_begin方式が丸ごと壊れていた**。`verify_breakout.mts` が別の流儀を使っていたおかげで
検出できた。**検査台本が1つの流儀しか通っていないと、もう一方は無検査で通過する。**
この修正と同時に、`verify_l1.mts` に frame_begin方式の台本を足すこと。

## 追記2（2026-09-01）: 実測して分かった2つの誤り

差分描画を入れたあとの実測（16MHz、1フレーム=260,000サイクル）:

| 条件 | ②③後 | ①後 |
|---|---|---|
| 利用者作品と同構成（命令55件、動く物1個） | 15fps | 30fps |
| 同・ブロック10個（命令15件） | 30fps | 60fps |
| `ide/samples/stars.c`（星220個が全部動く） | 8.8周/秒 | **2.4周/秒（悪化）** |

### 誤り1: 畳み先を「全画面」にしたのが逆効果だった

「dirty矩形が32枚を超えたら全画面1枚に畳む」は、**畳む前より高くつく**場合がある。
stars.c は星220個が全部動くので dirty は440枚になるが、**その総面積は440画素しかない**。
全画面に畳むと 262,144画素の塗り直しと512KBの転送になり、旧実装（220個の小矩形を
背景で塗り、220個を描き直し、440個の小矩形を送る）より桁違いに高い。

**直し方: 畳み先を「全画面」ではなく「旧実装と同じ再塗り」にする。**

- 前フレームの各命令の矩形を背景色で塗る（旧 `x68_cls` の塗り戻しと同じ）
- 今フレームの全命令を順番どおりに、クリップせず描き直す
- 突き合わせで不一致だった命令についてだけ、前後の矩形を転送する（旧 `flip` の差分転送と同じ）

こうすると**畳んでも旧実装と同じ費用**になり、「最適化したのに遅くなる」が原理的に起きない。
dirty矩形の一覧をメモリに持つ必要も無い（突き合わせ結果を辿るだけで済む）。

### 誤り2: 再生時に早期棄却が無く、動く物1個で全命令を舐めていた

実測（命令55件、うち動く物1個。1フレーム=260,000サイクル）:

- 全部静止 … 1フレーム（＝命令の記録と突き合わせだけなら 55件で約179,000サイクル）
- 動く物1個 … **2フレーム**（＝1個動いただけで81,000サイクル以上増える）
- 命令35件＋動く物1個 … 1フレーム

dirty矩形は2枚（玉の前の位置と今の位置、各4x4）しかないのに、
**dirty矩形ごとに全命令へ `exec_cmd_clipped` を呼んでいる**ため、(命令数 × dirty枚数) 回の
関数呼び出しが起きる。クリップの結果が空でも呼び出し費用は払う。

**直し方: 呼ぶ前に矩形の交差を判定する。**

1. dirty矩形全体の外接矩形を1つ作り、各命令とまず1回だけ比較して大半を捨てる
2. 残ったものだけ、個々のdirty矩形と交差判定する
3. 交差したものだけ `exec_cmd_clipped` を呼ぶ

判定はインラインの整数比較4回で済む。関数呼び出しを伴ってはいけない。

### 命令1件あたりの固定費（参考）

`memcpy` を32bit化する前は **5,850サイクル/件**、32bit化後は **3,250サイクル/件**（実測）。
40バイトの命令構造体の代入が gcc によって `memcpy` 呼び出しになっており、その `memcpy` が
1バイトずつのループだったため。静止した命令なら現在 **60件までは1フレームに収まる**（実測）。
