# Stage E-1 実測 20260819

`docs/API設計_20260819.md` の Stage E-1(65536色1ページの GVRAM 論理サイズと
1ライン当たりのバイト数)を実測した。幅を推測して当てにいく方式は使わず、
GVRAM の線形オフセット→画面座標の対応を全数で取ってから stride を求めた。

## 結論

| 項目 | 値 |
|---|---|
| stride(1ライン当たりのワード数) | **512 ワード = 1024 バイト** |
| 幅(SCREEN_W) | **512 ドット** |
| 高さ(SCREEN_H) | **512 ライン**(y=511 まで可視、y=512 は不可視) |
| GVRAM オフセット0の出力座標 | **(x=0, y=0)。原点のずれ無し** |
| フレームバッファ(canvas)全体のサイズ | 768 x 512(65536色グラフィック面は左側512ドットぶんのみを占める。右側256ドットぶんは今回未使用) |

Stage B/C のコード中コメントにあった「512x512dot = 0x80000バイト」という
(ソース読解による)推測値と、今回の実測結果(512幅 x 512高さ = 262,144ワード
= 0x80000バイト)は一致した。ただし本資料の値は実測によるものであり、
上記コメントはあくまで裏付けとして扱う(出所は分けて記録する)。

## 測定方法

`stage_e/src/main_e1.c` が、Stage B/C と同じ3レジスタ設定
(`$E80028`=`$08`, `$E82401`=`$03`, `$E82601`=`$01`)で65536色1ページモードを
有効にした後、ビルド時に埋め込んだ `(GVRAMワードオフセット, 16bit色値)` の
組(`markers[]`、`tools/gen_markers_e1.py` が生成)だけを GVRAM に1ワードずつ
書く。画面全体を単色で塗る検査は使っていない(未描画画面が最も強くその条件を
満たしてしまうため)。

起動後、px68k(WebX68k のコア)を Node から直接駆動して数千フレーム実行し、
`putImageData` で捕まえたフレームバッファ全体を走査、背景色以外のピクセルを
ラスタ順(y→x昇順)に集めて N(GVRAMオフセット)と対応付けた
(`verify/verify_e1.mts`)。

### 一次マーカー集合(候補stride推定)

N = 0, 1, 2, 255, 256, 257, 511, 512, 513, 767, 768, 769, 1023, 1024, 1025
にそれぞれ異なる16bit色を書いた。実測された N→座標の対応表:

| N | 観測座標 (x,y) | 観測RGB |
|---|---|---|
| 0 | (0, 0) | 0,4,0 |
| 1 | (1, 0) | 82,52,123 |
| 2 | (2, 0) | 165,109,8 |
| 255 | (255, 0) | 0,158,140 |
| 256 | (256, 0) | 90,215,24 |
| 257 | (257, 0) | 173,20,156 |
| 511 | (511, 0) | 8,77,41 |
| 512 | (0, 1) | 99,125,173 |
| 513 | (1, 1) | 181,182,57 |
| 767 | (255, 1) | 16,231,189 |
| 768 | (256, 1) | 107,44,74 |
| 769 | (257, 1) | 189,101,206 |
| 1023 | (511, 1) | 24,150,90 |
| 1024 | (0, 2) | 115,207,222 |
| 1025 | (1, 2) | 198,12,107 |

境界候補(256/512/768/1024)のうち、実際に「x が0へ戻り y が+1される」折り返しが
起きたのは **512 と 1024** のみ(1024 は 512 の2倍なので同じ折り返しの裏付けに
なる。256・768 では折り返しが起きなかった)。この実測から stride=512 を候補とし、
全15点の座標を stride=512・原点(0,0)から予測した値と実測値を突き合わせたところ
**すべて一致**(矛盾なし。`E1_STRIDE_SELF_CONSISTENT=true`)。

### 色の潰れ検査

`verify_e1.mts` は観測された非背景色の種類数がマーカー投入数と一致することを
実行時に検査する(一致しなければ対応表を作らずその場で異常終了)。一次マーカー
集合では **観測色15種 = 投入15種で一致**(`E1_COLOR_COLLISION_CHECK ok=true`)。

検出器自体が実際に機能するかも自己故障注入で確認した。わざと2つのマーカー
(N=0とN=300)に同一16bit色を与えたところ、観測色は2種類(投入3種類)となり、
検出器は不一致(潰れ)を正しく検出した(`E1_COLOR_COLLISION_SELF_FAULT_INJECTION_DETECTED=true`)。

### 陰性対照

マーカーを1つも書かない検体(レジスタ設定のみ)を同じフレーム数実行し、
背景色(黒 `0,0,0`)以外のピクセルが1つも観測されないことを確認した
(`E1_NEGATIVE_CONTROL_OK=true` 非背景クラスタ数=0)。

### 入力追従

一次マーカー集合の全オフセットに定数50を足した2本目を実行し、stride=512・
原点(0,0)から予測した新しい座標と実測座標を突き合わせた。全15点が一致
(`E1_INPUT_FOLLOWS=true`)。境界をまたぐケース(N=511+50=561 は
predicted=(49,1) のように行が繰り上がる)も含めて追従を確認した。

### 高さ(下端)の実測

候補stride=512の倍数で N = 512×100, 512×511, 512×512 にマーカーを投入した。

| N | 予測y | 可視 |
|---|---|---|
| 51,200 | 100 | 可視 |
| 261,632 | 511 | 可視 |
| 262,144 | 512 | **不可視** |

y=511 までは可視、y=512(=512本目の行、canvas高さと同じ512を超えた位置)は
不可視だった。これにより **高さ512ライン**(y=0〜511)を実測で確定した。

## 確定できなかった項目

なし。上記の対応表・stride・幅・高さ・原点はすべて矛盾なく1つの stride
(512ワード)で説明できた。

## 実行方法

```sh
npx --no-install tsx verify/verify_e1.mts
```

`WEBX68K_DIR`(既定 `../WebX68k`)、`FRAMES`(既定3000)で上書き可能。
`POSITIVE_CONTROL_IMG` は不要(Stage E-1 は起動可否ではなく GVRAM→座標対応が
主題のため)。
