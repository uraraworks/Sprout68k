## 矩形追跡の方式

裏バッファはメインメモリ上の静的配列(`lib/src/x68_l1.c`の
`x68_backbuffer[512*512]`、512KB)に置く。以下の2つのリストを持つ。

- `curRects`: **今フレームの描画プリミティブ**(pset/box_fill/box/line/circle)
  が追加した矩形。
- `prevRects`: 直前の`x68_screen_flip()`の時点での`curRects`(=前フレームに
  描画された矩形)。**次の`x68_cls`が「塗り戻す範囲」として参照する。**

`x68_screen_flip()`は垂直同期を待ってから、`force_full`フラグが立っていれば
裏バッファ全体を、そうでなければ`prevRects ∪ curRects`の矩形だけをGVRAMへ
転送する。転送後 `prevRects := curRects`、`curRects`は空にする。

`x68_cls(color)`は**全画面を塗らない**。前回と同じ色なら`prevRects`の範囲だけを
`color`で塗り戻す。**呼び出しごとに`curRects`へは追加しない**(理由は下記
「矩形リストがポイズニングする罠」を参照)。前回と異なる色、または
`x68_screen_open()`後に一度も`x68_cls`を呼んでいない場合だけ、裏バッファ全体を
塗り、`force_full=1`をセットして次の`flip()`で全画面転送させる
(この場合だけ稀に全画面転送になる。設計通り)。

### 矩形リストがポイズニングする罠(実装中に見つけて直した設計変更)

最初の実装は、`x68_cls`が塗り戻した領域をそのまま`curRects`へも追加していた
(「今フレームで裏バッファが変わった範囲」として素直に扱っていた)。これは
一見自然だが、**背景色が変わって全画面塗り直しが起きた直後、次のフレーム以降
`x68_cls`を毎回呼ぶだけで全画面相当の矩形がフレームを跨いで肥大化し続ける**
というポイズニングが起きることを、実装中の机上トレースで発見した。

具体的には: 全画面塗り直しで`curRects`を「画面全体」の矩形に設定すると、
`flip()`後にそれが`prevRects`になり、**次のフレームの`x68_cls`(背景色は変わって
いない)が「前フレームの矩形リスト」として画面全体を読み、また画面全体を
塗り戻し・`curRects`へ足す**……という無限ループに陥り、「矩形追跡による部分
転送」という設計目的そのものを永久に壊してしまう。

**対策**: `x68_cls`は`prevRects`を読んで裏バッファを塗り戻すだけにし、
`curRects`へは触れない。`flip()`側が`prevRects ∪ curRects`を転送するので、
`prevRects`(=前フレームの描画矩形、`cls`が塗り戻した範囲そのもの)は
`cls`が何もしなくても自動的に転送対象に含まれる。これにより:

- 通常フレーム(背景色不変・`cls`→描画→`flip`): `prevRects`は「前フレームに
  実際に描かれた小さい矩形」のままで肥大化しない。
- 全画面塗り直しが起きたフレームでは、`force_full`により`flip()`が独立に
  全画面転送を行い、かつ`curRects`/`prevRects`を空にリセットするので、
  次フレーム以降は通常の小さい矩形に戻る。

## 溢れた場合の扱い(固定長配列、64矩形/リスト)

矩形リストは`X68RectList`(固定長配列、`X68_L1_MAX_RECTS=64`)。矩形を追加する
たび、リストの外接矩形(bbox)を無条件に更新し続ける。個別リストが64件に
達した状態でさらに追加が来ると、そのリストを`overflowed`状態にし、以後は
**bboxだけを唯一の矩形として扱う**(安全側に倒す。動的確保はしない)。
bboxは追加のたびに毎回更新しているため、overflow直前までの矩形もすべて
含んだ状態で切り替わる(取りこぼしは無い)。転送/塗り戻し処理は
「`overflowed`ならbbox1つだけ処理、そうでなければ配列を全部処理」という
共通コードで扱う。

## 転送の実装(端数対応)

矩形の幅が512(画面幅いっぱい)の場合は、裏バッファ・GVRAMどちらも複数行が
連続領域になるため、1回のMOVEMコピー(+端数の個別コピー)にまとめる
(全画面転送はこの経路)。それ以外の矩形は行ごとに、`x68_gvram_copy_movem`
(16ワード=32バイト単位)で入る分だけバッチ転送し、**16ワードに満たない
端数は個別のワードコピーで転送する**(矩形の幅は32バイトの倍数とは限らない
という要件を満たす)。

## 裏バッファの配置とビルド時検査

`x68_backbuffer`(512x512x2=512KB)は`.bss`に置かれる。`.bss`はNOLOAD
セクションのため、既存の本体末尾(`.bin`のサイズ)とスタックの衝突チェック
(`tools/build_stage_c.sh`等の前例)には現れない。**このチェックだけでは
裏バッファがスタックへ食い込んでいても検出できない**(「借りた定数には
見えない前提が付く」の教訓通り、チェックの適用範囲そのものが前提を
持っていた)。

`tools/build_l1_test.sh`に新たに追加した検査: リンク後のELFから
`m68k-elf-nm`で`__bss_end`シンボルの実アドレスを読み、
`__bss_end + STACK_MARGIN(4096バイト) <= STACK_ADDR(既定$F0000)`
であることを確認する。満たさなければビルドを失敗させる。実測値:
`__bss_end = 0x00084b9c`(本体+裏バッファ512KB込み)で、`STACK_ADDR=$F0000`
まで十分な余裕がある。

## 検証(`verify/verify_l1.mts`)

### GVRAMをpeekWordで直接読む方式は機能しなかった(実装中に踏んだ罠)

最初の実装は、`lib_test/src/main_l1.c`が書いたGVRAM($00C00000〜)を
`host.peekWord()`で直接読んで期待グリッドと比較する設計だった。実行すると
**全フレームで`observed=0`が一様に返る**という結果になった。「不自然に
揃った数字は観測系の故障を疑う」の教訓通り、これを実測結果として受け取らず
実装を確認したところ、`WebX68k/src/core-shim.c`の`webx68k_peek16`は

```c
extern unsigned char *MEM;
int webx68k_peek16(unsigned int addr) {
  if (!MEM) return -1;
  return (MEM[addr ^ 1] << 8) | MEM[(addr + 1) ^ 1];
}
```

というコードで、コメントにも明記されている通り**「ゲストのメインメモリ」
(px68k-libretro内部のフラット配列`MEM[]`)しか読めない**ことが分かった。
GVRAM($00C00000〜)はメインメモリのフラット配列の外(メモリマップドI/O側)に
あり、`MEM[0x00C00000]`は配列範囲外の無関係な位置(常に0)を指していた。

**対策**: `verify_lib.mts`(既存)と同じ方式に切り替えた。実際にレンダリング
された`canvas`(`lastImage()`)を読み、GVRAM16bit色値→実RGB8の変換式
(`decode16to24`、`docs/lib実装_20260819.md`で確定したものと同じ式)で変換した
期待色と、観測されたRGB8との距離が閾値(90)以内かで判定する。

### 全画素比較の方式

- host側に「期待される画面」のモデル(`verify/verify_l1.mts`の`Model`クラス)を
  持つ。`cls`/`pset`/`boxFill`/`box`/`line`/`circle`をゲスト側の実装と
  1画素単位で一致するように独立実装した(特に`line`/`circle`は同じ
  Bresenham系の整数演算式を使うことで、host側モデルが「裏バッファ全体を
  毎フレーム塗り直す」単純な実装のまま、ゲスト側の矩形追跡による部分転送の
  「結果」と全画素一致することを確認できる。**host側は矩形追跡そのものは
  再実装しない**。それは実装詳細でありAPIの観測可能な結果ではないため)。
- 台本は8フレーム固定(下記)。各`x68_screen_flip()`直後にゲストが
  `HV2_PROGRESS`を書き、hostは`peekU32`でこれをポーリングして「flip完了」を
  検出し、その時点のcanvas全体(512x512、サンプリングではなく**全画素**)を
  期待グリッドと突き合わせる。
- host→guestへメモリを書き込む手段(poke)が無い(`LibretroHost`は
  `peekByte`/`peekWord`しか提供していない)ため、台本は
  `lib_test/src/main_l1.c`に固定で書き下ろしてあり、hostはこれをTSで
  独立に再実装している(2箇所を1桁単位で一致させる前提。既存の
  `verify_lib.mts`のgen_color()と同じやり方)。
- 各`flip()`の直後、ゲストは何も描かずに3回だけ`x68_vsync_wait()`する
  「静止区間」を置く。host側はflip完了検出後にさらに2回`runFrame()`を
  呼んでからcanvasを読むことで、px68kのビデオリフレッシュがGVRAM書き込みに
  追いつくまでの配送遅延を、安全マージン1回を残して吸収している。

- **主台本(8フレーム): 全フレームで全画素一致(PASS)**
  (`MAIN_SCRIPT_ALL_FRAMES_MATCH=true`)
- **陰性対照: 背景のみと一致(PASS)** (`NEGATIVE_CONTROL_OK=true`)
- **`x68_rgb()`のhost独立照合(3点): 一致(PASS)** (`RGB_CHECK ok=true`)

| # | 故障注入 | 検出結果 |

| 4 | `cls_no_full_repaint`: 背景色変更時に全画面を塗り直さない | frame6(背景色変更の回)でMISMATCH(count=249,903、画面のほぼ全体)。背景が旧色(黒)のまま残った |

(壊してもPASSしてしまう)は無かった。

**注意(色選定の罠)**: 最初は背景色をBG1=rgb(0,0,32)・BG2=rgb(64,0,0)と
していたが、`decode16to24`変換後のRGB距離が約73.8しかなく、

変更(距離400超)して解決した。この経緯自体が「検査が空振りしていないか」を
実際に確認する作業の実例になっている。

## 転送量の実測(API設計_20260819.md「API実装時の宿題」1)

上記8フレーム台本での`x68_screen_flip()`ごとの実転送バイト数(`x68_l1_last_flip_bytes`):

| frame | バイト数 | 内容 |
|---|---|---|
| 0 | 524,288 | 初回全画面転送(`x68_screen_open()`直後、GVRAM内容が不定なため) |
| 1 | 1,024 | 動く矩形のみ(16x16x2バイト x 2(前フレーム分+今フレーム分)) |
| 2 | 1,704 | 動く矩形 + 画面端矩形出現(クリップ後17x20相当) |
| 3 | 2,384 | 動く矩形 + 画面端矩形(継続) |
| 4 | 2,384 | 同上 |
| 5 | 25,170 | 動く矩形 + 画面端矩形消滅 + 点/線/円/枠が加わり矩形数が増加 |
| 6 | 524,288 | 背景色変更による全画面転送 |
| 7 | 1,024 | 動く矩形のみ(背景色変更後は`prevRects`/`curRects`ともリセット済み) |

最大値は524,288バイト(全画面転送、frame0とframe6のみ)、平均は
135,283.3バイト/フレーム。Stage E-3実測(16MHz、MOVEM.L、53,227バイト/フレーム)
に対する比率は、**最大値で985.00%(全画面転送は1フレームに収まらない。
Stage E-3の実測通り約10フレームぶんかかる計算になる。設計書が「稀な事象
なので許容する」としている通りの挙動)**、平均で254.16%となった。

**平均が予算比254%と高いのは、この台本が「全画面転送が2回含まれる8フレーム」
という意図的に厳しい構成だからである**(背景色変更・初回起動という「稀な
事象」を検証のために毎回発生させている)。全画面転送を除いた6フレーム
(frame1〜5,7)だけの平均は`(1024+1704+2384+2384+25170+1024)/6 ≈ 5,615バイト`
で、予算比約10.55%となり、`docs/API設計_20260819.md`の見積もり
(3〜4KB/フレーム、予算比約1割強)とおおむね近い水準だった。

**この台本はブロック崩し本体ではなく、矩形追跡の正しさ・転送機構の実測を
目的とした人工的な描画パターンである。実際のブロック崩し(パドル・ボール・
複数ブロック)の負荷とは異なるため、この数値は実負荷の値ではない。**
ブロック崩し本体実装時に、実際の描画呼び出しパターンで改めて実測すること。

  ある。今回の台本では顕在化していないため、ブロック崩し本体(多数の
  ブロックが同時に壊れる等)で実測が必要。
