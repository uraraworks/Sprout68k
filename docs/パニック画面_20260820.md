# パニック画面の実装と68030 VBR対応(2026-08-20)

## 位置づけ

`docs/API設計_20260819.md` 設計原則3「暴走は静かに固まるのではなく、見える形で
止まる」の実装。要件(a)(b)(`docs/構想_20260819.md`)の入口にあたる。
併せて「API実装時の宿題」2(68030機でのVBR対応)にも対応する。

## 重要な追記(2026-08-20、並行実測を受けた修正)

並行して進んでいた宿題3(テキスト面とグラフィック面の重なり方、
`docs/重なり実測_20260820.md`)の実測により、**65536色グラフィックモードが
有効な間、その512ドット幅の範囲(x=0〜511、テキストの桁0〜63)では
テキストがフレームバッファに一切現れない**(Text VRAMには正しく書き込まれる
がモードレベルで排他される)ことが判明した。パニックハンドラはIOCS $21で
テキストを表示する設計のため、**このままでは例外発生時にグラフィックモードが
有効なままだと画面には何も出ないまま停止し、設計原則3を満たせない**という
指摘を受け、実装・検証の両方を修正した。詳細は下記「グラフィック面が
テキストを隠す罠」節、および「検証」節の「手順1」「故障注入4」を参照。

## 実装

### ファイル構成

- `lib/asm/x68_panic.S`: 例外ベクタの差し替え(`x68_panic_install`)、
  4種の例外エントリスタブ(バスエラー・アドレスエラー・不正命令・ゼロ除算)、
  日本語メッセージのCP932バイト列。
- `lib/src/x68_panic.c`: `x68_panic_show(int type, unsigned long pc)`。
  メッセージ選択・IOCS $21経由の表示・無限ループでの停止。
- `lib/src/x68_l1.c`: `x68_screen_open()` の中で `x68_panic_install()` を
  呼ぶよう変更(設計通り、この関数の中で差し替える)。
- `lib_test/src/main_panic.c` / `tools/build_panic_test.sh`: 検証用。
- `verify/verify_panic.mts`: 検証本体。

### 対象例外と実装方式

Stage E-5(`docs/StageE-5_実測_20260819.md`)で実測確定した手段(ベクタ番地
0への直接書き込み。68000はベクタテーブルが番地0固定)をそのまま使う。

| 例外 | ベクタ番号 | 番地 | 対応 |
|---|---|---|---|
| バスエラー | 2 | $08 | ハンドラは実装。**px68k上では発火させられない(後述)** |
| アドレスエラー | 3 | $0C | 実装・実測OK |
| 不正命令 | 4 | $10 | 実装・実測OK |
| ゼロ除算 | 5 | $14 | 実装・実測OK |

ハンドラはStage E-5(`e5_handlers.S`)と同じ設計で、RTEで元の実行へは戻さず
無限ループで停止する。68000の例外スタックフレーム形式の違い(アドレスエラー/
バスエラーは7ワードの可変長寄りフレーム、不正命令/ゼロ除算は3ワードの
固定フレーム)を解析せずに済むための設計をそのまま踏襲した。

PCの取得は、アドレスエラー/バスエラーはスタックフレームのSP+10、
不正命令/ゼロ除算はSP+2から読む(Motorola一般文書化仕様に基づく解読。
StageE-5と同じ出所)。**この値そのものが実機で正しい番地であることを
Motorola資料以上の手段で裏取りしてはいない**(実機が無い)。本検証で
実測したのは「表示されるPCの値が例外発生位置に応じて変化すること」
「常に0のような固定値でないこと」であり、これは設計書が明示的に許容する
代替検証(「値そのものの正しさまで見るのが難しければ、毎回同じ値では
ないこと・例外を起こした箇所を変えると値が変わることを見る」)にあたる。

### バスエラーがpx68k上で発火しない(実測・ソース確認による事実)

`px68k-libretro/m68000/musashi/m68kcpu.h` に

```c
#define EXCEPTION_BUS_ERROR 2 /* This one is not emulated! */
```

とあり、かつ `m68k_pulse_bus_error()`(バスエラーを実際に起こすための
Musashi側API、`px68k-libretro/m68000/musashi/m68kcpu.c` で定義)の
呼び出し箇所を `grep -rn "m68k_pulse_bus_error"` でリポジトリ全体を検索した
ところ、定義自体(`m68kcpu.c`)と宣言(`m68k.h`)以外に**呼び出し箇所が
一つも無い**ことを確認した。つまりpx68kはメモリマップドI/O以外の未使用
領域への書き込み等でバスエラーを起こす仕組みを持たず、**このプロジェクトの
検証環境ではバスエラーの発火自体が原理的に不可能**。

このため:
- バスエラーのハンドラ・ベクタ差し替えは実装した(実機・他のCPUコア向け)。
- **発火テストはverify_panic.mtsで行っていない**(行っても無反応のまま
  タイムアウトするだけで検査として意味を持たないため)。
- 3種の弁別・PC表示の実測対象は**アドレスエラー・不正命令・ゼロ除算の3種**。

### 日本語表示: 実測でできることを確認した

**表示できた。** IOCS $21(`x68_iocs_print`、内部的に`puts`/`printf`経由)は
日本語(CP932バイト列)をそのまま表示できることを実測で確認した。

verify_panic.mtsの実測ログ(不正命令、通常ビルド、PAD=0):

```
lines: ["不正な命令を実行しました","PC = $304c","プログラムを停止します"]
```

`host.readTextScreen()`(既存の`WebX68k/src/text-screen.ts`)がCGROMの
16x16漢字ブロックから逆引き表を作り、テキストVRAMの実ビットマップと
1画素単位で突き合わせて文字を復元する実装であることを事前に確認した上で
使っている。つまりこの一致は「期待した文字コードを送った」ことの自己申告
ではなく、**画面に実際に描画されたグリフがCGROM上の対応する漢字と
一致した**という実測結果である。

**ただし、これだけでは「入門者が実際に画面で見えるか」の証明にならない**
(下記「グラフィック面がテキストを隠す罠と対策」参照)。`readTextScreen()`は
Text VRAMを直接読む経路であり、実際にレンダリングされるフレームバッファとは
独立している。

### グラフィック面がテキストを隠す罠と対策(2026-08-20追記)

並行して進んでいた宿題3の実測(`docs/重なり実測_20260820.md`)により、
**65536色グラフィックモードが有効な間、その512ドット幅の範囲
(x=0〜511、テキストの桁0〜63)ではテキストがフレームバッファに一切現れない**
(Text VRAMには正しく書き込まれるが、モードレベルで排他される。ピクセル単位の
合成ではない)ことが判明した。パニックハンドラのメッセージは`x68_locate(0,0)`
から出すため、まさにこの隠される範囲に収まってしまい、**グラフィックモードを
解除しないまま表示すると、Text VRAMには正しく書かれるのに画面には何も
出ないまま停止する**(設計原則3が満たせない)。

**原因(px68k-libretroのソース読解による特定、推測ではない)**:
`px68k-libretro/libretro/windraw.c`のcompositeロジックを読んだところ、
VCレジスタ2(`$E82601`、`VCReg2[1]`)のbit5(`0x20`)が`Text_DrawLine()`
呼び出しの唯一のゲートであり、グラフィックページ表示有効ビット(bit0-3)とは
独立していることが分かった。`x68_gvram_mode_65536_1page()`は
`VC_R2 = 0x01`(グラフィックページ0のみ有効化)を書き込むため、bit5(テキスト
表示)は立っておらず、テキストが描画パイプラインから除外されていた。
CRTC R20($E80028)はGVRAMのバイトアクセス時の色深度解釈にのみ関わり
(`px68k-libretro/x68k/gvram.c`)、VC R0($E82401)はグラフィックの色数モード
選択にのみ関わる(`windraw.c`の`switch(VCReg0[1]&3)`)ため、いずれもテキスト
表示のゲートには関与しない。

**対策**: `x68_panic_show()`(`lib/src/x68_panic.c`)の先頭で
`VC_R2($E82601) = 0x20`を書き込む。これによりグラフィックページ表示ビット
(bit0-3)が同時にクリアされる(グラフィック面自体も止まる)が、パニック画面を
出す以上ゲームは既に停止しているため問題ない。

**実測(修正前後の比較、フレームバッファのx:0-260,y:0-48領域と、遠く離れた
基準画素(450,350、どのメッセージも到達しない領域)とのRGB距離>40の画素数
で比較)**:

| 版 | フレームバッファの差分画素数 |
|---|---|
| 修正前(`VC_R2 = 0x20`を書かない) | **0**(文字が一切見えない) |
| 修正後(`VC_R2 = 0x20`を書く) | **1151**(文字が実際に描画されている) |

`readTextScreen()`(Text VRAM経由)はどちらの版でも同一のメッセージ文字列を
返す(=Text VRAM自体への書き込みは修正の前後で変わらない)ため、
**`readTextScreen()`だけの検査ではこの罠を検出できない**ことを実測で確認した
(下記「検証」節の故障注入4を参照)。

### 日本語メッセージのエンコード方式(既知の罠を避ける設計)

`lib/asm/x68_panic.S` のメッセージは、C/アセンブラの文字列リテラル
(`.ascii`。バックスラッシュエスケープを解釈する)を一切使わず、事前に
Python3で計算したCP932バイト列を`.byte`で直接列挙している。

```
python3 -c "
msgs = {
    'ILLEGAL': '不正な命令を実行しました',
    ...
}
for k, v in msgs.items():
    print(k, v.encode('cp932'))
"
```

**既知の罠(必ず踏まないこと。プロジェクトの過去の失敗)**: UTF-8から
Shift_JIS系へ変換するとき `SHIFT_JIS` コーデックではなく `CP932` を使う
こと。`SHIFT_JIS`だと0x5Cが¥記号になりCのエスケープが壊れる。

本実装はさらに一歩踏み込み、CP932の2バイト目がたまたま0x5C
(バックスラッシュ)と一致するグリフが混じっていても、`.byte`はエスケープ
解釈を一切行わないため、C/アセンブラの文字列エスケープの罠を構造的に
踏みようがない設計にした(今回使ったメッセージには実際には0x5Cを含む
バイトは無かったが、今後メッセージを追加・変更する際にも安全なやり方を
選んだ)。

## 68030のVBR対応(宿題2)

### 採った方式

`stage_c/boot/cache_flush.S` の「MOVECを試し、不正命令(vector4)が起きたら
68000相当とみなして安全にスキップする」手法をそのまま流用した
(`lib/asm/x68_panic.S`の`x68_panic_install`冒頭)。

1. 不正命令ベクタ(番地$10)を一時的な自前ハンドラへ差し替える
   (退避は`cache_flush.S`が実測で発見した罠「絶対アドレスへの書き込みは
   ロードアドレス前提が崩れると壊れる」を避けるため、メモリではなく
   レジスタ(%a2/%a3)だけを使う)。
2. `moveq #0,%d0` の後 `movec %d0,%vbr` を実行する。
   - 68000ならMOVEC自体が不正命令になり、一時ハンドラへ飛ぶ。ハンドラは
     退避しておいたSPを復元して安全に続行する(VBR設定はスキップされる)。
   - 68010以降ならMOVECが成功し、VBRが明示的に0になる。
3. 不正命令ベクタを元に戻し、直後に4種のパニックハンドラで本当に上書きする。

### なぜ「68020でだけ」ではなく「試して失敗したら諦める」方式にしたか

CPU種別を明示的に判定してから分岐する手段が無い(CPUID命令が無く、判定
すること自体がCPU依存の命令を要る「鶏と卵」の問題になる)ため、
`cache_flush.S`が命令キャッシュ制御で採った「試して、不正命令が起きたら
そのCPUには無い機能とみなす」という保守的な手法をVBR設定にもそのまま
適用した。結果として、68010以降であれば無条件にVBR=0への設定を試みる
実装になっている(「68020以降でだけ」という指示は`cache_flush.S`と
同じ*手法*を指すものと解釈した)。

### 実機/実測状況(正直に記録する)

**px68kは実測できない。** `px68k-libretro`が使うMusashiコアは
`m68k_set_cpu_type()`を一度も呼ばず常に68000として初期化される
(`docs/StageE-5_実測_20260819.md`・`stage_c/boot/cache_flush.S`のコメントで
既に確認済みの事実の再利用。今回新たに実測してはいない)。つまり
`movec %d0,%vbr` は本プロジェクトの検証環境では**常に不正命令として扱われ、
一時ハンドラへ飛んでスキップする経路しか通らない**。

**68000で「安全に素通りする」ことは実測した**: 本検証(`verify_panic.mts`)の
陽性テスト3件(アドレスエラー・不正命令・ゼロ除算)はすべて
`x68_panic_install()`(VBR設定の試行を含む)を経由してから例外を捕捉して
おり、3件ともPASSしている。これは「VBR設定コードを含む版が68000上で
正常に起動し、既存の動作(ハンドラ差し替え)が壊れていないこと」の実測に
あたる。

**68030側(MOVECが成功してVBRへ実際に書き込む経路)は一度も実行されておらず、
未検証のまま。** 実機での確認、またはCPU種別を切り替えられる別の
エミュレータコアの導入が必要(`docs/StageE-5_実測_20260819.md`と同じ結論)。
「対応済み」ではなく「68000での安全な素通りのみ実測、68030側は未検証」と
明記する。

## 検証(`verify/verify_panic.mts`)

`tools/build_panic_test.sh`でビルドした検体を`px68k`上で直接駆動する
(既存verify_*.mtsと同じ骨格)。すべて同期実行、自前タイムアウト
(`makeDeadline`、`MAX_FRAMES`既定1500)。

### 結果(2026-08-20実施、`npx tsx verify/verify_panic.mts` 同期実行、EXIT=0)

- **3種の陽性テスト**: アドレスエラー・不正命令・ゼロ除算の3種とも
  PASS(`aliveSeen=true`・`timedOut=false`・期待メッセージ検出・
  「プログラムを停止します」検出・**`fbVisible=true`=フレームバッファ上で
  実際に見えることを実測確認**)。
  - アドレスエラー: `PC = $3052`, `fbVisible=true(diffCount=1119)`
  - 不正命令: `PC = $304c`, `fbVisible=true(diffCount=1151)`
  - ゼロ除算: `PC = $410a`, `fbVisible=true(diffCount=1105)`
  (PCの具体値はビルドにより変動する。ここでの合否条件は「表示され、非ゼロで、
  位置を変えると変わること」であって固定値との一致ではない)
- **3種の弁別**: `PANIC_TYPES_DISTINCT=true`(3種のメッセージがそれぞれ
  独立して検出され、互いに他の2種のメッセージを含まない)
- **PCが例外発生位置に応じて変わるか**: PAD=0とPAD=8(不正命令トリガの
  直前にNOPを8個挿入し、コード上のアドレスを16バイトずらす)を比較。
  `pad0=0x304c pad8=0x305c`、`changes=true nonZero=true`。
- **陰性対照**: 例外を起こさない通常実行(MODE=1)は3種とも
  パニック画面のメッセージが一切出ず、正常終了(`HV4_DONE`到達)を確認。
  `PANIC_NEGATIVE_CONTROL_ALL_OK=true`。

### 故障注入(4件、すべて実際にFAILすることを確認)

| # | 故障注入 | 検出結果 |
|---|---|---|
| 1 | `no_install`(ハンドラを差し替えない) | パニック画面のメッセージが一切出ず、検査(陽性判定式)が期待通りFAILする状況を確認 |
| 2 | `same_message`(3種すべて同じメッセージ) | 3種とも「不正命令」のメッセージが出て、弁別検査(3種が別々のメッセージか)が期待通りFAILする状況を確認 |
| 3 | `pc_zero`(PCを常に0で表示) | 表示されたPCが`0x0`になり、「PCが非ゼロであること」の検査が期待通りFAILする状況を確認 |
| 4 | `no_mode_restore`(65536色グラフィックモードを解除しない) | `readTextScreen()`(Text VRAM経由)にはメッセージが出続ける(`textVramStillHasMessage=true`)のに、**フレームバッファ上では一切見えない**(`fbVisible=false, diffCount=0`)。「フレームバッファ上で見えること」検査が期待通りFAILする状況を確認した。これは`readTextScreen()`だけの検査では検出できない罠であることの実地証明でもある |

4件とも「壊した版で検査が実際にFAILする」ことを確認した(空振り無し)。

## 実装中に見つけた罠(教訓)

**Cの `*(volatile unsigned short *)1 = 0;` はアドレスエラーを起こさない
ことがある。** アドレスエラーのトリガを最初はC(ポインタ経由の書き込み)で
書いたところ、`objdump`で確認するとgccが`-Os`で「番地1への16bit書き込み」を
`moveb`(byteアクセス)2命令に分解しており、word/longアクセスでないため
アドレスエラーが一度も発生しなかった(陽性テストが`returnedSeen=true`・
`doneSeen=true`になり検出)。Stage E-5の`e5_handlers.S`と同じインライン
アセンブラ(`move.w #0,1`)に切り替えて解決した。**コンパイラが「不正な
番地へのアクセスを安全なアクセスへ最適化してしまう」ケースがあるため、
例外を意図的に起こすコードはインラインアセンブラで書くべき**という
知見が得られた。
