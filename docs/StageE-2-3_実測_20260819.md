# Stage E-2 / E-3 実測 20260819

`docs/API設計_20260819.md` の Stage E-2(垂直同期の検出方法)と Stage E-3(裏バッファ→
GVRAM 転送の速度)を実測した。手読みの候補と実測で確認した事実は出所を分けて記録する。

## 結論

### E-2: 垂直同期の検出方法

- **確定した検出手段**: MFP(MC68901相当) の GPIP レジスタ($00E88001) の **bit4(0x10)
  の立下りエッジ**(表示期間中は1、垂直帰線期間に入ると0になる)。
  「表示期間に入るまで待つ→帰線期間に入るまで待つ」の2段ポーリングで、1回の
  垂直同期待ちを検出できる。
- 実測(同期待ちあり版): host 側の `runFrame()` 呼び出し300回に対し、ゲスト内の
  同期待ちカウンタは **ちょうど300増加**(比=1.0000)。1回の同期待ち ≈ host側1フレーム
  という関係が成立することを確認した。
- **陰性対照**(同期待ちを外した版): 同じ300 `runFrame()` 呼び出しでカウンタは
  **2,355,722増加**(比=7852)。同期待ちを外すとこの関係が明確に崩れることを確認した
  (検出手段が「たまたま数字が合っただけ」ではないことの裏付け)。

### E-3: 裏バッファ→GVRAM 転送の速度

- K=64KB/128KB/256KB/512KB それぞれの転送で、E-2 で確定した検出手段を使い転送中に
  経過した垂直同期回数(ゲスト側で計測)を実測した。

  | K(転送バイト数) | 経過した垂直同期回数(実測) | K/回数(バイト/フレーム) |
  |---|---|---|
  | 65,536 (64KB) | 13 | 5041.23 |
  | 131,072 (128KB) | 26 | 5041.23 |
  | 262,144 (256KB) | 52 | 5041.23 |
  | 524,288 (512KB) | 104 | 5041.23 |

  4点とも K/回数 が**完全に一致**(5041.230769...バイト/フレーム。65536/13 と
  524288/104 は数式的に同一)。K が2倍になれば回数も正確に2倍になっており、
  この転送方式(後述)ではスループットが K に依存せず一定であることを確認した。

- **512KB(全画面)は1フレームに収まらない**(104回の垂直同期=約104フレームぶん
  かかった。1フレームに収まるなら回数は0〜1のはず)。
- **1フレームに収まる最大のバイト数(実測値から)**: 約 **5041 バイト**(5041.23、
  端数切り捨てで5041バイト)。
- これは 512×512 の全画面(512KB=524,288バイト)の **約0.96%** にあたる。

## 測定方法

### 共通: ハーネスのコアオプション(実際の値を調査・記録)

検証ハーネス(`verify/verify_e2.mts` / `verify/verify_e3.mts`)が px68k に明示的に
設定しているコアオプションは以下の3つ(`host.setCoreOption()` の呼び出し引数から
実際に確認):

| オプション | 設定値 |
|---|---|
| `px68k_cpuspeed` | `16Mhz`(Stage E-1 と同じ値。px68k-libretro/libretro.c で `Config.clockmhz = 16` に対応することをソースで確認) |
| `px68k_ramsize` | `1MB` |
| `px68k_no_wait_mode` | `enabled`(理由は下記「自己同期の罠」参照) |

明示的に設定していないオプションは `px68k-libretro/libretro_core_options.h` の
定義済み既定値のまま動く(これもソースで確認。推測ではない):

| オプション | 既定値 |
|---|---|
| `px68k_frameskip` | `Full Frame`(フレームスキップ無し) |
| `px68k_adjust_frame_rates` | `enabled` |
| `px68k_audio_desync_hack` | `disabled` |

なお px68k のベース機種は X68000(無印相当)固定で、`px68k_model` のような
機種切り替えオプションは存在しない(px68k-libretro/libretro.c を全数走査して確認)。
実機の X68000 無印は CPU クロック **10MHz** が標準であり、ハーネスが使った
`16Mhz` は実機の標準クロックより高い。

### 「コアが実時間に自己同期する」罠を踏んだ経緯(記録として残す)

`px68k_no_wait_mode` を未設定(既定 `disabled`)のまま E-2 の最初の測定を行ったところ、
同期待ちあり版で `runFrame()` 300回に対しゲスト内カウンタはわずか31しか増えなかった
(比=0.10)。これは検出手段(MFP GPIP)が誤っていたのではなく、px68k-libretro の
`retro_run()` が `Config.NoWaitMode` 無効時に `Timer_GetCount()`(実時間の経過)で
ゲートされ、**host側が `runFrame()` を何回呼んでも実時間が経過するまでゲストが
進まない**ためだった(既存メモリ `feedback_core_self_paces_to_wall_clock.md`、
2026-08-12 に別件で同じ罠を踏んだ記録がある)。`px68k_no_wait_mode=enabled` を
明示設定して撮り直したところ、比はちょうど1.0000になった(上記結論の値)。
E-3 は最初からこの設定で測定した。

この経緯自体が「候補を実測で確かめる」プロセスの一部であり、E-2 の結論は
この設定変更後の値を採用している。

### E-2 の測定手順

`stage_e/src/main_e2.c`(`tools/build_stage_e2.sh` でビルド。`USE_VSYNC_WAIT=1`/`0`
で2版)が、無限ループで「同期待ち→32bitカウンタをインクリメントして固定RAM
アドレス($000E0000)へ書く」を繰り返す。`USE_VSYNC_WAIT=0` 版は同期待ちを
空関数にした陰性対照。

`verify/verify_e2.mts` が Node から px68k を直接駆動し(`verify/verify_e1.mts` の
コア駆動部分を踏襲。`__BUILD_ID__`/`locateFile` の罠、自前タイムアウトも同じ)、
WARMUP=1500フレーム実行後にカウンタを読み(`host.peekWord()` を2回、上位/下位
ワードとして合成)、さらに MEASURE=300フレーム実行後に再度読んでその差分を
比較した。

判定基準:
- 同期待ちあり版: `rate = deltaCounter / deltaFrames` が [0.5, 2.0] の範囲内
- 陰性対照: 陰性対照の `rate` が同期待ちあり版の `rate` の10倍以上

いずれも実測で満たした(`E2_PASS=true`)。

### E-3 の測定手順

`stage_e/src/main_e3.c`(`tools/build_stage_e3.sh <K_bytes> <out.xdf>` でビルド)が、
65536色1ページモードを設定した後、固定アドレス($00020000〜、最大512KBまで)から
GVRAM($00C00000〜)へ K/2 ワードを1語ずつコピーしながら、同じループの中で
MFP GPIP のエッジ検出を行い、転送中に経過した垂直同期回数を数える(転送と
ポーリングを同じCPUで同時に行うので、ポーリングのオーバーヘッド自体も測定対象に
含まれる)。完了すると `DONE_FLAG`($000E0010`)を1にし、回数を `VSYNC_COUNT`
($000E0014、32bit)に書く。

`verify/verify_e3.mts` が WARMUP=150フレーム実行後、`DONE_FLAG` を
`host.peekByte()` で1フレームごとに監視して1になるまで `runFrame()` を呼び続け
(上限 MAX_EXTRA_FRAMES=20000、超えたらタイムアウトで異常終了)、完了後に
`VSYNC_COUNT` を読む。K=64KB/128KB/256KB/512KB の4点を実測した。

ブート完了までの host側フレーム数(`hostFramesAfterWarmup`)も裏取りとして記録した
が、WARMUP=150 は転送(最大でも100フレーム強)より小さいとは限らず、K が小さい
3点(64/128/256KB)では WARMUP 中に転送まで終わってしまい `hostFramesAfterWarmup=0`
になった(＝この値では裏取りできなかった)。主指標はゲスト側で直接計測した
`VSYNC_COUNT` であり、WARMUP の値を変えても(1500試行時・150試行時のいずれでも)
同じ13/26/52/104回という結果が再現することを確認済み。

### 転送方式についての注記(スループットの解釈に必要)

この5041バイト/フレームという値は、**単語(16bit)単位で `move.w` するだけの
素朴な CPU コピーループ**(ループ内で毎回 MFP GPIP のポーリングも行う)を
m68k-elf-gcc -Os でコンパイルしたものを測った値である。DMAC(DMAコントローラ)は
使っていない。ループ展開やアセンブラでの手動最適化も行っていない。したがって
この数値は「この方式での実測値」であり、「px68kでのGVRAM転送の理論上限」
ではない。より速い転送方式(DMA・ループ展開・ポーリング頻度を下げる等)を
使えば数値は変わりうる。今回はこの点の最適化は行っていない(未実施)。

## 結果の読み方(限界)

**この測定は px68k の実装を測っている。** エミュレータで測った速度は、
エミュレータのタイミングモデルを測ったものであって実機の速度ではない。

- 検証ハーネスは `px68k_cpuspeed=16Mhz` を設定した(実機 X68000 無印の標準クロック
  10MHzより高い)。`px68k_ramsize=1MB`、`px68k_no_wait_mode=enabled` も設定した。
  それ以外(`px68k_frameskip`=Full Frame、`px68k_adjust_frame_rates`=enabled、
  `px68k_audio_desync_hack`=disabled)は px68k-libretro のコード上の既定値のまま。
- **この値は px68k 上の実測であり、実機(10MHzの68000機など)では異なる可能性が
  ある。実機での確認は未実施。**
- 定性的な結論(512KBは1フレームに収まらない、桁としてはおおよそ1%程度しか
  収まらない)は採用するが、5041.23という数値自体の精度(小数点以下・±数%の
  範囲)を過信しない。転送方式(素朴なCPUコピー、DMA未使用)にも強く依存する
  値であることは上記の通り。

## 後退案検討のための判断材料(決定はしない)

構想上の後退案は「差分転送」または「16色4ページ方式」の二択とされている。
今回の実測で分かった事実のみを列挙する(どちらを選ぶかの決定はここでは行わない)。

- 全画面(512KB)を素朴なCPUコピーで転送すると約104フレーム(px68k上、16MHz・
  no_wait_mode設定時)かかる。1フレームに収まる量は全画面の約1%。
- **差分転送**を検討する場合: ブロック崩し(基準作例)は矩形の消去・再描画が
  中心なので、1フレームあたりの実際の差分量が全画面の1%程度に収まるかが
  判断材料になる(パドル・ボール・ブロック数個分の矩形なら数百〜数千バイト
  程度で収まる可能性がある。ただし未検証)。
- **16色4ページ方式**を検討する場合: 1ピクセルあたりのビット数が65536色モードの
  1/4(4bit vs 16bit)になるため、単純計算では同じ転送方式でも約4倍の面積を
  1フレームで転送できる計算になる(全画面512KB相当のピクセル数を16色で表現
  すると128KBになるため。ただし今回はこの計算を実機/エミュ上で計測していない
  ので推測にとどまる。あくまで検討材料であり実測ではない)。
- 転送方式そのものの最適化(DMAC使用、アセンブラでのループ展開、ポーリング頻度を
  下げる)は今回試していない。素朴なCPUコピーでの実測値(5041バイト/フレーム)を
  最適化すれば改善する余地があるかどうかは未検証。

## 確定できなかった項目

- E-3 の `hostFramesAfterWarmup`(host側フレーム数による転送時間の裏取り)は、
  WARMUP=150 の設定では K=64KB/128KB/256KB の3点で「WARMUP中に転送が完了して
  しまう」ため機能しなかった(K=524288のみ hostFramesAfterWarmup=33 が得られたが、
  ブート完了タイミングのばらつきの影響を受けるため主指標としては使っていない)。
  主指標であるゲスト側の `VSYNC_COUNT` は WARMUP の値に依存せず再現したため、
  結論への影響はないと判断した。
- 転送方式を変えた場合(DMA・ループ展開等)のスループットは未測定。
- 実機(実クロックの68000)での確認は未実施。

## 実行方法

```sh
npx --no-install tsx verify/verify_e2.mts
npx --no-install tsx verify/verify_e3.mts
```

`WEBX68K_DIR`(既定 `../WebX68k`)で上書き可能。E-2 は `WARMUP`(既定1500)・
`MEASURE`(既定300)、E-3 は `WARMUP`(既定150)・`MAX_EXTRA_FRAMES`(既定20000)で
上書き可能。
