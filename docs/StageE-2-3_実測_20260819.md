# Stage E-2 / E-3 実測 20260819

`docs/API設計_20260819.md` の Stage E-2(垂直同期の検出方法)と Stage E-3(裏バッファ→
GVRAM 転送の速度)を実測した。手読みの候補と実測で確認した事実は出所を分けて記録する。

## 結論

### E-2: 垂直同期の検出方法

- **確定した検出手段**: MFP(MC68901相当) の GPIP レジスタ($00E88001) の **bit4(0x10)
  の立下りエッジ**(表示期間中は1、垂直帰線期間に入ると0になる)。
  「表示期間に入るまで待つ→帰線期間に入るまで待つ」の2段ポーリングで、1回の
  垂直同期待ちを検出できる。
- 実測(同期待ちあり版): host 側の `runFrame()` 呼び出し300回に対し、ゲスト内の
  同期待ちカウンタは **ちょうど300増加**(比=1.0000)。1回の同期待ち ≈ host側1フレーム
  という関係が成立することを確認した。
- **陰性対照**(同期待ちを外した版): 同じ300 `runFrame()` 呼び出しでカウンタは
  **2,355,722増加**(比=7852)。同期待ちを外すとこの関係が明確に崩れることを確認した
  (検出手段が「たまたま数字が合っただけ」ではないことの裏付け)。

### E-3: 裏バッファ→GVRAM 転送の速度(rev3・最終結論)

**この節は3回測定をやり直した末の最終結論。rev1(ワード単位コピーの内側ループで
毎回MFPをポーリング)・rev2(ポーリングを分離したがポーリング間隔が疎すぎて
垂直帰線期間のエッジを取り逃した)はどちらも測定方法自体に欠陥があり、数値は
使わない。訂正の経緯は「E-3 の測定方法(訂正履歴)」の節に記録として残す。**

rev3では**ゲスト側の転送ループから垂直同期ポーリングを完全に無くし、時間は
ホスト側が `runFrame()` の呼び出し回数を数えて測る**方式に変更した。
3方式(word=`MOVE.W`単位、long=`MOVE.L`単位、movem=`MOVEM.L`による8ロング=32バイト
一括転送)を K=64/128/256/512KB について実測した(`stage_e/src/e3_copy.S`)。

| 方式 | バイト/フレーム(K=512KBでの実測) | 512KBの転送に要するフレーム数 | 全画面512KBに対する割合 | 1ロングあたりの換算サイクル数 |
|---|---|---|---|---|
| word(`MOVE.W`) | 14,266.34 | 36.75 | 2.72% | 72.99 |
| long(`MOVE.L`) | 22,795.13 | 23.00 | 4.35% | 45.68 |
| movem(`MOVEM.L`×8) | 53,227.21 | 9.85 | 10.15% | 19.56 |

- **512KB(全画面)は word・long・movem の3方式いずれも1フレームに収まらない**
  (word: 約36.75フレーム、long: 約23.00フレーム、movem: 約9.85フレーム)。
- **1フレームに収まる最大のバイト数(実測値から、最速のmovem方式)**: 約
  **53,227バイト**(全画面の約10.15%)。
- 陰性対照(R=0、転送なし)は3方式とも所要フレーム0を確認。線形性(R→2Rで
  所要フレームが2倍になるか)は3方式とも比≈2.00(word 2.000、long 1.995、
  movem 1.997)で確認できた。
- **妥当性の相互確認もすべて通過した**(後述): 1ロングあたりの換算サイクル数は
  72.99 / 45.68 / 19.56 サイクルで、いずれも「物理的にあり得ない」下限
  (5サイクル未満)を大きく上回り、常識的な上限も超えていない。movem/long の
  速度比は2.335倍で、指示された妥当範囲(1.5〜2.5倍)に収まった。
  **rev1・rev2と異なり、rev3の数値は妥当性チェックをすべて通過した「確定」
  結果として採用する。**

## 測定方法

### 共通: ハーネスのコアオプション(実際の値を調査・記録)

検証ハーネス(`verify/verify_e2.mts` / `verify/verify_e3.mts`)が px68k に明示的に
設定しているコアオプションは以下の3つ(`host.setCoreOption()` の呼び出し引数から
実際に確認):

| オプション | 設定値 |
|---|---|
| `px68k_cpuspeed` | `16Mhz`(Stage E-1 と同じ値。px68k-libretro/libretro.c で `Config.clockmhz = 16` に対応することをソースで確認) |
| `px68k_ramsize` | `1MB` |
| `px68k_no_wait_mode` | `enabled`(理由は下記「自己同期の罠」参照) |

明示的に設定していないオプションは `px68k-libretro/libretro_core_options.h` の
定義済み既定値のまま動く(これもソースで確認。推測ではない):

| オプション | 既定値 |
|---|---|
| `px68k_frameskip` | `Full Frame`(フレームスキップ無し) |
| `px68k_adjust_frame_rates` | `enabled` |
| `px68k_audio_desync_hack` | `disabled` |

なお px68k のベース機種は X68000(無印相当)固定で、`px68k_model` のような
機種切り替えオプションは存在しない(px68k-libretro/libretro.c を全数走査して確認)。
実機の X68000 無印は CPU クロック **10MHz** が標準であり、ハーネスが使った
`16Mhz` は実機の標準クロックより高い。

### 「コアが実時間に自己同期する」罠を踏んだ経緯(記録として残す)

`px68k_no_wait_mode` を未設定(既定 `disabled`)のまま E-2 の最初の測定を行ったところ、
同期待ちあり版で `runFrame()` 300回に対しゲスト内カウンタはわずか31しか増えなかった
(比=0.10)。これは検出手段(MFP GPIP)が誤っていたのではなく、px68k-libretro の
`retro_run()` が `Config.NoWaitMode` 無効時に `Timer_GetCount()`(実時間の経過)で
ゲートされ、**host側が `runFrame()` を何回呼んでも実時間が経過するまでゲストが
進まない**ためだった(既存メモリ `feedback_core_self_paces_to_wall_clock.md`、
2026-08-12 に別件で同じ罠を踏んだ記録がある)。`px68k_no_wait_mode=enabled` を
明示設定して撮り直したところ、比はちょうど1.0000になった(上記結論の値)。
E-3 は最初からこの設定で測定した。

この経緯自体が「候補を実測で確かめる」プロセスの一部であり、E-2 の結論は
この設定変更後の値を採用している。

### E-2 の測定手順

`stage_e/src/main_e2.c`(`tools/build_stage_e2.sh` でビルド。`USE_VSYNC_WAIT=1`/`0`
で2版)が、無限ループで「同期待ち→32bitカウンタをインクリメントして固定RAM
アドレス($000E0000)へ書く」を繰り返す。`USE_VSYNC_WAIT=0` 版は同期待ちを
空関数にした陰性対照。

`verify/verify_e2.mts` が Node から px68k を直接駆動し(`verify/verify_e1.mts` の
コア駆動部分を踏襲。`__BUILD_ID__`/`locateFile` の罠、自前タイムアウトも同じ)、
WARMUP=1500フレーム実行後にカウンタを読み(`host.peekWord()` を2回、上位/下位
ワードとして合成)、さらに MEASURE=300フレーム実行後に再度読んでその差分を
比較した。

判定基準:
- 同期待ちあり版: `rate = deltaCounter / deltaFrames` が [0.5, 2.0] の範囲内
- 陰性対照: 陰性対照の `rate` が同期待ちあり版の `rate` の10倍以上

いずれも実測で満たした(`E2_PASS=true`)。

### E-3 の測定方法(訂正履歴)

E-3 は3回測定をやり直した。それぞれの版が何を測っていたかを訂正として残す。
**rev1・rev2に共通する原因は「ゲスト側の転送ループの中で時間(垂直同期)を
測ろうとしたこと」そのものだった**。rev1はポーリングが重すぎて遅く出て
「転送速度」ではなく「転送+ポーリング」の速度を測ってしまい、rev2はポーリングを
疎にした結果、垂直帰線期間(フレーム全体の数%程度しかない)をまたいで飛び越し
エッジを見落とし、速く出すぎた。rev3ではゲスト側から時間計測そのものを無くし、
ホスト側が `runFrame()` の回数を数える方式に変えることで、この共通原因を解消した。

#### 第1版=rev1(誤り): ワード単位コピーの内側ループで毎回MFPをポーリング

`stage_e/src/main_e3.c`(旧版。`tools/build_stage_e3.sh <K_bytes> <out.xdf>` でビルド)
が、65536色1ページモードを設定した後、固定アドレス($00020000〜、最大512KBまで)から
GVRAM($00C00000〜)へ K/2 ワードを**1ワードコピーするごとに毎回** MFP GPIP を
読みながら転送し、転送中に経過した垂直同期回数を数えていた。

`verify/verify_e3.mts`(旧版) が WARMUP=150フレーム実行後、`DONE_FLAG`
($000E0010`)を `host.peekByte()` で1フレームごとに監視して1になるまで
`runFrame()` を呼び続け、完了後に `VSYNC_COUNT`($000E0014、32bit)を読む形で
K=64/128/256/512KBの4点を実測し、**5041.23バイト/フレームで完全に比例する**
結果を得ていた。

**この結果は誤りだった。** レビュー時の指摘により発覚: MFP は低速な I/O バスに
あり、1ワードコピー(2バイト)ごとにこれを読む実装では、読み出しコスト
(実測換算で1ワードあたり約106サイクル。素の `MOVE.W` によるワードコピー自体は
約12サイクル程度)がコピーそのものより遥かに大きく、**測っていたのは「転送速度」
ではなく「転送+ワード毎ポーリング」の速度**だった。4点が完全に比例していたのも
「正しさの証拠」ではなく、**ポーリングという一定コストが支配的だったことの
裏返し**に過ぎない(比例は変換式が丸ごと間違っていても成立する。過去の教訓
「相対検査は絶対値の誤りを見逃す」と同種の落とし穴)。

#### 第2版=rev2(誤り): ポーリングを内側ループから分離したが、間隔が疎すぎて取り逃した

`stage_e/src/main_e3.c`(新版)+ `stage_e/src/e3_copy.S` が、word/long/movem の
3方式それぞれについて、**POLL_INTERVAL 個のコピー単位ごとに1回だけ** MFP GPIP
を読む実装に書き直した。加えて、同じ K バイトの転送を **N_REPEATS 回繰り返し**、
累積した垂直同期回数で割ることでスループットを求める(理由は次節「量子化誤差と
N_REPEATSによる対処」を参照)。`tools/build_stage_e3.sh <K_bytes> <method:0|1|2>
<poll_interval> <n_repeats> <out.xdf>` でビルドする。

**組み込み時に発見した2つ目のバグ(呼び出し規約違反)**: 最初にこの新実装を組んだ
とき、N_REPEATS を2以上にすると必ずハングした(N_REPEATS=1なら正常終了するが、
2以上ではhost側のフレーム上限(数千〜数万フレーム)を使い切っても `DONE_FLAG` が
立たなかった)。原因は m68k の GCC ABI で `d2-d7`/`a2-a6` が
**呼び出され側が保存する(callee-saved)** レジスタであるにもかかわらず、
`e3_copy.S` の3ルーチンがこれらを退避せずに作業用として使っていたこと。
`main_e3.c` 側の `for` ループ変数(繰り返し回数・累積カウンタ)がこれらの
レジスタに割り付けられていたため、1回目の呼び出しの中でレジスタごと破壊され、
2回目の呼び出し以降ループ変数が意図しない値になって無限ループしていた。
呼び出し直後に引数を caller-saved レジスタ(a0/a1/d0/d1)へ読み込んでから、
作業用に使う callee-saved レジスタだけを `movem.l %d2-%d5,-(%sp)` 等でスタックへ
退避・復帰する形に修正して解決した(修正後、`m68k-elf-gcc` 側の `main_e3.c` は
無変更のまま、`e3_copy.S` 側の修正だけで N_REPEATS 何回でも正しく完走することを
実測で確認した)。

#### 量子化誤差と N_REPEATS による対処

ポーリングを分離した直後、K=512KB・N_REPEATS=1 で3方式を測ったところ、
1回の転送が**1回の垂直同期(約16.7ms)未満で終わる**ケースが大半になった
(movem方式はK=512KBでも1回の転送でguestVsyncEvents=0または1にしかならなかった)。
垂直同期の「回数」は整数でしか数えられないため、この状態でK/回数を取ると
量子化誤差が支配的になり、ポーリング間隔(256/1024/4096)を振っても値が
収束しているのか判別できなかった。そこで同じKバイトの転送をN_REPEATS回
繰り返し、累積した垂直同期回数で割る方式に変更した。N_REPEATSは、目標
累積回数(TARGET_VSYNCS=300)に近づくよう、あらかじめK=512KBで軽く測った
概算スループットから逆算して決めた(`verify/verify_e3.mts` の
`ROUGH_BYTES_PER_FRAME_SEED` / `pickNRepeats()`)。

#### ポーリング間隔の収束確認(実測: 収束しなかった)

K=512KB・N_REPEATS=100固定で、ポーリング間隔(POLL_INTERVAL)を256/1024/4096の
3通りに振った:

| 方式 | N=256 | N=1024 | N=4096 | N=1024→4096の差 |
|---|---|---|---|---|
| word | 11,377.78 B/frame | 20,464.01 B/frame | 82,305.81 B/frame | +302% |
| long | 19,912.19 B/frame | 41,088.40 B/frame | 163,329.60 B/frame | +298% |
| movem | 81,920.00 B/frame | 329,740.88 B/frame | 1,379,705.26 B/frame | +318% |

**収束しなかった**(指示された判定基準: N=1024→4096の差が5%以内なら収束。
実際は約300%増加しており、収束の目安から大きく外れている)。ポーリング間隔を
4倍(1024→4096)にしてもスループットがほぼ4倍のまま増え続けており、
**N=4096でもポーリング負荷はまだ支配的**と考えられる。この事実をそのまま報告する
(判定基準を緩めて「収束した」とはしない)。したがって、後述の主測定
(N=4096採用)の数値は「ポーリング皆無の理論上限」ではなく、**N=4096という
具体的なポーリング頻度における実測値**である。より疎なポーリング(N=8192,16384…)
や割り込みベースの検出に変えれば、さらに高い値が出る可能性が高い(未検証)。

**【rev3実施後に確定した診断】** 上記の「収束しなかった」現象そのものが、
実は「ポーリングが疎すぎて垂直帰線期間のエッジを取り逃していた」ことの署名
だった。垂直帰線期間はフレーム全体の数%程度しかなく、ポーリング間隔が
帰線期間の長さより長いと GPIP が0になっている区間をまるごと飛び越し、
立下りエッジ(垂直同期)を見落とす。見落とすと分母(検出回数)が過少になり、
K/回数(バイト/フレーム)は大きい方向にずれる。**N を大きくする(ポーリング
間隔を疎にする)ほど取り逃しが増えて値が過大に出る**ため、「N=1024→4096で
約300%増加」はまさに取り逃しが悪化していく様子そのものだった。この診断は
レビューでの指摘によるものであり、本資料作成時点(rev2実施時)では
「ポーリング負荷がまだ支配的(=遅く出すぎている)」と誤って解釈していた
(方向を逆に読み違えていた)。以下の rev2 の「主測定」「線形性の確認」
「陰性対照」の数値は、この取り逃しの影響を受けた**過大評価**であり、
使わない(訂正記録として残す)。

#### 第2版=rev2(誤り、続き): 主測定・線形性・陰性対照の数値(過大評価。使わない)

| 方式 | K=64KB | K=128KB | K=256KB | K=512KB |
|---|---|---|---|---|
| word | 82,968.13 | 82,413.16 | 91,946.03 | 81,865.57 |
| long | 162,290.16 | 164,737.75 | 162,954.38 | 163,506.77 |
| movem | 661,913.60 | 1,315,681.72 | 1,328,251.92 | 1,381,898.17 |

(単位: バイト/フレーム。各セルは `K×N_REPEATS ÷ 累積垂直同期回数` で算出。
実測に使った N_REPEATS・累積回数は `docs/StageE-2-3_実測_20260819.md` 生成元の
`verify/verify_e3.mts` 実行ログに記録)

#### 線形性の確認

同一方式内でK/(累積回数から求めたバイト/フレーム)がほぼ一定(比例)しているかを
確認した(比例そのものは正しさの十分条件ではない。第1版で踏んだ教訓と同じ理由で、
ここでは「破綻していないかの消極的なチェック」としてのみ扱う):

- **long方式**: 162,290〜164,738の範囲に収まり(最大最小差1.5%)、ほぼ一定 = 線形性OK。
- **word方式**: K=256KBの点(91,946)だけ他の3点(81,865〜82,968)より約12%高い。
  他の3点はほぼ一定なので、この1点だけの逸脱は測定ノイズ(この点の累積回数が
  他よりやや少ない=268回で、量子化誤差がやや大きめだったこと)によるものと
  考えられるが、断定はしない。
- **movem方式**: K=65536(64KB)だけ661,913と、K=131072以降(1,315,682〜1,381,898)の
  約半分しかない。K=64KBはN_REPEATS=6363と非常に多い回数を繰り返す必要があった
  (小さいKほどTARGET_VSYNCS=300に到達するために多くの繰り返しが要るため)。
  繰り返しごとに発生する関数呼び出しオーバーヘッド(レジスタ退避・復帰、
  ポーリングの初期状態読み取り)が、K=64KBのように1回あたりのペイロードが
  小さい条件では無視できない比率を占め、実効スループットを押し下げた
  可能性がある(推測。未検証)。K=131072以降は比較的安定している。

#### 陰性対照(K=0、rev2時点)

3方式とも K=0(転送バイト数0)で `guestVsyncEvents=0` を確認した
(`E3_NEGATIVE_CONTROL_ZERO_OK=true`)。この陰性対照自体はゲスト側のポーリング
機構そのものは検証できていた(転送が無ければエッジも検出されない、という点は
取り逃し問題と無関係に成立する)ため、rev3でも同種の陰性対照を別途実施した。

#### 第3版=rev3(訂正後・本資料が採用する最終結論): ゲスト側のポーリングを完全に無くし、ホスト側でフレーム数を数える

**測定方法**: `stage_e/src/e3_copy.S`(word/long/movemの3ルーチン)から MFP GPIP
の読み出しを完全に削除し、コピーだけを行う素のループにした(オーバーヘッドが
ゼロになる)。`stage_e/src/main_e3.c` は転送ループの直前に `START_FLAG`
($000E0020)を、`N_REPEATS` 回すべて完了した直後に `DONE_FLAG`($000E0010)を
書くだけにした。`verify/verify_e3.mts` が host 側で `runFrame()` を1回ずつ
呼びながら両フラグを `peekByte()` で監視し、`START_FLAG` が立ってから
`DONE_FLAG` が立つまでの `runFrame()` 呼び出し回数を数える。host は自分が
何回呼んだかを正確に知っているため、取り逃しも過剰計上も原理的に起きない。
分解能は1フレームなので、所要フレーム数が最低30フレーム(目標40フレーム)
以上になるよう、`N_REPEATS` を方式・Kごとに校正した(小さい `N_REPEATS` で
試し、目標に届くまで倍率をかけて再測定する)。rev2で発見した callee-saved
レジスタ退避の修正は維持した(`e3_copy.S` のmovem版が引き続き該当。word/long版
はGPIPポーリング撤去に伴い callee-saved レジスタを一切使わなくなったため、
退避コード自体が不要になった)。

**主測定(K=64/128/256/512KB)**:

| 方式 | K=64KB | K=128KB | K=256KB | K=512KB |
|---|---|---|---|---|
| word | 14,266.34 | 14,266.34 | 14,266.34 | 14,266.34 |
| long | 22,810.87 | 22,795.13 | 22,795.13 | 22,795.13 |
| movem | 53,279.92 | 53,311.67 | 53,237.47 | 53,227.21 |

(単位: バイト/フレーム。校正の性質上、各K・方式の組は所要フレームがおおむね
目標値付近になるよう `N_REPEATS` を選ぶため、値がK間でほぼ一定になるのは
校正の設計通りであり、これ自体は独立した線形性の証拠ではない。独立した線形性の
証拠は次項の「R→2R」テスト)

**線形性の確認(K=512KB、校正されたRと2Rで所要フレームが2倍になるか)**:

| 方式 | R1 | 所要フレーム(R1) | R2=2×R1 | 所要フレーム(R2) | 比 |
|---|---|---|---|---|---|
| word | 4 | 147 | 8 | 294 | 2.000 |
| long | 8 | 184 | 16 | 367 | 1.995 |
| movem | 40 | 394 | 80 | 787 | 1.997 |

3方式とも比がほぼ厳密に2.00倍で線形性を確認した(`E3_ALL_LINEARITY_OK=true`)。

**陰性対照(R=0、転送なし)**: 3方式とも所要フレーム0を確認した
(`E3_NEGATIVE_CONTROL_OK=true`)。

**妥当性チェック(後述の「妥当性の相互確認」節で詳細)**: サイクル数換算・
movem/long比とも妥当範囲に収まり、`E3_VERDICT=DETERMINED`(数値を「確定」として
採用してよい)と判定された。

## 妥当性の相互確認: サイクル数換算

### rev2時点の記録(誤った原因の推測。訂正として残す)

rev2実施時、各実測値(バイト/フレーム)を `host.fetchAvInfo()` が自己申告する
`fps`(61.46Hz、CPUクロック16MHz)で「1ロングワードあたり何サイクルに相当するか」
に換算したところ、word=12.72 / long=6.37 / movem=**0.75**サイクル/ロングという、
68000として物理的にあり得ない値(目安20〜40サイクル/ロングを大きく下回り、
movemは1サイクル未満)が出た。当時は**この不整合の原因をサイクル換算の基準
(`avInfo.fps`取得タイミングや`adjust_frame_rates`の影響)ではないかと推測**し、
「バイト/フレームの実測値そのものは信頼できるが、サイクル数への変換式に
不整合がある」という切り分けで報告していた。

**この推測は誤りだった。** 真の原因はサイクル換算の基準ではなく、
「E-3の測定方法(訂正履歴)」に記録した通り、**分子であるバイト/フレームの
実測値そのもの(rev2のポーリング疎すぎ問題による垂直同期の取り逃し)が
過大評価されていたこと**だった。rev3では以下の通り、rev2と**同じ換算基準**
(`avInfo.fps=61.46Hz`、同じ取得タイミング=`loadGame`直後・ゲスト側CRTC書き換え前)
を使い、分子(バイト/フレーム)だけをポーリング皆無の実装に直してもう一度
換算したところ、3方式とも妥当な範囲に収まった(下表)。**これは換算基準
(61.46Hz)そのものは最初から正しかったことの裏付けでもある。**

### rev3の結果(妥当性チェックを通過)

| 方式 | K=512KBでのバイト/フレーム | 1ロングあたりの換算サイクル数 | 妥当性 |
|---|---|---|---|
| word | 14,266.34 | 72.99 | 妥当(5サイクル未満ではない。目安20〜40よりやや高いが「GVRAMのウェイト次第でもう少し」の範囲) |
| long | 22,795.13 | 45.68 | 妥当 |
| movem | 53,227.21 | 19.56 | 妥当(目安20〜40の下限付近) |

換算に使った2値: **CPUクロック16,000,000Hz**、**`avInfo.fps`=61.459999...Hz**
(`host.fetchAvInfo()` が返す値。`loadGame()` 直後、ゲスト側が65536色1ページ
モードへ切り替える前に取得。rev2時点で「実際のビデオモードと異なる可能性がある」
と留保していたが、rev3の結果が妥当な範囲に収まったことから、この留保は
実害が無かったと判断できる。ただし「同一かどうかの直接確認」自体は今回も行って
いない)。1フレームあたりのサイクル数は **16,000,000 ÷ 61.459999... =
260,331.93サイクル**。

**movem/long の速度比**: 53,227.21 ÷ 22,795.13 = **2.335倍**。指示された妥当範囲
(1.5〜2.5倍)に収まった(`MOVEM.L`による8レジスタ一括転送が`MOVE.L`単体より
明確に速いが、8倍のような極端な差にはならない、という常識的な関係が実測でも
再現された)。

**総合判定**: `E3_ALL_PLAUSIBLE=true`、`E3_VERDICT=DETERMINED`。rev3の数値
(バイト/フレーム・サイクル/ロングとも)は妥当性チェックをすべて通過したため、
本資料の結論として採用する。

## 結果の読み方(限界)

**この測定は px68k の実装を測っている。** エミュレータで測った速度は、
エミュレータのタイミングモデルを測ったものであって実機の速度ではない。

- 検証ハーネスは `px68k_cpuspeed=16Mhz` を設定した(実機 X68000 無印の標準クロック
  10MHzより高い)。`px68k_ramsize=1MB`、`px68k_no_wait_mode=enabled` も設定した。
  それ以外(`px68k_frameskip`=Full Frame、`px68k_adjust_frame_rates`=enabled、
  `px68k_audio_desync_hack`=disabled)は px68k-libretro のコード上の既定値のまま。
- **この値は px68k 上の実測であり、実機(10MHzの68000機など)では異なる可能性が
  ある。実機での確認は未実施。**
- rev3は時間計測をゲスト側から完全に排除し(ポーリングオーバーヘッド無し)、
  host側の `runFrame()` 呼び出し回数だけで所要フレーム数を測っている。
  したがって rev2 で懸念していた「ポーリング負荷が乗った状態の実測値」という
  限界は rev3 では解消されている(妥当性チェック・線形性チェックともに通過)。
- 転送方式(word/long/movem)にも強く依存する値であることは実測の通り。DMAC
  (DMAコントローラ)は使っていない。DMACを使えばさらに変わりうる(未検証)。
- 分解能は1フレーム(`runFrame()` 1回)。所要フレーム数が最低30フレーム以上に
  なるよう `N_REPEATS` を校正した上での実測値であり、量子化誤差は小さいと
  考えられるが、「所要フレーム数÷N_REPEATS」という平均値である点は変わらない
  (1回ごとのばらつきそのものは見ていない)。

## 後退案検討のための判断材料(決定はしない)

構想上の後退案は「差分転送」または「16色4ページ方式」の二択とされている。
今回の実測(rev3)で分かった事実のみを列挙する(どちらを選ぶかの決定はここでは
行わない)。

- **3方式いずれも全画面(512KB)は1フレームに収まらない**(word: 約36.75フレーム
  =全画面の約2.72%、long: 約23.00フレーム=約4.35%、movem: 約9.85フレーム=約
  10.15%)。最速のmovem方式でも1フレームで転送できるのは全画面の1割程度にとどまる。
- **差分転送**を検討する場合: ブロック崩し(基準作例)の1フレームあたりの実際の
  差分量(パドル・ボール・ブロック数個分の矩形)が、採用する転送方式に応じて
  2.7%(word)〜10.15%(movem)の枠に収まるかが判断材料になる。movem方式を
  採用すれば同じデータ量でもword方式の約3.7倍(≈53,227/14,266)の面積を
  1フレームで転送できる。
- **16色4ページ方式**を検討する場合: 1ピクセルあたりのビット数が65536色モードの
  1/4(4bit vs 16bit)になるため、単純計算では同じ転送方式でも約4倍の面積を
  1フレームで転送できる計算になる(全画面512KB相当のピクセル数を16色で表現
  すると128KBになるため)。仮にmovem方式(全画面の約10.15%)と組み合わせると
  単純計算で約40.6%相当まで拡大する計算になるが、この掛け合わせ自体は今回
  実機/エミュ上で計測していないので推測にとどまる(あくまで検討材料であり
  実測ではない)。
- 転送方式そのものの最適化のうち、DMAC使用は今回試していない。movem方式が
  すでにword/long方式より明確に高速(word比で約3.7倍、long比で約2.34倍)である
  ことは実測したが、DMACならさらに改善するかは未検証。

## 確定できなかった項目

- 転送方式をDMAC(DMAコントローラ)にした場合のスループットは未測定。
- 16色4ページ方式でのGVRAM転送スループットは未測定(推測にとどまる)。
- 実機(実クロックの68000)での確認は未実施。
- rev3のK×方式ごとの `N_REPEATS` 校正はTARGET_FRAMES=40を目安にした自動校正
  であり、より大きい所要フレーム数(数百〜数千フレーム)で測定した場合に
  同じ値に収束し続けるかの追加確認はしていない(K=512KBについてはR→2Rの
  線形性確認で部分的に裏取りした)。

## 実行方法

```sh
npx --no-install tsx verify/verify_e2.mts
npx --no-install tsx verify/verify_e3.mts
```

`WEBX68K_DIR`(既定 `../WebX68k`)で上書き可能。E-2 は `WARMUP`(既定1500)・
`MEASURE`(既定300)、E-3(rev3) は `MAX_FRAMES`(既定20000、タイムアウト用の
フレーム数上限)で上書き可能。E-3 は
`tools/build_stage_e3.sh <K_bytes> <method:0|1|2> <n_repeats> <out.xdf>` で
個別のビルドも可能(method: 0=word/1=long/2=movem。rev2まであった
`poll_interval` 引数はrev3で削除した)。
