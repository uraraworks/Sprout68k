# 学習用ライブラリ第一版(L0 + 標準名の層) 実装記録 20260819

## 位置づけ

`docs/API設計_20260819.md` の2層構成のうち、**L0(生層)と標準名の層のみ**を
実装した。**L1(`x68_cls`/`x68_screen_flip`/描画プリミティブ等の入門者向けAPI)
はこの回では実装していない**(次回作業のスコープ)。

## 構成

- `lib/include/x68.h` — 単一ヘッダ(第一版はヘッダ分割しない)
- `lib/src/x68_l0.c` — L0のうちTRAP不要な部分(垂直同期待ち、65536色1ページ
  モード設定)
- `lib/src/x68_std.c` — 標準名の層(memcpy/memset/strlen/abs/srand/rand/
  puts/printf)。故障注入用の`X68_FAULT_*`マクロもここにある
- `lib/asm/x68_iocs.S` — IOCS呼び出し($21/$23/$04/$46)の薄いラッパ。
  stage_c/stage_eの既存実装と挙動は同じ(シンボル名だけ`x68_`接頭辞に
  焼き直した。既存Stageの検証は壊していない)
- `lib/asm/x68_gvram_copy.S` — `stage_e/src/e3_copy.S`のMOVEM版
  (`e3_copy_movem`)をそのまま流用したメインメモリ→GVRAM高速コピー
- `lib_test/src/main.c` — 検証用テストプログラム(全関数を自己検査しつつ
  host側が末端を実測できるよう固定アドレスへ結果を書く)
- `tools/build_lib_test.sh` — テストプログラムのビルド(通常/故障注入版)
- `verify/verify_lib.mts` — px68k上で実際に走らせて検査するNodeスクリプト

## 実装した関数

**L0**: `x68_iocs_print` / `x68_iocs_locate` / `x68_iocs_bitsns` /
`x68_iocs_disk_read` / `x68_vsync_wait` / `x68_gvram_mode_65536_1page` /
`x68_gvram_copy_movem`

**標準名の層**: `memcpy` / `memset` / `strlen` / `abs` / `srand` / `rand`
(`X68_RAND_MAX`定義) / `puts` / `printf`

## printf 対応/非対応(第一版)

対応: `%d %u %x %c %s %%` のみ。非対応(幅指定・0埋め・精度指定・長さ修飾子・
浮動小数点・その他未知の指定子・末尾`%`)に出会ったら **`[BADFMT]` を実際に
出力して処理を継続する**(黙って誤動作しない)。詳細一覧は
`lib/include/x68.h` のコメントに記載。

## printf/puts の改行の扱い(実装判断、実測で確認)

IOCS $21のコンソールが`\n`単体で改行する保証が無かったため、出力直前に
`\n`の手前へ`\r`を補って`\r\n`として送る設計にした(`x68_emit`)。
`puts`は標準と同じく出力後に必ず改行を1つ追加する。**この設計が実際に
複数行の表示として機能することは検証(下記PUTS_OK/PRINTF_FMT_OK)で
実測済み。**

## 検証の穴2件と修正(2026-08-19、コーディネータからの指摘を受けて対応)

初回実装の`verify/verify_lib.mts`と故障注入3件(memcpy/strlen/printf)は
正しく機能していたが、**その3件が当たっていない箇所に2つの穴があった**。
指摘を受けて両方を修正し、それぞれに対応する故障注入を追加した。

### 穴1: `x68_vsync_wait`の検査は、待っていなくても通っていた

**症状**: 修正前の判定は`normal.vsyncCounter !== 300`だけだった。
`run_vsync_test()`は300回のループなので、`x68_vsync_wait`が実際に待たず
即returnする実装でも、ループは最後まで回ってカウンタは最終的に300へ到達し
PASSしてしまう。「到達したこと」を「待ったこと」の証拠として扱っていたのが
誤りだった。「300回待つループなので到達していれば待てて完走した証拠」という
コメントは、到達の速さ(何hostフレームかかったか)を見ていない時点で成立
していなかった。

**修正**: Stage E-2(`verify/verify_e2.mts`)と同じ「host側フレーム数と
ゲスト内カウンタ増分の比」判定に戻した。`HV_PROGRESS`が7(`run_vsync_test`
開始直後、まだ1回も待っていない)になった瞬間を基準点にし、そこから固定の
50host フレーム(300回のループ上限よりずっと小さい)を進めた時点での
`HV_VSYNC_COUNTER`増分を見る。measure窓を上限より十分小さくすることで、
「正しく待てていれば窓内では終わらない」状態を作り、即returnする実装との
違いを比として検出できるようにした。判定基準はStage E-2と同じ
`rate ∈ [0.5, 2.0]`。

**追加した故障注入**: `x68_vsync_wait`が即returnする版(`vsync_no_wait`)。
修正後の検査でrate=0.0000(範囲外)を検出しFAILすることを確認した。

### 穴2: GVRAMの検査は、転送先がずれていても通っていた

**症状**: 修正前の判定は「6点が背景色でないこと」「6点が互いに異なる色で
区別できること」の2条件だけだった(全面クラスタ数一致条件を外した際の
代替として設けた条件)。期待する色そのものとは突き合わせていなかったため、
`x68_gvram_copy_movem`の転送先が1ワードずれる(あるいは転送順序が入れ替わる)
故障が起きても、6点はいずれも背景色ではなく互いに異なる色のままなので
両条件とも満たしてしまいPASSしていた。「変化したこと」は「正しいこと」の
証拠にならないという典型例だった。

**修正**: host側に既にあった`genColor()`(ゲストの`gen_color()`と同じ生成式)
に加えて、GVRAM16bit色値が実際にcanvas上のRGB8へどう変換されるかを
px68k-libretro(`x68k/palette.c`のPal_SetColor、`libretro/windraw.c`)と
WebX68k(`src/libretro-host.ts`のhandleVideoRefresh)のソースを実際に読んで
確認し、`decode16to24()`として実装した(G5 R5 B5 I1 → 内部RGB565
(Iビットはgreenの最下位に落ちる) → ビット複製でRGB888)。

ただしcanvasの拡大縮小に伴う補間により、実測値は変換式そのままの値と
完全一致はしない(実測: 単一ワードのマーカーで距離13.9〜30.5のずれ)。
このため「完全一致」ではなく、**各サンプル点の観測色に最も近い期待候補
(全16ワードぶんの`copy_i`色 + 2つの直接書き込み色 + 背景色)を求め、
それが自分自身の期待値と一致するか」を判定基準にした**(閾値80、実測の
ずれに対して十分な余裕を見た値)。期待候補同士は`genColor()`の設計により
互いに大きく離れているため、この閾値でも取り違えは起きない。

**追加した故障注入**: `x68_gvram_copy_movem`の転送先を1ワード(2バイト)
ずらす版(`gvram_copy_offset`)。修正後の検査で、4サンプル点すべてが
「自分自身の期待色」ではなく隣接するワード(`copy_5`地点で`copy_4`の色、
`copy_10`地点で`direct_B`の色、`copy_15`地点で`copy_14`の色)を示している
ことを検出しFAILすることを確認した。**この結果は同時に、修正前の
「非背景・相互区別」判定がなぜ空振りしていたかも裏付けている**
(観測された色は本物の別ワードの色そのものなので、背景色でも重複色でも
なく、旧判定の2条件をどちらも満たしてしまう)。

### 追加したもう1件: `x68_iocs_bitsns`が常に0を返す版

既存のBITSNS検査(押下区間でpressedFrac、解放区間でreleasedFracを見る方式)
自体は元から妥当だったが、指摘に「常に0を返す版でもFAILすることを確認」が
含まれていたため`bitsns_always_zero`を追加した。修正後の検査で
pressedFrac=0.000(閾値0.9未満)を検出しFAILすることを確認した。

## 実装中に踏んだ罠(記録)

1. **32bit同士の乗除算にlibgcc.aが必要**: `-nostdlib`は`-nodefaultlibs`相当を
   含みlibgccも道連れに除外するため、`rand()`の乗算・`printf`の10進/16進変換の
   除算で`__mulsi3`/`__udivsi3`/`__umodsi3`のリンクエラーになった。
   `m68k-elf-gcc -m68000 -print-libgcc-file-name`のパスを明示的にリンクに
   加えて解決した。
2. **BITSNS検証: 粗い「WARMUPフレームを先に一括消化してから状態を見る」実装は
   検証区間ごと素通りする**: 最初の実装ではWARMUP(1500フレーム)を一括で
   消費してから`HV_PROGRESS`/`HV_BITSNS_COUNT`を見ていたが、この環境では
   ブート+全テスト実行が1500フレームよりずっと短い時間で完了しており、
   BITSNSテスト区間そのものがWARMUP消化中に丸ごと過ぎ去っていた(実測:
   1500フレーム時点で既に`HV_DONE`到達、`HV_BITSNS_COUNT=200`)。
   起動直後から1フレーム単位でキー状態を追従させる実装に直して解決した
   (修正後は`HV_BITSNS_COUNT`がフレームと1:1で増加することを実測で確認)。
3. **GVRAM検証: 全面クラスタ数の一致を条件にすると量子化衝突で誤FAILする**:
   `x68_gvram_copy_movem`は指定したバッチの16ワード全部をGVRAMへ書くため、
   確認対象に選んだ4点以外の12点も画面に出ており、かつ5-5-5-1量子化で
   複数ワードが同じRGBに潰れる(実測: 16語中2組が衝突し14クラスタになった)。
   「クラスタ総数が期待点数と一致するか」で判定すると無関係な衝突で
   誤ってFAILになるため、当初は期待する座標を直接サンプリングし「背景色で
   ない」「選んだ点同士が互いに区別できる」の2条件に判定基準を変更した。
   **ただしこの2条件は「穴2」として後日指摘を受け、期待色との一致を見る
   方式にさらに修正した(詳細は上の「検証の穴2件と修正」節を参照)。**
