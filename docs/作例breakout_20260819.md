# 作例「ブロック崩し」実装記録 20260819

## 位置づけ

`docs/API設計_20260819.md` が最初の作例として基準に据えたブロック崩しを実際に
動かし、入力の学習層(`x68_key_down`)・乱数の学習層(`x68_rand_int`)を実装した
上で完成させた。L0/標準名の層(`docs/lib実装_20260819.md`)・L1画面(`docs/L1実装_20260819.md`)
に続く回。

## 実装した関数

- `int x68_key_down(int key);`(`lib/src/x68_input.c`) — L0の`x68_iocs_bitsns`
  (実装済み)の薄いラッパ。`group=(key>>3)&0xf`・`bit=key&7`を`unsigned long`
  経由で計算するため、範囲外のキー番号(負値・巨大な値)を渡しても落ちない
  (設計原則1)。
- キー定数 `X68_KEY_LEFT`(0x3b) / `X68_KEY_UP`(0x3c) / `X68_KEY_RIGHT`(0x3d) /
  `X68_KEY_DOWN`(0x3e) / `X68_KEY_SPACE`(0x35) — `docs/StageE-4_実測_20260819.md`
  の実測値をそのまま使用(推測なし)。
- `int x68_rand_int(int n);`(`lib/src/x68_std.c`) — `n<=0`なら0を返す
  (ゼロ除算で落とさない)。実装済みの`rand()`の上に載せるだけ。
- `void x68_locate(int col, int row);`(`lib/src/x68_l1.c`) — **今回発見した
  未実装項目**。`docs/API設計_20260819.md`の表は公開名を`x68_locate`と
  定めていたが、`docs/lib実装_20260819.md`の回で実装されていたのは
  L0の`x68_iocs_locate`のみで、L1の薄いラッパが無かった(ドキュメント上は
  「実装済みのため再掲しない」と誤って扱われていた)。ブロック崩しの
  スコア表示を書く過程でコンパイルエラーとして発覚し、`x68_iocs_locate`を
  1行で呼ぶだけのラッパとして追加した。挙動は変えていない。

## ライブラリ側で追加修正した点(サンプル実装中に発見)

**`x68_screen_open()`に起動時の割り込みマスク解除を追加した。**
`docs/StageE-4_実測_20260819.md`に「キーのmake/breakはMFP割り込み経由で
IOCS内部状態へ反映されるため、起動直後のSRを明示的に`#0x2000`へ設定しないと
BITSNSが更新されない」という実測記録があったが、この手順はStage E-4の
テストプログラム(`stage_e/src/main_e4.c`)にしか入っておらず、L1/L0のどの
共通関数にも組み込まれていなかった。ブロック崩しでパドルがキー入力に
反応しない不具合として最初に顕在化し(後述「検証で見つけた不具合」参照)、
`x68_screen_open()`(入門者が必ず最初に呼ぶ関数)の先頭に
`move.w #0x2000,%sr`を追加することで解決した。**サンプルコード
(`samples/breakout/main.c`)側にはアセンブラを一切書かせない**設計方針を
維持したまま解決できた。この変更は`lib/src/x68_l1.c`(既存のL1実装)への
修正であり、`verify/verify_l1.mts`を再実行して回帰が無いことを確認済み
(全項目PASS、故障注入5件も引き続き検出成功)。

## ブロック崩し本体(`samples/breakout/main.c`)

L1と標準名の層だけを使用(`x68_iocs_*`等のL0は直接呼ばない)。ポインタは
使わず、配列と添字だけで書いた(文字列リテラルを除く)。

- **画面**: 512x512、背景黒。
- **パドル**: 幅64x高さ8、`X68_KEY_LEFT`/`X68_KEY_RIGHT`で毎ループ4px移動、
  画面内にクランプ。
- **ボール**: 8x8、初速dx=+2,dy=-2固定(決定論的。乱数はブロック色にのみ使用)。
  壁反射・パドル反射・画面下へ落ちたら中央へリセット(ゲームオーバー処理は
  簡潔にする、との指示に従い、ライフ制はなし)。
- **ブロック**: 4行x8列(計32個)、当たったブロックだけ壊れてスコア+10。
  ブロック色は`x68_rand_int(4)`で4色から選ぶ(乱数の使用例。当たり判定・
  検証結果には影響しない)。
- **スコア表示**: `x68_locate(0,0)` + `printf("SCORE:%d", score)`。
  最大でも "SCORE:" + 4桁程度で桁10前後に収まり、桁63の制約を満たす。
- ループは `x68_cls()` → 描画(ブロック→パドル→ボール→スコア文字) →
  `x68_screen_flip()` の素直な形。

## 検証(`verify/verify_breakout.mts`)

ホストが`LibretroHost.setKey()`で実際にキーを押し(Stage E-4で確定した経路。
1フレームの配送遅延を踏まえてrunFrame()の回数に余裕を持たせた)、`px68k`上で
ゲームを動かして実測した。`px68k_no_wait_mode=enabled`を設定し、すべて同期
実行(自前タイムアウト、バックグラウンド無し)。

### 検証で見つけた不具合(実装中に発見・修正)

1. **`x68_key_down`が常に偽を返す**: 上記「ライブラリ側で追加修正した点」の
   通り、割り込みマスク未解除が原因。`x68_screen_open()`側で修正。
2. **paddleLeftMoved/ballMovedの判定が最初は全滅した**: ブロック崩し本体は
   **毎フレーム全32ブロック+パドル+ボールをcurRectsへ積む**実装のため、
   1回の`x68_screen_flip()`(=ゲスト側の1ループ)が転送する量は常に多く、
   実測で**1ゲストループが概ね20〜25 hostフレームぶんのCPU時間を消費する**
   ことが分かった(初期のHOLD_N=20/MOVE_N=20/RUN_BUDGET=2000という
   `verify/verify_l1.mts`と同程度のフレーム数を流用した設計では、ゲスト側の
   ループが数回しか進まず「押しても動いていないように見える」誤検出をして
   いた)。host側のframe数を押す/待つ区間ごとに200(パドル)・100(ボール)・
   8000(反射・ブロック破壊観測)へ引き上げ、`HV3_PROGRESS`(完了ループ数)を
   ログへ出して実際にゲストループが進んでいることを確認しながら調整した。
   これは検証ハーネス側の誤り(閾値を緩めたのではなく、対象が十分な回数
   実行される保証が無かった)であり、ゲーム本体のバグではない。

すべて`npx tsx verify/verify_breakout.mts`で実測(2026-08-19実施、EXIT=0)。

| # | 項目 | 結果 | 詳細 |
|---|---|---|---|
| 1 | パドルが左右キーで動く | PASS | 陰性対照(200フレーム無入力): `x=224→224`不変。LEFT押下(200フレーム): `224→192`(左へ移動)。RIGHT押下(200フレーム): `192→220`(右へ移動)。押した向きに動き、押さなければ動かないことを確認 |
| 2 | ボールが移動している | PASS | 100フレームの間に`(308,200)→(316,192)`と変化 |
| 3 | ボールが壁で反射する | PASS | X方向・Y方向どちらの反射も観測(`atFrame=2094`、進行方向の符号反転を検出) |
| 4 | ブロックが実際に消える | PASS | `HV3_LAST_DESTROYED`が示す破壊済みブロック(index=30)の矩形中心をcanvas実測。観測RGB=(0,4,0)、期待背景RGB=(0,4,0)、距離0.0(閾値90以内)で背景色になっていることを確認。**自己申告(HOSTVAR)だけでなく実際のGVRAM画素で確認**(atFrame=887) |

## 実負荷での転送量の実測(API設計_20260819.md「API実装時の宿題」1を閉じる)

通常ビルドを実際に動かした状態で、`x68_l1_last_flip_bytes`を毎フレーム
(host runFrame基準で2095サンプル、ゲストループ換算で概ね90ループ以上ぶん)
記録した。

- **最大値: 116,992バイト/フレーム**
- **平均値: 114,941.7バイト/フレーム**
- Stage E-3実測スループット(16MHz, MOVEM.L, 53,227バイト/フレーム)に対する比率:
  **最大219.80%、平均215.95%**
- L1実装時に台本で測った値(全画面転送を除く平均5,615バイト、予算比10.55%)との比較:
  **平均2047.0%**(約20倍)

**予算(Stage E-3実測)を大きく超えている。これは実測結果であり、本検証の中で
対策は入れていない(指示通り、超過をそのまま報告する)。**

### 超過の原因(実装から読み取れる範囲)

`samples/breakout/main.c`は**毎フレーム、生存している全ブロック(最大32個)+
パドル+ボールを`x68_box_fill`で描き直す**実装になっている。L1の矩形追跡は
「前フレーム∪今フレームの矩形」を転送するため、ブロックの見た目が
まったく変化していないフレームでも、32個のブロック矩形が毎回`curRects`
(かつ`prevRects`)に積まれ、転送対象になり続ける。これがL1実装時の台本
(動く矩形1〜2個+稀な全画面転送)より1桁以上重い理由である。

**入門者が最初に書くコードとして「変化した部分だけ描き直す」最適化を要求
するのは第一版の範囲外と判断し、本実装では行っていない。** ブロックが
そのままの静止画像を毎フレーム再送しているだけなので、静止画差分検出
(例えば「壊れていないブロックはそもそも毎フレーム呼ばない」)を入門者に
教える発展課題として位置づけるのが妥当と考えられるが、**この判断・対策の
要否はメインセッション側で検討すること(本実装では数字を作らず、実測の
まま報告する)。**

## 未実装・未確定の項目(明記)

- **転送量が予算を大幅に超えている**(上記参照)。対策は未実施。
- **UP/DOWNキーはブロック崩しで未使用**(ゲーム設計上不要なため)。
  `x68_key_down`自体の実装はLEFT/RIGHT/SPACEと同じ式なので原理的に成立する
  はずだが、UP/DOWN単体の実測(押しっぱなし・弁別)はStage E-4時点でも
  今回でも行っていない(Stage E-4の「確定できなかった項目」がそのまま
  持ち越し)。
- **SPACEキーは未使用**(ブロック崩しの仕様上、ポーズ/再スタート等の機能を
  持たせていない。定数のみ定義済み)。
- 例外ハンドラ/日本語パニック画面は今回もスコープ外のまま(次回)。
- **`x68_screen_open()`への割り込みマスク解除の追加は、既存のL0/L1検証
  (`verify/verify_lib.mts`・`verify/verify_l1.mts`)が壊れていないことを
  再実行で確認済み**(両方とも全項目PASS、故障注入もすべて検出成功のまま)。
- ボールの初期方向・パドル速度・ブロック配置は決定論的な固定値(乱数は
  ブロックの色選択にのみ使用)。ゲームバランスの調整は行っていない。
