# X68kDev IDE 実装・実測記録 2026-08-22

## 目的と現在地点

ブラウザ内で X68000 向け C ソースを編集・保存し、wasm 版ツールチェーンで `.xdf` を
生成し、そのイメージを同じページ内の px68k で起動する学習者向け IDE を実装した。
Chromium 系ブラウザ1種で、**書く → ビルド → 実行**が一続きに動くことを確認した。
Safari / Firefoxでは未実測であり、配布・オフライン設計やデバッグ機能まで完成した、
という意味ではない。

IDE は次の4段で作った。

## 1. IDEシェル、エディタ、保存（`7e22e8d`）

同じ作者 URARA-works の WorkbenchNP2 を土台に、3ペインのIDEシェル、CodeMirror 6.0.2
によるCハイライト、タブ、ファイルツリー、IndexedDBへの保存を移植した。PC-98固有処理と
デバッグ機能は削除し、ビルド・実行は差し替え可能なアダプタのスタブとした。

Chromium 系ブラウザ、`http://127.0.0.1:5180/ide/`、1280×800で確認した値・状態:

- 3ペイン構成とCのシンタックスハイライトが表示された。
- ビルドボタンは未実装スタブの状況を表示した。
- IndexedDB `X68kDevProjectFS` が生成され、同一originの別製品用DBと衝突しない名前になった。

## 2. 利用者ソースのブラウザ内ビルド（`0d02976`）

F-4で作った「アセット束をfetchし、`MemoryHostFs`へ入れ、memfs版
`cc1` → `as` → `ld` → `objcopy` を動かす」経路を共有モジュールに整理した。
利用者が編集したCソース1本を、既存の `lib/`、crt0、ブートセクタとリンクする
`user` ターゲットを追加した。リンク構成とメモリ配置検査はbreakoutと同じである。

実測結果:

- IDEの `hello.c` から `user.xdf` **1,261,568バイト**を生成し、ダウンロードできた。
- `;` を消した実コンパイルエラーではGCC原文とキャレットが表示され、編集中ソースは
  失われなかった。修正後は同じエディタ内容から再びビルドできた。
- `samples/breakout/main.c` と同一内容を `user` ターゲットへ渡した `.xdf` は、既存
  breakoutターゲットの全native版と **1,261,568バイトすべて一致**した。
- 利用者ソースを1バイト変更する陽性対照では不一致になった。

## 3. px68kによるブラウザ内実行（`c0f0bdb`）

別リポジトリへの実行時依存を避けるため、WebX68kから
`px68k_libretro.js`（73,762バイト）と `px68k_libretro.wasm`（638,990バイト）を
X68kDev内へバイト一致でコピーした。WebX68kのlibretroホスト層は、環境callback、
RGB565描画、テキストVRAM読出しなどABI境界の取りこぼしを避けるため、必要な依存とともに
丸ごと流用した。

ビルド済み `user.xdf` をfd0へ入れ、`px68k "<path>" ""` を `/game/boot.cmd` に書いて
`loadGame()`する。Human68kは経由せずfd1は空である。通常実行はrAFループのままとし、
右ペインのcanvasへ描画する。

実測結果:

- Node検証ではIDEの `hello.c` を `user` ターゲットでビルドして起動し、800フレームで
  テキスト画面の `HELLO X68000` を確認した。
- 全バイト0の1,261,568バイトXDFでは、1800フレーム後にも同じ文字列が出なかった。
- Chromium系ブラウザでは「実行」後にプローブの状態が `running` になり、canvasへの
  描画開始を確認した。

## 4. 内部情報の遮蔽とブラウザ検証用プローブ（`ee0282f`）

学習者向け診断では、利用者ソースの内部パスだけを学習者が知るファイル名へ戻し、残る
作業領域内生成物はbasenameにした。パス以外の行・桁・本文・文脈行・ソース行・キャレット行
は変更しない。内部例外と生stderrは開発者向け `console.error` に残し、UIの失敗要約から
memfsモード名や内部JSパスを除いた。Emscripten factoryの `thisProgram` には実ツール名を
渡し、既定の `./this.program` を表示させないようにした。

ページ非表示時にも実測できるよう、`window.x68kdevEmulatorProbe` に同期実行用
`runFrames(n)` を追加した。呼出し時は保留中rAFをcancelし、同期実行後にrAFを1本だけ
再登録する。JavaScriptは単一スレッドであり、実行中callbackとの割込みは起きないため、
可視状態で呼んでも二重ループにならない。製品の通常経路は引き続きrAFである。

Chromium系ブラウザ1種での確定実測:

- `;` を実際にキー入力で消して再ビルドすると、
  `hello.c:6:27: error: expected ';' before 'for'` がキャレット付きで表示された。
  `/workspace` と `objects/user/source` は表示されず、エディタ内容も保持された。
- リンク警告は
  `m68k-elf-ld: warning: user.elf has a LOAD segment with RWX permissions` と表示された。
- 成功時の成果物は `user.xdf` **1,261,568バイト**だった。
- ページ非表示（`document.hidden=true`）のまま、呼出し前はframes=0、テキスト空であることを
  確認し、`window.x68kdevEmulatorProbe.runFrames(800)` を呼んだ。その後
  `readTextScreen()` に `HELLO X68000` が出た。

## WorkbenchNP2からの流用判断

ゼロからUIを作らず、同じ作者のWorkbenchNP2をコピーしてX68kDev向けに作り替えた。
共通ライブラリ化を先に行わなかった理由は、WorkbenchNP2の `buildCurrent`、`runCurrent`、
`startDebug`、`stopDebug`、`initialize` でUI操作とPC-98固有処理が同一関数に混在していた
ためである。先に共通化するには、両製品に適用できる抽象境界を設計し、WorkbenchNP2側も
改修したうえで互換性を検証する必要がある。独立製品として短い経路で実測へ進むため、
今回はコピー後に固有処理を削り、X68kDev内だけで境界を作った。

### 流用したもの

- `ide/vendor/codemirror/`一式: Cハイライトを含むCodeMirrorのローカルbundleとMIT本文。
- `ide/project-fs.mjs`: DB名を `X68kDevProjectFS` として使うIndexedDBファイル層。
- 骨格として `ide/index.html`、`workbench.css`、`workbench.js`、`source-view.mjs`、
  `sample-manifest.mjs`: ブランド、レイアウト、操作、サンプルをX68kDev向けに変更した。

### 削除・不採用にしたもの

- DOS／PC-98ツールチェーンと実行系: `browser-toolchain.mjs`、`toolchain.js`、
  `dos-prompt.mjs`、`freedos-session.mjs`、`loader-control.mjs`、`exec-load-result.mjs`、
  `legacy-hdd-runner.mjs`、`c-runner.*`、`saka-*`。
- PC-98エミュレータ資産: `core/`、`freedos/`、`vendor/webnp2/`。
- PC-98用のデバッグ／アドレス処理: `debug-*`、`segment-arithmetic.mjs`、
  `source-debug.mjs`。ブレークポイント、ステップ実行、ソース行マップも削除した。
- 製品固有表示: `help*`、`pc98dev-icon.svg`。PC-98アイコンは流用していない。

### 差し替え口

- `ide/x68k-adapter.mjs` の `createX68kAdapter()` がUIと実装の境界である。
  `initialize()`、`build()`、`run()`を公開し、UIは個々のwasmツールやpx68k内部を持たない。
- `build()` は `web/browser-toolchain.ts` の共有ブラウザビルド経路へ接続する。
- `run()` は `ide/px68k-runtime.ts` の `X68kRuntime` へXDFを渡す。
- `workbench.js` の `buildCurrent()` / `runCurrent()` は保存・ボタン状態・結果表示に限定した。
- 68kソースデバッグ用の差し替え口はまだ作っていない。

## ライセンス判断

同梱px68k-libretroコアはGPLv2であり、フロントエンドと一体で動作するため、X68kDevの
ソフトウェア全体をGPLv2として公開する判断をした。本文はルートの `COPYING` に置いた。
上流とビルド元はREADMEに記載している。

- IDEシェルの由来はURARA-worksのWorkbenchNP2（MIT）。
- CodeMirrorはMITで、同梱各パッケージの本文を `ide/vendor/codemirror/` に保持する。
- 同梱IPL ROMには権利者の再配布許諾が適用され、許諾文を
  `ide/system/IPLROM-LICENSE.txt` として同梱する。GPLv2へ再ライセンスしたものではない。
- `cgrom.dat` は実機ROMの複製ではなく、Public Domainの東雲フォントからWebX68k側で
  自作生成された代替文字ROMである。帰属は `ide/system/CGROM-NOTICE.md` に記録する。

## 利用者ターゲットをバイト一致で証明する仕組み

`user` と `breakout` は、main.cの供給元以外について同じbuilder経路、ライブラリ、crt0、
リンカスクリプト、ブートセクタ、メモリ配置検査を使う。検証では利用者ソースとして
`samples/breakout/main.c` と同一内容を渡し、既存breakoutターゲットを全nativeで作った
正典XDFと比較する。結果は **1,261,568バイト一致**した。

したがって、既存breakoutのコンパイル・リンク・メモリ配置・ブートセクタ・起動検証を
変えずに、利用者ソース供給だけを新経路へ通したことを証明できる。さらにソース1バイト変更で
不一致になる陽性対照を取り、比較が単に固定出力を見ているのではないことも確認した。

## 検証一覧と実行方法

リポジトリ直下で次を実行する。IDE第4段完了時の確定結果はすべて終了コード0だった。

|---|---|---|
| `node tools/driver/verify.mts` | gcc driver経由と全native駆動層、最適化変更の陽性対照 | PASS |
| `node tools/driver/verify_wasm.mts` | native / NODERAWFS / MEMFS混成表#1〜#8、2ターゲット | **16件PASS、SKIP 0** |
| `node tools/driver/verify_hostfs.mts` | HostFs一致、メモリ衝突、ソース変更 | PASS |
| `node tools/driver/verify_web_assets.mts` | 配信束とnative正典、必須ヘッダ欠落 | PASS |
| `node tools/driver/verify_user_target.mts` | user対breakoutの一致、診断書換、素通し、ツール名 | PASS |
| `node verify/verify_ide_boot.mts` | hello XDFのpx68k起動と全ゼロXDFの陰性対照 | 800フレームで文字列、陰性1800フレーム、PASS |
| `node ide/verify-ide.mjs` | IDE資産、DOM、コアhash、ライセンス、プローブの静的検査 | PASS |

配布用bundleは次で検査し、IDE第4段完了時にエラーなし・終了コード0を確認した。

```sh
../WebX68k/node_modules/.bin/vite build
```

診断書換検査の陽性対照は、書換だけを検査上で無効化して非0終了を確認する。

```sh
X68KDEV_DIAGNOSTIC_REWRITE_FAULT=1 node tools/driver/verify_user_target.mts
```

第4段では内部パス残存を検出し、終了コード1になった。製品コードには書換を無効化する
設定はない。

ブラウザ検証の準備と操作:

```sh
node tools/build_web_assets.mts
../WebX68k/node_modules/.bin/vite --config vite.config.ts
```

1. <http://127.0.0.1:5180/ide/> をChromium系ブラウザで開く。
2. `hello.c` の `;` を実際にキー入力で消してビルドし、ファイル名・行・桁・GCC原文・
   キャレット、内部パス非表示、ソース保持を確認する。`;` を戻してビルドし、
   `user.xdf` が1,261,568バイトであることを確認する。
3. 「実行」を押してページを非表示にし、`document.hidden`、`getFrameCount()`、
   `readTextScreen()` の事前状態を確認してから
   `window.x68kdevEmulatorProbe.runFrames(800)` を呼ぶ。確定実測の事前状態は順に
   `true`、`0`、空文字列だった。
4. `window.x68kdevEmulatorProbe.readTextScreen()` に `HELLO X68000` が含まれることを
   確認する。これはChromium系1種でのみ実測済みである。

## 踏んだ罠

### ページ非表示でrAFが進まず、実行中なのに文字が出ない

- **症状**: ブラウザペインを非表示にするとrAFが1回も来ない場合があり、別の観測では
  framesが8のまま停止した。`state=running` なのに画面もテキストも進まず、エミュレータが
  壊れているように見えた。
- **真因**: エミュレーションの通常ループをrAFだけで駆動しており、非表示ページでは
  ブラウザがrAFを停止・抑制するためだった。px68kの起動やXDFの異常ではない。
- **どう気づいたか**: `document.hidden=true` の状態で400ms観測してrAFが0回だった。
  一方、Nodeでは同期的に800フレーム進めると同じXDFから文字列が出たため、コアではなく
  ブラウザのスケジューリング差へ切り分けた。
- **再発防止**: 検証専用プローブに同期の `runFrames(n)` を設けた。確定実測では非表示、
  frames=0、テキスト空から800フレーム進め、`HELLO X68000` を確認した。通常製品動作は
  rAFのままにし、検証口と分離した。

### 学習者向け画面に内部実装名が漏れた

- **症状**: 診断に `/workspace/objects/user/source/hello.c`、失敗要約にmemfsモード名と
  内部JSパス、リンク警告のツール名に `./this.program` が表示された。
- **真因**: stderrと駆動層例外を開発者向け内部表現のままUIへ渡し、Emscripten生成glueの
  `thisProgram` も既定値のままにしていた。
- **どう気づいたか**: Node検証は成果物一致とstderr捕捉を確認していたが、学習者が見る
  最終表示までは観測していなかった。実ブラウザでエディタから実際に `;` を消す操作を
  行い、初めて漏れが見えた。
- **再発防止**: 本物のcc1診断を使い、内部パス0件と、行・桁・本文・文脈・キャレット保持を
  同時に検査する。内部パスを含まない行の完全な素通し、書換無効化で検査が落ちる陽性対照、
  実ld警告のツール名もNode検証へ追加した。内部詳細はconsoleだけに残す。

- ブレークポイント、ステップ、行マップを含む68kソース行デバッグ。
