# 学習用 API 第一版 設計 20260819

## 位置づけ

Stage A〜D でブート経路・C 実行・ディスク全体ロード・実機互換が実測で通った。
次は構想（`../../docs/構想_20260819.md`）の必須要件 (c)「学習用 API は範囲外を
無視して落ちない設計」を担う層を作る。

## 2層に分ける

- **L0（生層）**: 実測済みの事実そのまま。GVRAM/CRTC/VC 直書き、IOCS 直呼び。
  上級者と、L1 の実装自身が使う。
- **L1（学習層）**: 入門者が触るのはここだけ。以下の原則を守る。

### L1 の設計原則

1. 座標・色・添字は**すべてクリップ/丸め**。エラーコードを返さない
   （返しても入門者は見ない。「何も起きない」で済ませる）
2. **ポインタを露出しない**。値と配列だけで書けるようにする
3. **暴走は「静かに固まる」ではなく「見える形で止まる」**。例外ベクタを埋め、
   日本語のパニック画面を出す。要件 (a) 1クリック復帰・(b) エラーの日本語注釈と
   噛み合わせる
4. **API は最初の作例から逆算して削る**。網羅から入ると、測っていない機能の
   宣言だけが増える

## 基準にする作例: ブロック崩し

構想の発端（あうぇっど氏の投稿の題材）と同じ。矩形塗り・当たり判定・キー入力・
フレーム同期で成立し、スプライトも音源も要らない。第一版の API はこれに要る
機能だけとする。

## 画面モード: 65536色1ページ固定 + 矩形追跡の部分転送

**決定(2026-08-19、Stage E-3 の実測を受けてメインセッションで決定)**

Stage B/E-1 で実測済みの 65536色1ページモード(512x512、stride=512ワード)は維持する。
**当初案の「全画面の裏バッファをフレーム毎に丸ごと転送する」方式は破棄する。**

### 破棄の根拠(Stage E-3 実測)

全画面は 512x512x2 = 524,288バイト。px68k・16MHz での実測スループットは
最速の `MOVEM.L` 方式でも 53,227バイト/フレームで、**全画面転送には約10フレームかかる**
(全画面の約10.15%/フレーム)。実機標準の 10MHz ではさらに落ちる。
詳細: `docs/StageE-2-3_実測_20260819.md`

### 採る方式

裏バッファはメインメモリに持つが、**GVRAM へ転送するのは「前フレームと今フレームに
描画された矩形の和集合」だけ**にする。裏バッファの内容が GVRAM と食い違うのは描画が
あった場所だけなので、これで正しさを保ったまま転送量が実際の描画面積に比例する。

`cls()` も同じ機構で処理する。**全画面を塗る実装にしない。**入門者が最初に書くループは
`cls()` → 描画 → `screen_flip()` であり、ここで `cls()` が全画面を塗ると全画面転送が
復活して破綻するため。前フレームに描画された矩形だけを背景色で戻せばよい。

**入門者が書くコードは素直な `cls` → 描画 → `screen_flip` のまま変えない。**
矩形の追跡は L1 の内部で行い、API には出さない(設計原則2「ポインタを露出しない」と
同じ理由で、簿記を入門者に持たせない)。

### 成立の見積もり(未実測。API 実装時に実測すること)

ブロック崩しで1フレームに書き換わる面積は、パドル(消去+描画で約2KB)、ボール(約256B)、
たまに壊れるブロック(約1KB)で合計 3〜4KB 程度と見積もった。10MHz 実機換算の
概算予算(約33KB/フレーム)に対して1割強にあたる。**これは見積もりであって実測ではない。**
API 実装時に、実際のブロック崩し相当の描画負荷で1フレームあたりの転送量と所要フレーム数を
実測して確かめること。

### 採らなかった案

- **16色4ページへの後退**: 転送自体が不要になる利点はあるが、上記の見積もりで予算に
  収まる見込みが立ったため採らない。パレットの概念を入門者に説明する必要が生じる点も
  理由(採否の判断は上記の実測結果に基づく。将来 budget が足りないと実測されたら再考する)
- **DMA(DMAC)経由の転送を先に測る**: GVRAM 側の帯域が律速なら大差ない可能性が高く、
  部分転送で予算に収まる見込みが立ったため、今は測らない。必要になったら測る

### 実装後の訂正: 転送対象は「触った領域」ではなく「内容が変わった領域」

当初の実装は「描画命令が**触った**領域」を転送対象にしていた。これだと毎フレーム
同じ場所に同じ絵を描き直したとき、内容が1ドットも変わっていないのに転送される。
作例のブロック崩し（静止したブロック32個）で**予算の216%（平均114,942バイト/フレーム）**
に達し、方式として成立しなかった。

実装を「**内容が変わった**領域」の転送に変更した。裏バッファは毎フレーム同じ手順
（`cls` の塗り戻し → 全描画）で組み立て直されるため、**前フレームと今フレームで
描画命令が同一なら、その領域の内容も同一**である。よって描画命令の一覧を突き合わせ、
異なる命令の前後の矩形・追加された命令の矩形・消えた命令の矩形だけを転送すればよい。

実測（作例ブロック崩しの実負荷）: **平均 323.7バイト/フレーム（予算比 0.61%）**、
最大 7,680バイト（14.43%）。**入門者が書くコードは変わらない。**
詳細: `docs/L1実装_20260819.md`、`docs/作例breakout_20260819.md`

### Video Controller の設定値（実測確定）

`$E82601`(VC R2 下位) = **`0x21`**（`0x01`=グラフィックページ有効 + `0x20`=テキスト表示）で、
**65536色グラフィックとテキストが同時に表示され、重なった位置ではテキストが手前**になる。
VC R2 下位・VC R1 下位を各0x00〜0xFF全数（計512通り）振って確定した。
詳細: `docs/VC重畳実測_20260820.md`

**当初は `0x01` のみを設定しており、テキストが画面に出ていなかった。**このとき
「65536色モードではテキストが表示できない（モード全体の排他）」と結論したが、
これは**誤帰属**だった。実験でグラフィックモードの有効/無効だけを振り、
**一度も触っていないレジスタの既定値が結果を決めていた**ことに気づかなかったため。
訂正の経緯: `docs/重なり実測_20260820.md`

## 命名規則（2026-08-19 決定）

1. **C 標準に同じ意味のものがあるなら、標準の名前とシグネチャに合わせる。**
   `printf` / `puts` / `memcpy` / `memset` / `strlen` / `rand` / `srand` / `abs` など。
   この環境は `-nostdlib` のフリースタンディングで C 標準ライブラリが存在しないため
   実装は自前になるが、**名前と使い方は本物と同じにする**
2. **標準に無い、この機械固有のものだけ `x68_` を接頭辞に付ける。**
   `x68_flip` / `x68_key_down` / `x68_box_fill` など。定数は `X68_` を接頭辞にする
3. 結果として **「`x68_` が付いている＝X68000 固有、付いていない＝どの C でも同じ」**
   という読み方が成立する。接頭辞が「うちのもの」の印ではなく、
   **「移植するとき書き換えが要る場所」の印**になる

### `api_` のような接頭辞を採らなかった理由

「これは C ではなく用意されたものだ」と示す目的自体は正しいが、`api_` は分野ではなく
カテゴリを名乗るため呼び出し箇所で情報を持たず、かつ実在のライブラリに存在しない規約
なので後で覚え直しが要る。実在のライブラリは例外なく自分の名前を接頭辞にする
(`SDL_`、`gl`、`al_`)ため、**その規約自体を覚えてもらう**方が構想の判断基準
（「考え方が後続の言語で崩れない」）に合う。

`x68_` は製品名ではなく機種名なので、**名称が決まっても改名が不要**である
（構想では名称は未定）。

### SDL に名前を寄せなかった理由

- SDL は `SDL_Renderer*` 等のハンドルを全描画関数に渡す設計で、L1 の設計原則2
  （ポインタを露出しない）と衝突する
- このコードはベアメタルの X68000 向けで、本物の SDL に対してコンパイルできることは
  ない。**名前だけ似せると「SDL の知識がそのまま使える」という誤った期待**を生む
- 語彙の転移は資料側で渡せる（「これは SDL では `SDL_RenderPresent` にあたる」と書く）

### `memcpy` / `memset` は必須

フリースタンディングでも gcc は構造体コピーや配列初期化で `memcpy` / `memset` を
暗黙に呼び出すため、自前で持っていないとリンクが通らない。

### `printf` を名乗ることの要件

標準の名前を使う以上、挙動が本物とズレると学習者を誤らせる。第一版では:

- **整数・文字列・文字の書式に絞り、浮動小数点は非対応**とする
- **未対応の書式指定は、黙って誤動作させず目に見える形で失敗させる**
- 対応している書式と、していない書式を利用者向けの資料に明記する

## 第一版 API（案）

未実測の項目に依存する部分は「Stage E で確定」と明記する。関数名は仮。

### 画面

| 宣言 | 挙動 |
|---|---|
| `void x68_screen_open(void);` | 65536色1ページモードを設定し裏バッファを用意する |
| `void x68_screen_flip(void);` | 垂直同期を待ち、裏バッファを GVRAM へ転送する |
| `void x68_cls(int color);` | 裏バッファ全体を塗る |
| `void x68_pset(int x, int y, int color);` | 範囲外は無視（何もしない） |
| `int  x68_pget(int x, int y);` | 範囲外は 0 を返す |
| `void x68_box_fill(int x, int y, int w, int h, int color);` | 画面外にはみ出す分はクリップ。w/h が負なら何もしない |
| `void x68_box(int x, int y, int w, int h, int color);` | 枠のみ |
| `void x68_line(int x1, int y1, int x2, int y2, int color);` | 両端とも画面外でも落ちない |
| `int  x68_rgb(int r, int g, int b);` | 0〜255 を受け、範囲外は丸めて 16bit 色値を返す |

画面サイズ定数（`X68_SCREEN_W` / `X68_SCREEN_H`）は **Stage E-1 で実測により確定した**
（詳細: `docs/StageE-1_実測_20260819.md`、検証コード: `verify/verify_e1.mts`）。

- `X68_SCREEN_W = 512`（GVRAM 1ライン = 512 ワード = 1024 バイト。stride を全数対応表から実測）
- `X68_SCREEN_H = 512`（y=511 まで可視、y=512 は不可視であることを実測）
- GVRAM オフセット0はフレームバッファ上の (0,0) に出る（原点のずれ無し）

Stage B で読んだ 768x512 は px68k のフレームバッファ（canvas）側の寸法であり、
65536色1ページの GVRAM 論理サイズ（512x512）とは別物だった。65536色グラフィック面は
canvas の左側512ドットぶんのみを占める。

### 文字（旧: print / print_at）

**`print` / `print_at` は廃止し、標準名との組み合わせにする。**

| 宣言 | 挙動 |
|---|---|
| `int  printf(const char *fmt, ...);` | テキスト画面へ出力。標準名（上記「`printf` を名乗ることの要件」を参照） |
| `int  puts(const char *s);` | 標準名 |
| `void x68_locate(int col, int row);` | 表示位置の指定（IOCS $23。Stage E-6 で実測確定）。座標系は96桁 x 32行。範囲外座標はハードウェア側が無視するため追加のクリップは不要 |

旧 `print_at(col, row, s)` は `x68_locate(col, row); printf(s);` の組み合わせで書ける
ため、独立した関数を置かない。

#### テキスト画面とグラフィック画面は幅が違う

Stage E-1 と E-6 の実測値を並べると次のようになる。

| 面 | 実測値 |
|---|---|
| 65536色グラフィック面 | 512 x 512 ドット(Stage E-1) |
| テキストの座標系 | 96桁 x 32行(Stage E-6)。1文字8x16ドットなら 768 x 512 ドットに相当 |

**テキスト側のほうが横に広い。**グラフィック面の幅512ドットは64桁ぶんにあたるため、
桁64以降に文字を出すと、65536色で描いているゲーム画面の外側に出ることになる。
スコア表示などは桁63までに収める必要がある。

**重なり方は実測で確定した**（`docs/重なり実測_20260820.md`）。

| 項目 | 実測値 |
|---|---|
| 桁0・行0の位置 | グラフィックの (0,0) 相当。原点のずれ無し |
| 1桁 / 1行 | **8ドット / 16ドット** |
| グラフィック面に収まる範囲 | **桁0〜63**（桁64以降は x=512 以降でグラフィック面の外） |
| 重なったときの前後 | 上記 VC R2 = `0x21` では**テキストが手前** |

### 入力（すべて Stage E-4 で確定）

| 宣言 | 挙動 |
|---|---|
| `int x68_key_down(int key);` | 押されている間ずっと真。IOCS $04(BITSNS)を `TRAP #15` で呼び、D1.W にキーコードグループ、D0.B に返る8キー分の押下ビットパターンを見る。ブロック崩しのパドルに要るのは押しっぱなし判定なので、1回読むと消える入力ではなくビットセンス側が本命 |

キー定数は `X68_KEY_` を接頭辞にする（スキャンコードは X68000 固有のため）。
実測で確定した値だけを定義する（詳細: `docs/StageE-4_実測_20260819.md`）。

| 定数 | スキャンコード | グループ/ビット |
|---|---|---|
| `X68_KEY_LEFT` | 0x3b | group7 bit3 |
| `X68_KEY_UP` | 0x3c | group7 bit4 |
| `X68_KEY_RIGHT` | 0x3d | group7 bit5 |
| `X68_KEY_DOWN` | 0x3e | group7 bit6 |
| `X68_KEY_SPACE` | 0x35 | group6 bit5 |

### 停止画面（設計原則3の実装）

`x68_screen_open()` が例外ベクタを自前ハンドラに差し替え、アドレスエラー・不正命令・
ゼロ除算で**日本語の停止画面**（何が起きたかと PC の値）を表示して止まる。
表示前に65536色グラフィックモードを解除して、メッセージを読める状態にする。
詳細: `docs/パニック画面_20260820.md`

68020以降の VBR にも対応した（宿題2）。ただし **px68k は CPU を常に68000として
初期化するため、68030機での動作は検証できていない。実機での確認は未実施。**

### 時間

`screen_flip()` が垂直同期待ちを兼ねるため、第一版では独立した待ち関数を置かない。
必要性が出たら追加する。

### 乱数（旧: rand_seed / rand_int）

| 宣言 | 挙動 |
|---|---|
| `void srand(unsigned int seed);` | 標準名。種を設定 |
| `int  rand(void);` | 標準名 |
| `int  x68_rand_int(int n);` | 0〜n-1 を返す。`n <= 0` なら 0 を返す（ゼロ除算で落とさない）。範囲付きの安全な乱数は標準に無いため `x68_` を付ける |

| `unsigned long strlen(const char *s);` | |

### 音

第一版では**出さない**。構想で「新規作業として重いもの」に分類済み
（MXDRV/ZMUSIC は Human68k 常駐前提で使えない）。

## 落ちない代わりに「見える形で止まる」

例外ベクタを全部埋め、アドレスエラー・不正命令・ゼロ除算で日本語の停止画面を
出す。表示するのは「何が起きたか」と PC の値まで。ここが要件 (a) の1クリック
復帰の入口にもなる。

**実現可能性は Stage E-5 で実測する**（ベクタを書き換えて実際に捕まえられるか）。

| E-4 | キー入力（押しっぱなし判定を含む）のレジスタ規約 | **実測済み(2026-08-19)**。IOCS $04(BITSNS)を `TRAP #15` で呼ぶ(D1.W=キーコードグループ、D0.B=8キー分の押下ビットパターン)。押しっぱなし・離鍵・キーの弁別・押し直しをすべて実測で確認。陰性対照も取得済み(詳細: `docs/StageE-4_実測_20260819.md`) |
| E-5 | 例外ベクタを書き換えて実際に捕捉できるか | **実測済み(2026-08-19、ただし68000前提)**。例外ベクタテーブルは番地0固定で、$0C(アドレスエラー)/$10(不正命令)/$14(ゼロ除算)へ直接書き込むことで自前ハンドラへ差し替えられる。3種の弁別・ハンドラからのIOCS $21表示・陰性対照すべて確認済み。**68030機(VBRあり)での成立は未検証**(px68kがCPUを常に68000として初期化するため本プロジェクトの手段では原理的に検証できない)(詳細: `docs/StageE-5_実測_20260819.md`) |
| E-6 | 文字表示の座標指定の手段 | **実測済み(2026-08-19)**。IOCS $23 で位置指定(D1.L=桁、D2.L=行)した後に IOCS $21 で表示すると指定位置に出る。4箇所で実測一致、陰性対照も取得済み。座標系は**96桁 x 32行**。範囲外座標(負値・上限超え)はカーソルが動かず無視され、暴走しない(詳細: `docs/StageE-6_実測_20260819.md`) |

各項目とも、**陰性対照または故障注入を1つ添えてから合格とする**。検査が空振り
していないことを先に確かめる（Stage B の判定が空振りしていた実績があるため）。

### 検証ハーネスの性質（テストを書くときの注意）

Stage E-4 の実測で、ホスト側がキーを押してからゲストが観測するまで**一貫して1フレームの
配送遅延**があることが分かった(コア側で `WinX68k_Exec()` が入力ポーリングより先に走る
実装順序による)。これは**検証ハーネス側の性質**であって API の設計には影響しないが、
この経路で入力を測るテストを書くときは常に効く。閾値を緩めて誤魔化さず、遅延として
織り込むこと。
