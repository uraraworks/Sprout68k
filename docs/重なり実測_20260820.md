# テキスト面とグラフィック面の重なり方 実測 20260820

`docs/API設計_20260819.md`「テキスト画面とグラフィック画面は幅が違う」節、
「API 実装時の宿題」3番の実測。Stage E-1(65536色グラフィック面 512x512ドット)と
Stage E-6(テキスト96桁x32行)は個別には実測済みだが、**両者の重なり方
(テキストの桁0がグラフィックのx=0と揃っているか)は未実測**だった。本資料は
推定を確認するのではなく、グラフィック面の既知座標にマーカーを描き、テキストの
既知桁・行に文字を出して、同じフレームバッファ上で位置関係を直接読んだ結果。

## 結論(4項目)

| # | 項目 | 確定できたか | 結論 |
|---|---|---|---|
| 1 | 桁0・行0の対応先ドット座標(原点のずれ) | **確定** | 文字の描画インク(グリフの実インク画素)は x=0, y=1 から始まる。x方向はずれ無し。y方向は「セルの中でグリフが上に1ドットの余白を持つ」フォント由来のオフセットで、桁・行ピッチ(後述)から見て原点そのもの(セル境界)は(0,0)相当と矛盾しない |
| 2 | 1桁・1行あたりのドット数 | **確定** | 1桁 = **8ドット**、1行 = **16ドット**(19点の実測値すべてで矛盾なく成立、後述) |
| 3 | グラフィック面(512ドット幅)に収まる桁の範囲 | **確定** | **桁0〜63がグラフィック面(x=0〜511)の内側、桁64以降は外側**(桁63の描画範囲はx=504〜511、桁64はx=512〜519で実測点そのものが512ドット幅の外に出ている) |
| 4 | 文字とグラフィックが重なったときの前後関係 | **確定(ただし「前後関係」ではなく「排他」という形で確定)** | 65536色グラフィックモードが有効な間、**その512ドット幅の範囲内ではテキストはフレームバッファに一切現れない**(Text VRAMには正しく書き込まれているのに、描画結果に出ない)。ピクセル単位の合成ではなく、グラフィックの塗りの有無に関わらず起きるモード全体の排他だった |

**確定できなかった項目: なし。**

> **【訂正(2026-08-20追記、`docs/VC重畳実測_20260820.md`)】** 上表項目4の
> 「排他」という結論は、**Video Controller のレジスタをVC R2下位バイトの
> 1値(`0x01`)しか振っていなかったことによる誤帰属だった。** この実験は
> グラフィックモードの有効/無効だけを振っており、プレーン表示・優先順位を
> 決めるVC R2そのものの値やVC R1(優先度制御)は一度も振っていなかった。
> 直後のパニック画面実装(`docs/パニック画面_20260820.md`)で`VC_R2=0x20`に
> するとテキストが見える(=固定していた`0x01`という値の側が原因)ことが
> 実測され、この帰属を作り直した。
>
> `docs/VC重畳実測_20260820.md`でVC R2下位バイト(0x00〜0xFF全数)・VC R1下位
> バイト(0x00〜0xFF全数)・VC R2上位バイト/VC R1上位バイト(粗く)を実測で
> 振った結果、**65536色グラフィックとテキストは同時に表示できる**(例:
> `VC_R2下位=0x21`)。重なった位置では**通常はテキストが手前**(グラフィック
> の塗り色ピクセルの上にグリフのインクが別色として観測される)。ただし
> VC R2上位バイトの特定の値(`0x14`)では例外的にグラフィックが手前になる
> 組み合わせも見つかっている。詳細・振った範囲・実機未確認である旨は
> `docs/VC重畳実測_20260820.md`を参照。
>
> 元の実験・記述は誤りの経緯として消さずにそのまま残す(このプロジェクトの
> 方針)。「排他」という言葉自体は誤りだったが、**当時固定していた
> `VC_R2=0x01`という設定下ではテキストが実際に見えなかったという実測事実は
> 変わらない**(原因の帰属先が「モード」ではなく「その1つのレジスタ値」
> だったという訂正)。

## 測定方式

推定(2つの実測値の突き合わせによる「たぶんこう」)を確認するのではなく、
同一フレーム内、または直接比較可能な条件下で、既知の位置に置いたマーカーの
観測位置を実測する2フェーズ構成にした。

### フェーズ1: テキストの桁・行あたりドット数と境界の実測

Stage E-6 実測済みの `stage_e/src/main_e6.c`(変更していない)をそのまま使い、
桁だけを変えた19点のマーカー(文字 `#`)を、**1マーカーにつき専用の行**
(row=0〜18)で1つずつ配置した。

```
row=0  col=0    row=7  col=60   row=14 col=70
row=1  col=2    row=8  col=61   row=15 col=80
row=2  col=4    row=9  col=62   row=16 col=90
row=3  col=8    row=10 col=63   row=17 col=94
row=4  col=16   row=11 col=64   row=18 col=95
row=5  col=32   row=12 col=65
row=6  col=48   row=13 col=66
```

行を重複させない理由: 桁の値を自由に振っても、connected component(後述)が
縦方向で確実に分離され、桁同士の水平衝突リスクを測定手法に持ち込まずに済むため。
桁61〜66は512ドット境界(桁63/64相当)を1桁刻みで見るための専用点。

起動後、`putImageData` で捕まえたフレームバッファ全体を走査し、非背景ピクセルの
**8近傍連結成分**ごとに外接矩形を求め、ラスタ順(y→x昇順)に校正マーカーへ
対応付けた(Stage E-1 の「N昇順=ラスタ順」の手法をそのまま踏襲)。

**実測で判明した注意点**: ANKフォントの字形(`6`・`D`・`O`等、曲線を含む文字)は
4近傍(上下左右)だけでは1文字の内部が複数成分に分裂する(斜め方向にしか隣接
しないドットがあるため)。実測で確認: `E6 DONE` を4近傍で解析すると31成分に
分裂し、8近傍にしたところ空白を除く6文字分＝6成分にきれいに分離した。この事実
(4近傍31→8近傍6)を最初にデバッグスクリプトで確認してから、本測定に8近傍を
採用した(想像で決めていない)。

陰性対照(マーカー無し、`main_e6.c` が必ず末尾に無指定で出す `"E6 DONE"` のみが
出る検体)でも同様に6成分(空白を除く6文字)であることを確認済み
(`OVL_CAL_NEGATIVE_CONTROL_OK=true`)。

校正本体では合計25成分(マーカー19 + `E6 DONE`6)が実測され、マーカー群
(Y範囲 1〜302)と `E6 DONE` 群(Y範囲 305〜)が重ならないことを確認した上で
機械的に分離した(仮定のまま使わず、分離の事実を実測で検証してから使っている)。

**実測結果(col,row → 観測bbox)**:

行ピッチ(隣接するrowのminY差分、18組すべて)は **全て16** で一定
(`OVL_PITCH_Y_DETERMINED=true`)。桁ピッチ(隣接するcolのminX差分をcolの差で割った値、
18組すべて)は **全て8** で一定であり、さらに col=0 の点を基準に
`x = 0 + col*8` で19点全てが矛盾なく説明できることを確認した
(`OVL_PITCH_X_DETERMINED=true`、Stage E-1の「候補stride全数一致検査」と同じ考え方)。

境界(桁60〜66)の実測値は上表の通りで、桁63の最大x(511)がグラフィック面の
実測済み最大可視x(511、Stage E-1)と一致し、桁64の最小x(512)がその外に
出ていることを直接確認した。

### フェーズ2: グラフィックとテキストの重ね合わせ(同一フレーム)

新規追加した `stage_e/src/main_overlay.c`(Stage B/C/E-1と同じ3レジスタ設定で
65536色モードを有効化した後、GVRAM矩形塗り→IOCS $23+$21での文字表示、の順に
両方行う。`lib/` は変更していない)を使い、フェーズ1で実測したピッチ・原点
(8x16、原点(0,0)基準)から計算した4セルを1フレームに同居させた:

| セル | 内容 | 桁,行 |
|---|---|---|
| box+text | 塗り(明色)+文字'Z' | col=5, row=3 |
| box-only | 塗りのみ(対照) | col=8, row=3 |
| text-only | 文字'Z'のみ、塗り無し(対照) | col=11, row=3 |
| negative | 何も置かない(陰性対照) | col=20, row=3 |
| far | 文字'FAR'のみ(境界確認用、グラフィック外想定) | col=70, row=3 |

さらに `farRow` の x=511(グラフィック面の実測済み最大可視x)に基準ドットを
置いた。

**実測結果**:

- negative セル: 背景色(0,0,0)のみ(`OVL_PHASE2_NEGATIVE_CONTROL_OK=true`)
- box-only セル: 塗り色(0,231,0)のみで単色に埋まっている
  (`OVL_PHASE2_BOX_ONLY_SOLID=true`、対照として正常)
- text-only セル: **フレームバッファ上は背景色のみ**(文字が見えない)。
  ただし `readTextScreen()`(Text VRAMを直接読む、フレームバッファとは独立の経路)
  では col=11,row=3 に確かに `Z` が書き込まれていることを確認した
  (`OVL_PHASE2_TEXT_ONLY_IN_TEXTVRAM=true`)
- box+text セル: box-only セルと**完全に同一の単色**(塗り色のみ)。
  ここも `readTextScreen()` では `Z` が書き込まれていることを確認済み
  (`OVL_PHASE2_BOXTEXT_IN_TEXTVRAM=true`)
- far セル: `readTextScreen()` に `FAR` が出現し、かつフレームバッファ上でも
  x=512以降(グラフィック面512ドット幅の外側)に非背景ピクセルが実際に出現した
  (`OVL_FAR_TEXT_BEYOND_X511=true`)

**結論(項目4の詳細)**: 65536色グラフィックモードが有効な間、**グラフィック面の
512ドット幅の範囲内(x=0〜511、桁0〜63)ではテキストが一切見えない**。これは
「文字を置いた場所だけ隠れる」というピクセル単位の合成ではなく、**塗りを
一切行っていないセル(text-onlyセル)でも同様に文字が消える**ことから、
グラフィックモード全体がその範囲のテキスト表示を排他している(モードレベルの
排他)と判断できる。

**この結論が「文字表示機能自体の欠陥ではない」と言える根拠**: フェーズ1
(65536色モードを一切使わない`main_e6.c`)では同じ文字表示手段(IOCS $23 + $21)
でフレームバッファに正しく文字が描画されることを実測済み(25個の連結成分が
検出できた事実そのものが証拠)。フェーズ2との差はグラフィックモードの
有効/無効のみであり、原因をそこに切り分けられる。

一方、x=512〜767(桁64以降、グラフィック面の外側)は65536色グラフィック面が
物理的に存在しない領域のため、そこでは通常通りテキストが表示される
(farセルの実測で確認)。**したがって、項目3と項目4は同じ境界(桁63/64)で
つながっている**: グラフィック面の外(桁64以降)ではテキストは常に見えるが、
グラフィック面の内側(桁0〜63)では65536色モード有効時にテキストが完全に
隠れる。

## 入力追従

- フェーズ1: 桁を0,2,4,...,95まで19通りに振り、観測x座標がすべて
  `x = col*8` で説明でき、行(row=0〜18)を振ると観測y座標が一定の16ドット
  刻みで移動することを確認した(19点、うち桁61〜66は1桁刻みの細かい追従も確認)。
- フェーズ2: セルの桁・行(5,3 / 8,3 / 11,3 / 20,3 / 70,3)を変えると、
  塗り・文字それぞれの観測位置が対応して移動することを確認した(セル位置は
  フェーズ1で実測したピッチ・原点から計算した座標をそのまま使っている)。

## 陰性対照

- フェーズ1: マーカー無し検体で `"E6 DONE"` 以外の成分が出ないこと
  (`OVL_CAL_NEGATIVE_CONTROL_OK=true`)。
- フェーズ2: 何も置いていないセルに背景色以外のピクセルが出ないこと
  (`OVL_PHASE2_NEGATIVE_CONTROL_OK=true`)。

## 確定できなかった項目

なし。4項目すべて実測で確定できた(項目4は当初想定していた「ピクセル単位の
前後関係」ではなく「モードレベルの排他」という形での確定になった。これは
推定を裏切る結果であり、推定通りに解釈して埋めることはしていない)。

## 成果物・実行方法

- `stage_e/src/main_overlay.c`: GVRAM矩形塗り + IOCS $23/$21 でのテキスト表示を
  同一プログラムで行う検体(新規追加。`lib/` は変更していない)
- `tools/gen_markers_overlay.py`, `tools/build_stage_overlay.sh`: 上記のビルド一式
  (Stage E-1/E-6のビルドスクリプトと同じ構成。crt0・ブートセクタはStage Cを流用、
  IOCSスタブはStage C/E-6のものをそのまま流用)
- `verify/verify_overlay.mts`: フェーズ1(テキスト校正、`main_e6.c`流用)→
  フェーズ2(重ね合わせ、`main_overlay.c`)の順に実測する

```sh
npx --no-install tsx verify/verify_overlay.mts
```

`WEBX68K_DIR`(既定 `../WebX68k`)、`FRAMES`(既定3000)で上書き可能。
`px68k_no_wait_mode=enabled` を最初から設定している(未設定だとコアが実時間に
自己同期し `runFrame()` を何回呼んでも進まない既知の罠)。すべて同期実行、
自前タイムアウト(`makeDeadline`)を使用。
