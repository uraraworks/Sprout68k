# Stage E-4 実測 20260819

学習用 API の `key_down(key)`(押されている間ずっと真になる判定)を実装するための
下地を実測した。手読み・文献の解読で得た候補と、実測で確認した事実は出所を分けて
記録する。

## 結論(要約)

- **読み取り手段は確定した。** IOCS $04(BITSNS、`D1.W`=キーコードグループ、
  `TRAP #15`、`D0.B`=8キー分の押下ビットパターン)を実際に呼び出し、ホスト側の
  `setKey()` による押下操作が観測できることを実測で確認した。
- **押しっぱなし・陰性対照・離鍵・キーの弁別・押し直しの5条件、すべて合格。**
- **副産物として「ホストの `setKey()` からゲストの観測まで、ちょうど1フレームの
  配送遅延がある」ことを実測で発見・確定した。** 最初の実装ではこれを考慮せず
  「押し直し」テストが3項目とも false になり、原因調査でこの遅延を突き止めた。

## 読み取り手段(実測で確定)

IOCS $04(BITSNS)を `TRAP #15` で呼ぶ。呼び出し規約:

| レジスタ | 意味 |
|---|---|
| `D0.L`(呼び出し前) | `4`(関数番号) |
| `D1.W`(呼び出し前) | キーコードグループ(0〜$f) |
| `D0.B`(戻り値) | 指定グループ8キー分の押下ビットパターン(1=押されている、0=離されている) |

`group = scancode >> 3`、`bit = scancode & 7` の対応で、今回使う5キーは:

| キー | スキャンコード | group | bit |
|---|---|---|---|
| LEFT | 0x3b | 7 | 3 |
| UP | 0x3c | 7 | 4 |
| RIGHT | 0x3d | 7 | 5 |
| DOWN | 0x3e | 7 | 6 |
| SPACE | 0x35 | 6 | 5 |

ゲスト側(`stage_e/src/main_e4.c`, `stage_e/src/e4_bitsns.S`)は無限ループで
`iocs_bitsns(7)` / `iocs_bitsns(6)` を呼び続け、結果を固定アドレスへ書く:

- `HOSTVAR_GROUP7 = *(0x000E0040)`(LEFT/UP/RIGHT/DOWN を含む)
- `HOSTVAR_GROUP6 = *(0x000E0041)`(SPACE を含む)
- `HOSTVAR_POLLS = *(0x000E0044)`(32bit、ループが実際に回っていることの生存確認)

起動直後の SR 割り込みマスクが不明(boot.S/crt0.S のどちらも変更していない)
だったため、`main_e4.c` の先頭で明示的に `move.w #0x2000,%sr` を実行し、全レベルの
割り込みを受け付ける状態にしてから計測している(キーのmake/breakはMFP割り込み
経由でIOCS内部状態へ反映されるため)。

## host→core の入力経路(px68k-libretro 実装の確認)

WebX68k の `LibretroHost.setKey(retrok, down)` は内部の `keyState: Set<number>` を
更新するだけで、コアへの通知は libretro の `input_state_cb(0, RETRO_DEVICE_KEYBOARD,
0, id)` をコアが毎フレーム呼んでポーリングする形(px68k-libretro `libretro.c` の
`retro_run()` 冒頭付近、`for(i=0;i<RETROK_LAST;i++) Core_Key_State[i] = ...`)。
別途 `retro_keyboard_event_t` によるプッシュ型コールバック(`keyboard_cb`)も
コード上に存在するが `#if 0` で無効化されており使われていない(実際に確認)。

前フレームの `Core_Key_State` との差分がある場合のみ `handle_retrok()` が呼ばれ、
`Keyboard_KeyDown()`/`Keyboard_KeyUp()` が make/break コードを `KeyBuf`(リング
バッファ)へ積む。`KeyBuf` の中身は `Keyboard_Int()`(1フレームに4回呼ばれる、
`libretro.c` の scanline ループ内)が1バイトずつ取り出し、MFP割り込みとして
ゲストCPUへ配送する。

## 配送遅延の実測(発見の経緯を含む)

**最初の実装では「押し直し」テスト(setKey→runFrame→観測、を3回繰り返す)が
firstPress/releasedBeforeRepress/repressed の3項目すべて false になった。**
デバッグ出力で各ステップの生の `group6` 値を見たところ、観測される値は常に
「1つ前の遷移の結果」を示しており、押下操作から観測まで一貫してちょうど1フレーム
ずれていることが分かった。

原因はコードの実行順序にある: `retro_run()` は `WinX68k_Exec()`(ゲストCPUの実行。
この中で `Keyboard_Int()` が呼ばれ `KeyBuf` の先頭バイトを配送する)を、キーボード
入力のポーリング・`handle_retrok()` 呼び出し(=`KeyBuf` への新規書き込み)より
**前**に実行する。そのため、あるフレームの `setKey()`→`runFrame()` で変えた押下
状態は、その `runFrame()` 呼び出し内では `KeyBuf` に積まれるだけで配送されず、
**次の `runFrame()` 呼び出しの `WinX68k_Exec()` で初めて配送される**。

これを「校正」ステップとして実測で確認した: SPACEキーを独立に3回押し、
setKey(true) から何回 `runFrame()` を呼べば `HOSTVAR_GROUP6` に反映されるかを
測ったところ、**3回とも一貫して1フレーム**だった(`lag=1,1,1`)。以降の全テストは
この実測済みの遅延(`DELIVERY_LAG_FRAMES=1`)を踏まえて `runFrame()` の回数を
調整している(閾値を緩めてPASSにしたのではなく、遅延を織り込んだ上で「遅延ぶんを
除いた残りが正しく振る舞うか」を検査する形にした)。

## key_down(key) API 実装への示唆

- ゲスト側実装は「毎フレーム BITSNS を呼んでビットを見る」だけで、
  「押されている間ずっと真」をそのまま満たせる(1回読むと消える入力ではなく、
  呼ぶたびに現在のレベルが返る)。
- **ホストの入力操作からゲストが観測できるまで、最短でも1フレームの遅延がある。**
  ブロック崩しのパドル操作のように「押した瞬間から動く」体感を要る用途では、
  この1フレームの遅延を織り込んだ上で許容できるかを確認すべき(60fps相当なら
  約16msで、実用上は問題にならない可能性が高いが、体感評価はしていない)。
- 押し直し(離してすぐ押し直す)も、setKey→runFrame の呼び順さえ本番と同じに
  保てば正しく新しい押下として観測できることを確認した。ただし今回の測定は
  「host側が毎フレーム必ず1回 `runFrame()` を呼ぶ」前提での実測であり、
  もし実装が複数の押下/解放イベントを1回の `runFrame()` の間に取りこぼさず
  まとめて処理しようとする設計にする場合は、この遅延1フレームの中で
  press→release→press のような短い変化が起きたときにどう振る舞うかは
  **未検証**(下記「確定できなかった項目」参照)。

## 確定できなかった項目

- **$800番地からの直接メモリ参照**(BITSNSと同内容とされる16バイトのワークエリア)は
  文献にのみ記述があり、今回は実測していない。IOCSコール経由(BITSNS)だけで
  合格条件を満たせたため、直接参照の実装・実測は行わなかった。もし
  IOCSコールのオーバーヘッドが問題になる場面が出てきたら、別途実測が必要。
- **1回の `runFrame()` の間に複数回 setKey() で press/release を繰り返した場合の
  挙動**(例: 同一フレーム内で押して即座に離す)は未検証。今回のテストは全て
  「setKey() の後に必ず `runFrame()` を1回以上挟む」呼び順で行っている。
- UP/DOWN キー(group7 bit4/bit6)は LEFT/RIGHT/SPACE ほど個別には実測していない
  (弁別テストは LEFT/RIGHT の組のみ)。スキャンコード・group/bit の対応式は
  LEFT/RIGHT/SPACEと同じ式から機械的に導出しているため、原理的には成立すると
  推定されるが、UP/DOWN 単体での押しっぱなし・弁別の実測は行っていない。
