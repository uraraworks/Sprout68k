# 実機互換の要件追加(2026-08-19)

## 経緯

これまでの Stage A〜D は px68k(エミュレータ)上での起動を実測してきたが、
**実機(当時の X68000)で動くこと**は要件に入っていなかった。今回、それを要件に
加えたところ、その時点で以下の2点が実機非互換だと判明した。

1. **スタック位置が1MB機でRAMの外**: 直前のセッションでスタックを `$1F0000`
   (約2MB地点)へ移していたが、X68000の標準構成(ACE/EXPERT/SUPER/XVI等)は
   RAM 1MBが基本で、`$1F0000` はそのRAMの外。px68kは検証で `px68k_ramsize=2MB`
   に設定していたため、この非互換にエミュレータ上では気づけなかった。
2. **68030機での命令キャッシュ**: ディスクから読み込んだコードへJMPする構成は、
   命令キャッシュを持たない68000では無条件に動くが、68030(X68030)では
   命令キャッシュに読み込み先アドレスの古い内容が残っている可能性があり、
   キャッシュを明示的にクリアしないと誤動作しうる。

以下、それぞれの対処と実測状況を記録する。

## 1. スタック位置の既定値

### 方針

「実RAM量の動的検出」は行わない。番地を記憶や伝聞で決めないという方針の下、
SRAMの特定番地にRAM容量が入っているといった類の情報を裏を取らずに使うことを
避け、**既定値+明示パラメータのみで運用する**。

### 既定値

- 本体ロードアドレス: `$3000`(既存のまま)
- スタック既定値: **`$F0000`**
- スタックとロード末尾の間のマージン: 4096バイト
- 既定で使える本体サイズの上限: `$F0000 - $3000 - 4096 = 966,656バイト`
  (`≒ 944KB`。1MB機の実RAM `$100000` の中に収まる)

`tools/build_stage_c.sh` / `tools/build_stage_d.sh` は `STACK_ADDR`(スタック
アドレス)と `RAM_SIZE`(対象機の実RAM量。ビルド時衝突検査がこの値を超えていない
かを確認する)を環境変数として受け取る。既定値は 1MB機向け
(`STACK_ADDR=0xF0000` / `RAM_SIZE=0x100000`)。

### 大サイズ試験(近似1MB・ディスク全体)の扱い

977セクタ(約1MB)・1231セクタ(ディスク全体、本体が取り得る最大)は既定の
944KB予算に収まらない。これらは**明示的に** `STACK_ADDR=0x1F0000` /
`RAM_SIZE=0x200000`(2MB機相当)を指定してビルド・起動する
(`verify/verify.mts` の `LARGE_BUILD_ENV` / `LARGE_BOOT_RAMSIZE`)。
「ディスク全体まで読める」は**2MB以上のRAMを積んだ機械での話**であり、標準の
1MB機では本体サイズに約944KBという上限があることを、ここに条件付きで記録する。

### 本体サイズごとに必要なRAM量(表)

| 本体サイズ(目安) | 必要なRAM量 | 既定スタック($F0000)で収まるか | 検証での扱い |
|---|---|---|---|
| 〜約944KB(966,656バイト) | 1MB機で可 | 収まる | 既定値のまま(`STACK_ADDR`/`RAM_SIZE`未指定) |
| 約1MB(1,000,000バイトパターン、977セクタ) | 2MB機相当が必要 | **収まらない** | `STACK_ADDR=0x1F0000`/`RAM_SIZE=0x200000` を明示指定 |
| ディスク全体(1,260,544バイト、1231セクタ、本体が取り得る最大) | 2MB機相当が必要 | **収まらない** | 同上 |

Stage D の実際の試験サイズとの対応(`verify/verify.mts`):

| ラベル | パターンバイト数 | 実bodyサイズ | 既定(1MB機)で収まるか |
|---|---|---|---|
| small_7168 | 6,000 | 6,303 | 収まる |
| side_cross | 10,000 | 10,303 | 収まる |
| 32k | 32,000 | 32,303 | 収まる |
| 256k | 262,144 | 262,447 | 収まる |
| near_1mb | 1,000,000 | 1,000,303 | **収まらない**(2MB機相当が必要) |
| disk_max | 1,260,000 | 1,260,303 | **収まらない**(2MB機相当が必要) |

### ビルド時衝突検査の更新

`tools/build_stage_c.sh` / `tools/build_stage_d.sh` の衝突検査(本体末尾と
`STACK_ADDR` が重ならないか、`STACK_ADDR` が `RAM_SIZE` を超えていないか)は
新しい既定値(`STACK_ADDR=0xF0000` / `RAM_SIZE=0x100000`)に合わせて更新した。
**故障注入で実測済み**: 既定の944KB予算を超える構成(977セクタ相当)を
`STACK_ADDR`/`RAM_SIZE` を上書きせずにビルドすると、非ゼロ終了し `.xdf` を
一切残さないことを確認した(`verify/verify.mts` の
`STAGE_D_BUILD_COLLISION_CHECK_DETECTED`)。

### 検証ハーネス側のRAM設定

`verify/verify.mts` の `bootRaw()` に `ramSize` 引数を追加し、
`px68k_ramsize` core option をテストごとに指定できるようにした。既定944KB
予算に収まるビルド(STACK_ADDR/RAM_SIZE未指定)は `px68k_ramsize='1MB'` で
起動し、**エミュのRAM量を実機の1MB機と一致させた状態で実際に起動することを
実測**した(「エミュ側のRAMを大きく設定していたせいで実機非互換に気づけ
なかった」の再発防止)。大サイズ試験(near_1mb/disk_max)だけ
`px68k_ramsize='2MB'` を使う。

## 2. 68030機の命令キャッシュ対策

### 実装

`stage_c/boot/cache_flush.S`(Stage C/D で共用、`cache_flush_before_jump` を
$3000 への JMP 直前に呼ぶ)。

- キャッシュ制御レジスタ CACR への `MOVEC` は68010以降の命令で、68000では
  不正命令(vector4)。無条件実行は68000機を落とすため、**まず不正命令ベクタ
  (アドレス`$10`)を自前ハンドラへ差し替えてから MOVEC を試す**方式にした。
  例外が起きれば「MOVECが使えないCPU(68000/68010相当)」とみなしキャッシュ
  操作をせず戻り、例外が起きなければ CACR に `EI|CI`(bit0=命令キャッシュ
  有効化、bit3=命令キャッシュクリア。MC68020/68030の一般的なビット割当)を
  書き込む。
- 例外ハンドラは、例外前のスーパーバイザSPを**レジスタ(`%a2`)に**保存して
  おき、例外が起きたらそのSPをそのまま復元するだけで、例外スタックフレームの
  正確なバイト数(68000は6バイト固定、68010以降はフォーマット/ベクタ
  オフセットワード付きで可変)を一切解析せずに安全復帰できる設計にした。

### 実測で見つけた罠(退避先はメモリではなくレジスタにする)

最初の実装は退避先(元のSP、元のベクタ4の値)をこのファイル内のローカル
ラベル(メモリ)にしていた。これは実測で**ブートセクタが完全に無応答になる**
(画面塗り・IOCS文字列表示のどちらも実行された形跡が無い)という壊れ方をした。

原因: m68kのMOVE命令はPC相対アドレッシングを書き込み先には使えない。この
ため `move.l %sp,ローカルラベル` はアセンブラによって暗黙に絶対アドレス参照
になる。絶対アドレスはリンカスクリプト(`. = 0x0`)が仮定する「ブートセクタは
物理アドレス0にロードされる」という前提でしか正しく解決されないが、実際の
IPLはそれ以外の実アドレスにロードしている。切り分け実測(デバッグ用の
IOCS文字列を例外ハンドラの前後に仕込んで通過箇所を特定)で原因を確定し、
退避先を**レジスタ(`%a2`/`%a3`)のみ**に変更して解消した(修正後は
`STAGE C OK` / `LOAD OK` が想定通り表示されることを実測で確認済み)。

この罠は「委譲先はテストを緩めてPASSにする」ような話ではなく、**実装その
ものの初回実装ミス**であり、実測(実際に起動して画面/テキストを読む)で
初めて発覚した。故障注入や自己診断では検出できない種類のバグだったため、
「実際に動かして確認する」検証方針の価値を裏付ける事例として記録する。

### 実機/実測状況(正直に記録する)

**px68k(このリポジトリの検証ハーネスが使うコア)にはCPU種別を切り替える
core option が無い。** `px68k-libretro/libretro_core_options.h` の
`px68k_` プレフィックスの全 core option を確認したが、CPU種別
(68000/68010/68020/68030等)を切り替えるものは存在しない。さらに
`px68k-libretro/m68000/m68000.c` を確認したところ `m68k_set_cpu_type()` が
一度も呼ばれていない。Musashi(px68kが使うCPUコア)は明示的に呼ばなければ
68000として初期化される(`px68k-libretro/m68000/musashi/m68k.h` のコメント、
および `px68k-libretro/m68000/musashi/m68kops.c` の `movec_32_rc` の実装が
`CPU_TYPE_IS_010_PLUS(CPU_TYPE)` が偽なら即 `m68ki_exception_illegal()` を
呼ぶことで確認済み)。

つまり **本プロジェクトの検証環境では68030の実測は原理的に不可能**であり、
実測できたのは以下のみ:

- **68000として不正命令例外が発生し、安全にキャッシュ操作をスキップして
  正常続行する経路**: `verify/verify.mts` の全Stage(A/B/C/D、退行チェック
  含む)がこのルーチンを経由してPASSすることを実測した。

**68020/68030側(MOVECが成功しCACRへ実際に書き込む経路)は、このプロジェクトの
手段では一度も実行されておらず未検証。** 書き込む値(EI|CI = `$00000009`)は
MC68020/68030の一般に文書化されているCACRビット割当(bit0=命令キャッシュ
有効化、bit3=命令キャッシュ全体クリア)に基づく一般的な規約であり、SRAM番地の
ような「本プロジェクト固有の未文書化な値」ではないが、**実機やエミュレータで
実測した値ではない**。データキャッシュ側のビット(bit8以降)には一切触れない
設計にして、万一ビット割当の理解が誤っていた場合の影響範囲を命令キャッシュ側
だけに限定してある。

### 検証で見つかったもう1つの実測結果(検証ハーネス側の頑健性)

`cache_flush_before_jump` が68000機で不正命令例外を起こすことは今後
**毎回の起動で確実に発生する**(68000固定のpx68k上では常にこの経路を通る)。
これに伴い、px68kが例外処理中に**一時的に不正なジオメトリ(実測: 幅4096/
高さ-512)を1フレームだけ`videoRefresh`経由で報告する**ことを実測で発見した
(真の原因はpx68k内部のタイミング依存の挙動と見られ、本プロジェクトの
ブートコード側の不具合ではない)。これに対処しないと検証ハーネス(Node側)が
負のバイト長で `Uint8ClampedArray` を確保しようとして例外で落ちるため、
`verify/verify.mts` の `createImageData`/`putImageData` に、幅/高さが0以下の
フレームを安全に無視して直近の正常フレームを保持するガードを追加した。

## 検証結果のまとめ(実測した範囲を正確に記録する)

新しい既定値(1MB機相当、`STACK_ADDR=$F0000`)と `cache_flush_before_jump`
(68030キャッシュ対策)を組み込んだ上で、以下を**同期実行で実測**した:

- **陽性/陰性対照・Stage A・Stage B**: 従来通りPASS(退行なし)。
- **Stage C**(色1/色2、いずれも `px68k_ramsize='1MB'`・既定`STACK_ADDR`で
  起動): `STAGE C OK` のテキスト表示・2色の塗り分けともにPASS。
- **Stage D 小〜中サイズ**(既定`STACK_ADDR`・`px68k_ramsize='1MB'`):
  small_7168(7セクタ)・side_cross(11セクタ)・32k(32セクタ)は
  いずれも `LOAD OK` を実測。
- **Stage D 故障注入(中規模、20,000バイトパターン=20セクタ、1セクタ不足)**:
  `LOAD NG` を実測(検出できている)。同条件で不足なしのビルドは
  `LOAD OK` を実測(陽性対照)。
- **ビルド時衝突検査への故障注入**(既定予算を超える977セクタ相当を
  `STACK_ADDR`/`RAM_SIZE`を上書きせずビルド): 非ゼロ終了・`.xdf`を残さない
  ことを実測。
- **68000構成でキャッシュ対策コードが安全に素通りすること**: 上記の
  Stage C/D の全ケースが `cache_flush_before_jump` を経由した上でPASSして
  いること自体が実測結果。px68kは常に68000固定(後述)のため、この経路は
  毎回必ず通っている。

**今回のセッションでは測定していない(優先度が低いため、時間の都合で
「未測定」のまま残した。PASS/FAILを推測で埋めていない)**:

- Stage D の256KB(257セクタ)・約1MB(977セクタ)・ディスク全体(1231セクタ、
  `STACK_ADDR=$1F0000`/`RAM_SIZE=$200000`/`px68k_ramsize='2MB'`を明示指定する
  大サイズ試験)。ビルドスクリプト・検証ハーネスの実装(`LARGE_BUILD_ENV`/
  `LARGE_BOOT_RAMSIZE`)は用意済みで、単独のビルド確認(衝突検査が正しく
  通ること)は前セクションで別途実施済みだが、px68k上での起動〜LOAD OK確認
  まではこのセッションでは行っていない。
- Stage D の最大サイズ付近(1231セクタ)での故障注入
  (`STAGE_D_SELF_FAULT_INJECTION_MAX_DETECTED`)。同上の理由で未測定。

これらは前回セッションの `verify/verify.mts` 実行(コード変更前の状態、
および今回のバグ修正前の状態)では実測していたが、`cache_flush_before_jump`
バグ修正後の最新コードでは再実測できていない。次回セッションで
`npx tsx verify/verify.mts`(既定のFRAMES設定のまま、時間を確保して)を
実行し、この節を更新すること。

## 未検証のまま残った事項(動くと書かない)

- **68030実機/実エミュレータでの命令キャッシュクリア経路**: px68kにCPU種別
  切り替えが無いため、このプロジェクトの手段では一度も実行できていない。
  CACRのビット割当(EI=bit0, CI=bit3)は一般的な文書化された規約に基づく
  実装だが、実機・エミュレータいずれでも実測していない。
- **IPLのバージョン差**: X68000シリーズは機種・年代によりIPL ROMの内容が
  異なりうる。本プロジェクトが実測した挙動(IOCS $46のレジスタ規約等)は
  検証ハーネスが使う特定のIPL ROM 1種類でのみ確認したものであり、他バージョン
  のIPLでの互換性は未検証。
- **2HD媒体への書き込み手段**: 本プロジェクトはNode/px68k上で `.xdf` イメージ
  ファイルを直接生成・検証しているのみで、実際の2HDフロッピーディスク媒体へ
  書き込んで実機で起動を試したことは無い。書き込み手段・機材・手順は未検証。
- **実機のRAM実装差**: 「1MB機」を単一の均質なRAM構成として扱っているが、
  実際のX68000シリーズは増設RAM構成やアクセスウェイト等の個体差がありうる。
  それらの差異による影響は未検証。
